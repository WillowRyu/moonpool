T12 · Validate before settling a promise

응답 번호가 맞아도,
내용을 확인한 뒤 기다림을 끝냅니다.

택배의 주문 번호만 맞는다고 수령 완료로 처리하면 안 됩니다. 클라이언트도 응답 전체가 올바른 데이터인지 확인한 뒤, 그 번호로 기다리던 요청을 완료합니다.

1 · 이전에는 무엇이 부족했을까요?

단계설명
이전 동작버전·번호·result/error의 유무와 오류의 기본 필드만 검사했습니다. 결과 안쪽의 Date나 undefined가 통과할 수 있었습니다.
문제잘못된 응답이 도착해도 클라이언트가 요청을 완료하고 타이머를 지울 수 있었습니다. 그러면 나중에 오는 정상 응답을 사용할 수 없습니다.
이번 결과응답 전체의 JSON 데이터와 응답 형식을 먼저 검사합니다. 잘못된 응답은 무시하고 원래 요청과 마감 시간을 유지합니다.

T11은 호스트가 받는 요청을 검사했고, T12는 클라이언트가 받는 응답을 검사합니다. 이번에는 기존 SPEC와 JSON-RPC의 응답 규칙을 구현했으므로 새 정책 승인은 필요하지 않았습니다. 구현 결정은 ADR 0017에 기록했습니다.

2 · unknown을 실제 검사로 좁힙니다

export function isJsonRpcResponse(value: unknown): value is JsonRpcResponse {
  if (
    !isJsonValue(value) ||
    !isJsonObject(value) ||
    !Object.hasOwn(value, 'jsonrpc') ||
    !Object.hasOwn(value, 'id') ||
    value.jsonrpc !== '2.0' ||
    (typeof value.id !== 'number' && value.id !== null)
  ) {
    return false;
  }
  // Check the outcome next.
}

위 코드는 검사 함수의 앞부분입니다. unknown은 “아직 확인하지 않은 값”이라는 뜻입니다. as JsonRpcResponse로 믿어 버리지 않고, 검사를 통과할 때만 TypeScript에도 응답이라고 알려 줍니다.

isJsonValue는 이미 만든 JSON 검사 함수입니다. result·error.data·추가 항목을 포함한 전체 데이터를 확인합니다. Date·함수·undefined·NaN·순환 참조 등을 거절하며 getter나 toJSON을 호출하지 않습니다. isJsonObject로 마지막에 배열이나 null인 응답도 제외합니다.

Object.hasOwn(value, 'id')는 다른 객체에서 물려받은 값 대신 응답 자신에게 id 항목이 있는지 확인합니다. 검사는 원본 값을 바꾸거나 JSON 문자열로 변환하지 않습니다.

3 · 성공과 실패는 둘 중 하나만 있습니다

const hasResult = Object.hasOwn(value, 'result');
const hasError = Object.hasOwn(value, 'error');
if (hasResult === hasError) {
  return false;
}

두 값이 같다면 둘 다 있거나 둘 다 없는 경우입니다. 둘 다 잘못된 응답입니다. 여기서 확인하는 것은 값이 참인지가 아니라 항목이 존재하는지입니다.

응답의 결과 부분판단
result: false / 0 / "" / null정상 결과입니다. 값을 그대로 전달합니다.
result와 error가 함께 있음잘못된 응답입니다.
result와 error가 모두 없음잘못된 응답입니다.
result: null, error: undefined앞선 JSON 검사에서 거절합니다. undefined를 생략으로 바꾸지 않습니다.
isJsonObject(error) &&
Object.hasOwn(error, 'code') &&
Object.hasOwn(error, 'message') &&
typeof error.code === 'number' &&
Number.isInteger(error.code) &&
typeof error.message === 'string'

오류라면 code가 정수이고 message가 문자열인지 확인합니다. 예를 들어 -32603.5는 숫자지만 정수가 아니므로 실패합니다. 유효한 정수 오류 코드는 알려진 목록에 없더라도 보존합니다. 선택 항목 data도 JSON이면 false·0·빈 문자열·null을 그대로 전달합니다.

4 · 검사를 통과해야 대기표를 꺼냅니다

if (!isJsonRpcResponse(message)) {
  return;
}
if (message.id === null) {
  return;
}

const entry = pending.get(message.id);
if (entry === undefined) {
  return;
}
pending.delete(message.id);
clearTimeout(entry.timer);

pending은 아직 답을 기다리는 요청의 대기표 보관함입니다. Map에 요청 번호별 Promise의 resolve·reject와 타이머를 넣어 둡니다. Promise는 나중에 결과를 받겠다는 약속이고, resolve는 성공 완료, reject는 실패 완료입니다.

응답 도착
→
JSON·응답 형식 검사
→
번호로 대기표 찾기
→
대기표·타이머 정리
→
성공 또는 오류 전달

기존 클라이언트도 검사 뒤에 대기표를 처리했습니다. 이번에는 그 검사를 강화하고, 받는 값을 unknown으로 표시했습니다. 잘못된 응답에는 답장을 보내지 않고, 기존 타이머를 다시 시작하지도 않습니다.

entry.reject(new MoonpoolError(error.code, error.message, error.data));
// Or, for a successful response:
entry.resolve(message.result);

이 두 줄은 서로 다른 분기에서 실행됩니다. 유효한 오류는 실패로, 유효한 결과는 성공으로 전달합니다. 호스트가 민감한 내용을 제거해 만든 오류도 코드·메시지·data를 그대로 받습니다. 클라이언트의 JSON 검사가 비밀번호 같은 내용을 알아서 찾아 지우는 것은 아닙니다.

5 · 잘못된 답장 뒤에 정상 답장이 오면?

h.inject(make()); // A malformed response for request 1.
await flush();
expect(first.settled).not.toHaveBeenCalled();
expect(vi.getTimerCount()).toBe(2);

h.inject(success(2, { displayName: 'Second reply first' }));
expect(await second.outcome).toEqual({
  value: { displayName: 'Second reply first' },
});
expect(vi.getTimerCount()).toBe(1);

h.inject(success(1, false));
expect(await first.outcome).toEqual({ value: false });
expect(vi.getTimerCount()).toBe(0);

테스트의 작은 전송 장치가 응답을 직접 전달합니다. 처음에 두 요청이 기다리고 있을 때 잘못된 답장을 넣어도 둘 다 기다립니다. 2번 응답이 먼저 오면 2번만 끝내고, 나중에 1번의 정상 응답이 오면 1번을 완료합니다. 응답의 완료 순서는 요청 순서와 달라도 됩니다.

새 테스트 116개를 구현 전에 작성했고, 실제 동작을 비교한 RED 실행에서는 39개가 실패하고 77개는 기존 동작을 확인하며 통과했습니다. 구현 후 모두 통과했습니다. 잘못된 응답을 반복해도 원래 시각에 시간 초과가 발생하고, 이미 끝난 번호·모르는 번호·id:null 응답은 다른 요청을 끝내지 못하는 것도 확인했습니다.

6 · 이번 검사가 보장하는 범위

이번 검사는 공통 응답 형식과 JSON 데이터를 확인합니다. profile.get 결과에 displayName이 있는지 같은 메서드별 의미 검사는 별개입니다. initialize의 기존 결과 타입 단언도 이번 작업에서 바꾸지 않았습니다. 새 코드에는 타입 단언을 추가하지 않았습니다.

호스트가 잘못된 요청 번호 0·음수·소수를 오류에 그대로 돌려주는 기존 규칙을 유지합니다. 클라이언트는 자신이 실제로 발행해 기다리는 번호만 Map에서 찾으므로, 그런 번호가 다른 요청을 완료하지 않습니다. 성공 응답의 id:null은 여전히 거절합니다.

임의 Proxy의 부수 효과, 크기 제한, 이전 문서의 늦은 응답 문제는 기존 한계로 남습니다. SPEC §9의 출처·권한 경계도 그대로이며, 이번에 호스트 접근 권한을 늘리는 변경은 없습니다.
