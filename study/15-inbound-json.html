T11 · Inspect the envelope, then validate the params

기능을 실행하기 전에,
메시지 전체가 데이터인지 확인합니다.

기존 저장 값 검사에 더해 메시지의 바깥 항목과 인자 전체를 확인합니다. 권한 오류와 입력 오류의 순서를 지키면서 getter 실행과 자동 변환을 막습니다.

1 · 이전 동작과 이번 결정의 결과

단계설명
이전 동작storage.set의 value는 깊이 검사했지만, 메시지의 다른 추가 항목은 JSON인지 확인하지 않았습니다.
현재 문제profile.get의 추가 항목에 Date·undefined 등이 있어도 기능이 실행될 수 있었습니다. 속성을 읽다가 getter 코드가 실행되는 경우도 있었습니다.
승인한 결과바깥 메시지의 잘못된 데이터는 -32600, 인자 안의 잘못된 데이터는 초기화·권한 확인 후 -32602로 거절합니다. 정상 JSON 추가 항목은 허용합니다.

2026.10.23에 권장안을 승인받아 SPEC §4.1·§4.2·§5.1에 먼저 반영했습니다. ADR 0016에는 번호·초기화·권한 검사와의 순서를 기록했습니다.

2 · id를 읽는 것부터 검사합니다

id = storedValue(Object.getOwnPropertyDescriptor(value, 'id'));

새 내부 파일 packages/host/src/incoming-request.ts에서 받은 값을 unknown으로 검사합니다. Object.getOwnPropertyDescriptor는 실제 속성을 읽어 getter를 실행하지 않고, 그 속성의 설명 정보를 가져옵니다.

function storedValue(descriptor: PropertyDescriptor | undefined): unknown {
  return descriptor !== undefined && Object.hasOwn(descriptor, 'value')
    ? descriptor.value
    : undefined;
}

설명표에 저장된 value가 있는 경우만 값을 사용합니다. getter라면 실행해서 id를 만들지 않습니다. 안전하게 읽을 수 있는 직접 저장된 숫자 id가 없으면 응답하지 않는 규칙을 따릅니다.

숨겨진 속성, symbol 키, Date 같은 특수 객체, 함수, 순환 데이터도 유효한 JSON 봉투로 인정하지 않습니다. 숫자 id가 NaN이나 Infinity이면 오류 응답에는 null을 사용해 응답 자체가 JSON이 되도록 합니다.

3 · 봉투와 인자를 각각 알맞은 단계에서 검사합니다

delete descriptors.params;
const envelope: unknown = Object.create(Object.getPrototypeOf(value), descriptors);
const envelopeIsJson = paramsDescriptorValid && isJsonValue(envelope);

descriptors는 원본에서 새로 얻은 속성 설명표입니다. 위 코드는 그 설명표로 검사용 봉투를 만들며, 원본 메시지나 params를 삭제하지 않습니다. params 속성 자체도 저장 값인지 확인하고, 원래 params의 내용은 다음 검사 단계까지 그대로 보관합니다.

바깥 부분은 isJsonValue로 확인합니다. 이 함수는 이전 저장 값 검사에서 만든 것으로, 자동 문자열 변환 없이 값의 안쪽까지 확인합니다. 새로 만든 파서로 JSON 글자를 읽는 작업이 아닙니다.

export function isJsonParams(value: unknown): value is Record<string, JsonValue> | undefined {
  return value === undefined || (isJsonValue(value) && isJsonObject(value));
}

인자는 그다음 이 검사로 좁힙니다. 이 함수에 도착하기 전에 params의 바깥 모양과 생략 여부를 이미 확인합니다. 따라서 여기의 undefined는 실제 생략을 뜻합니다. 직접 params: undefined를 넣은 메시지는 앞 단계에서 -32602로 거절합니다.

유효한 요청은 봉투와 인자 모두 검사한 뒤 기능 호출로 진행합니다. 잘못된 값을 제거하거나 Date를 문자열로 바꿔서 통과시키지 않습니다. provider가 받는 저장 값도 원래 참조와 내용을 보존합니다.

4 · 오류가 여러 개면 정해진 순서로 판단합니다

→

→

-32602
→

그림은 일반 호출의 오류 판단 순서입니다. 바깥 검사 결과를 미리 수집하더라도, 중복 번호에는 T10의 id:null 오류를 우선 반환합니다. 초기화는 별도 분기에서 문서 경계를 적용합니다.

상황결과
profile.get의 추가 envelope 항목이 Date-32600 · 기능 호출 없음
권한 없는 storage.set의 value가 NaN기존처럼 -32000 · 권한을 먼저 확인
권한 있는 storage.set의 value가 NaN-32602 · provider 호출 없음
권한 있는 profile.unknown의 params에 Date메서드 조회 전에 -32602
형식이 맞는 unknown 메서드와 정상 JSON params기존 권한 확인 후 -32601
중복 번호와 잘못된 envelope 데이터T10의 -32600 / id:null

초기화의 바깥 메시지가 잘못됐다면 기존 문서 상태를 초기화하지 않습니다. 바깥 메시지와 params 모양은 맞지만 인자 안에 getter 같은 잘못된 값이 있다면 새 문서 경계는 적용하고, 초기화 상태를 false로 바꾼 뒤 -32602로 거절합니다.

SPEC §9.3·§9.6의 권한·입력 경계를 다룹니다. 정상 JSON 추가 항목은 계속 허용하지만, 그것으로 권한을 늘릴 수는 없습니다. 실제 권한은 호스트가 정한 grantedScopes가 결정합니다.

5 · 거절되는 입력과 정상 연결을 함께 확인했습니다

처음 58개 테스트에서 49개의 실패를 확인한 뒤 구현했습니다. 검토 중 함수 자체가 메시지인 경우도 추가해 실패를 확인하고 보완했습니다. 최종 새 테스트는 59개이며 모두 통과합니다. 기존 NaN 오류 응답 테스트는 승인된 id:null 정책에 맞게 수정했습니다.

테스트는 실제 호스트에 잘못된 값을 직렬화 없이 넣습니다. getter·toJSON 미실행, 원본 보존, 숨겨진 속성과 symbol, 순환·공유·깊은 데이터, 번호와 초기화 순서, 권한과 provider 호출 여부를 확인합니다. 임의 Proxy가 일으킬 수 있는 모든 부수 효과나 동시 변형, 크기 제한은 이번 검사의 보장 범위가 아닙니다.

실제 브라우저의 서로 다른 origin에서도 초기화, Moonpool Explorer 표시, storage 허용 구성의 저장과 조회가 동작하는 것을 확인했습니다.
