T06 · Check the entry and recognize the scopes

시작 파일은 앱 안에,
권한 이름은 실제 규칙 안에.

T05가 설정 서류의 항목과 자료형을 확인했다면, T06은 시작 파일 경로의 문법과 요청한 권한 이름을 확인합니다. 두 단계를 합쳐 공개 함수 parseManifest를 완성했습니다.

퍼센트 인코딩, 역슬래시, 폴더 경로를 어떻게 해석할지는 기존 명세에 없었습니다. 승인한 규칙을 먼저 SPEC §7과 ADR 0011에 기록한 뒤 구현했습니다.

2 · 애매한 경로를 자동으로 고치지 않습니다

if (
  entry === '' ||
  entry !== entry.trim() ||
  entry.startsWith('/') ||
  /[\\%:?#\p{Cc}]/u.test(entry)
) {
  return false;
}

빈 문자열, 앞뒤 공백, 맨 앞 슬래시, 금지 문자를 확인합니다. ||는 하나라도 해당하면 거절한다는 뜻입니다. trim의 결과는 비교에만 쓰며, 입력을 잘라서 통과시키지 않습니다.

정규식의 \\는 역슬래시 한 글자를 찾는 표기이고, \p{Cc}는 줄바꿈·탭·NUL 등을 포함한 유니코드 제어문자를 찾습니다. 퍼센트는 모두 거절하므로 %2e%2e를 디코딩할 횟수를 고민할 필요가 없습니다.

입력결과이유
pages/start.html허용일반 상대 파일 경로
시작/화면.html허용문자 그대로 쓴 Unicode 경로
pages/hello world.html허용경로 안쪽의 공백은 허용
https://other.example/index.html거절콜론을 포함한 URL
pages%2Fstart.html거절인코딩된 경로
pages\start.html거절역슬래시는 구분자로 사용하지 않음
index.html?theme=dark거절파일 경로에 쿼리를 섞지 않음
const segments = entry.split('/');
const last = segments.at(-1);
if (last === undefined || last === '' || last === '.' || last === '..') {
  return false;
}

split은 슬래시마다 나누고, at(-1)은 마지막 구간을 가져옵니다. pages/, pages/., pages/..처럼 폴더만 가리키는 형태를 거절합니다. 파일 확장자는 요구하지 않으므로 pages/start도 문법상 허용합니다.

3 · ..를 발견할 때마다 현재 위치를 확인합니다

let depth = 0;
for (const segment of segments) {
  if (segment === '' || segment === '.') {
    continue;
  }
  if (segment === '..') {
    if (depth === 0) {
      return false;
    }
    depth -= 1;
  } else {
    depth += 1;
  }
}
return true;

일반 이름을 지나면 1을 더하고, ..로 돌아오면 1을 뺍니다. 빈 중간 구간과 .은 현재 위치를 바꾸지 않습니다. continue는 그 구간의 나머지 처리를 건너뛰고 다음 구간으로 이동합니다.

경로읽는 순서판정
pages/../index.htmlpages: 0→1 · ..: 1→0 · index.html: 0→1허용
../index.html첫 ..에서 이미 depth가 0즉시 거절
a/../../a/index.htmla: 0→1 · ..: 1→0 · 다음 ..에서 거절뒤에 다시 들어와도 거절

성공해도 entry를 다시 조립하지 않습니다. 입력 경로를 그대로 보존하고 유효성만 판단합니다. 파일시스템이나 브라우저 URL API를 사용하지 않으므로 같은 검사를 다른 전송 환경에서도 재사용할 수 있습니다.

검사의 경계: 이것은 경로 글자의 문법 검사입니다. 파일이 실제로 존재하는지, 심볼릭 링크가 밖을 가리키는지는 파일을 읽는 로더의 책임입니다. 커널이 파일시스템을 조사했다고 주장하지 않습니다.

4 · 권한 이름은 메서드의 앞부분에서 얻습니다

const capabilityScopes = new Set(
  [...Object.values(PROFILE_METHODS), ...Object.values(STORAGE_METHODS)].map((method) =>
    method.slice(0, method.indexOf('.')),
  ),
);

Object.values는 메서드 이름을 꺼내고, map은 이름마다 점 앞부분을 추출합니다. profile.get에서는 profile, storage.get·set·delete에서는 storage를 얻습니다. Set에 넣으면 중복된 storage는 한 번만 남습니다.

이렇게 하면 권한 목록을 별도로 손으로 관리하지 않아도 됩니다. 현재 허용 이름은 profile과 storage입니다. portal은 권한 없이 쓰는 프로토콜 전용 이름이므로 권한 선언 목록에 포함하지 않습니다.

if (!manifest.permissions.every((scope) => capabilityScopes.has(scope))) {
  throw new ManifestError(
    'permissions',
    'manifest.permissions contains an unknown capability scope',
  );
}

every는 모든 항목이 아는 이름인지 묻고, has는 집합에 그 이름이 있는지 확인합니다. 한 개라도 모르면 서류 전체를 거절합니다. 몰래 빼고 계속하지 않습니다. 빈 배열은 허용하며, 원래 배열의 순서와 중복은 보존합니다.

5 · 선언이 통과해도 실제 권한이 생기지는 않습니다

설정과 호스트 상태storage.get 결과
storage 선언 · 호스트 허용 없음-32000 · 권한 거절
선언 없음 · 호스트가 storage를 허용-32000 · 공통으로 허용한 권한이 없음
storage 선언·허용 · provider 없음-32001 · 알고 있는 기능이지만 구현이 설치되지 않음

SPEC §9의 보안 경계를 다룹니다. §9.3에 따라 요청을 실제 처리하기 직전에 호스트가 권한을 검사하고, §9.7에 따라 실제 grantedScopes만 권한을 부여합니다. 파서는 이름을 확인할 뿐 호스트 허용이나 provider 설치를 대신하지 않습니다.

테스트는 실제 client와 host를 메모리 전송으로 연결해 위 세 경우를 확인합니다. 문자열 검사만 통과했다고 저장 기능을 사용할 수 있게 되는 일이 없습니다.

6 · 밖에서는 한 함수로 검사합니다

import { ManifestError, parseManifest } from '@moonpool/host';

try {
  const manifest = parseManifest(manifestText);
  // The embedder can use the validated manifest to configure a Portal.
} catch (error) {
  if (error instanceof ManifestError) {
    // error.field identifies the failed configuration field.
  }
}

manifestText는 호스트가 읽어 온 JSON 글자입니다. 파서는 T05 필드 검사 → 경로 검사 → 권한 이름 검사 순서로 확인합니다. 실패하면 어느 칸이 문제인지 field에 담은 로컬 오류를 던집니다. 오류에 검사하지 않은 경로나 권한 원문을 복사하지 않습니다.

이 함수는 파일을 읽거나 브리지를 열지 않습니다. 순수한 동기 설정 검사이며, 모든 capability를 비동기로 유지하는 약속과 충돌하지 않습니다. protocolVersion의 실제 지원 여부도 연결할 때의 handshake가 판단합니다.

7 · 실패를 먼저 확인하고 규칙을 구현했습니다

권한 검사 전에는 13개, 기본 경로 검사 전에는 4개, 승인된 추가 경로 검사 전에는 40개가 예상대로 실패했습니다. 정상 경로와 필드 검사 재사용, 실제 권한·provider 경계를 포함한 T06 테스트는 총 107개이며 이제 모두 통과합니다.
