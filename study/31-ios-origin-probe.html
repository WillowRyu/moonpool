2 · URL을 받아 주는 것과 격리는 다른 검사입니다

configuration.setURLSchemeHandler(handler, forURLScheme: "moonpool")
// Measured page origins:
"moonpool://com.example.probe.a"
"moonpool://com.example.probe.b"

WKURLSchemeHandler는 moonpool 주소의 요청에 번들 파일을 공급하는 담당자입니다. HTML이 화면에 보인다는 사실만으로 보안 출처까지 분리됐다고 단정할 수 없어, 실제 페이지의 origin과 서버가 받은 Origin 헤더를 따로 확인했습니다.

// A can read its own loaded frame.
selfFrame.domMarker;     // "a"
selfFrame.storageMarker; // "a"

// B really loaded; A still cannot read B's DOM or localStorage.
crossFrame.loadedMarker; // "b"
crossFrame.domError;     // "SecurityError: ..."
crossFrame.storageError; // "SecurityError: ..."

다른 앱의 프레임이 로드되지 않았다면 접근 실패의 원인을 구분할 수 없습니다. 그래서 프레임의 공개 메시지로 로드를 확인하고, 같은 앱 접근은 성공하는지 대조한 뒤 다른 앱 접근의 차단을 확인했습니다.

보안 명세 §9: 탐색 콜백의 sourceFrame.securityOrigin도 관찰했지만, 이것은 실제 브리지 메시지의 발신자 인증이 아닙니다. 이번 앱에는 게스트가 호출하는 네이티브 핸들러가 없습니다. 메시지·프레임·문서 신원은 T26에서 따로 시험합니다.

3 · 저장소 세 종류를 따로 판정했습니다

let store = WKWebsiteDataStore.default()
configuration.websiteDataStore = store // Same store for A and B.

// A and B write the SAME key with different public values.
localStorage.setItem(key, app); // A writes "a"; B writes "b".

별도 데이터 저장소를 앱마다 만들어 주면 원래 출처의 격리 능력을 확인하기 어렵습니다. 이번에는 기본 영구 저장소 하나를 함께 사용했습니다. A에 값을 쓴 뒤 B에 같은 키를 쓰고, A를 다시 읽어도 a가 남는지 확인했습니다. IndexedDB도 같은 방식으로 검사했습니다.

같은 앱의 두 번째 WebView, 새로고침, WebView 재생성, 네이티브 앱 프로세스 종료·재실행에서도 자기 앱 값이 유지됐습니다. 시뮬레이터 재부팅·OS 업데이트·강제 WebKit 프로세스 종료나 전원 손실까지 검증한 것은 아닙니다.

쿠키는 custom scheme에서 쓴 뒤에도 빈 문자열이었습니다. HTTP 대조군의 localhost와 127.0.0.1에서는 첫 페이지에서 각 앱 쿠키가 저장됐지만, 다른 앱으로 이동한 관찰과 앱 재시작 뒤에는 비었습니다. 만료기한 없는 세션 쿠키를 사용했으므로 영구 쿠키의 지속성까지 검증한 것은 아닙니다. 포트만 다르게 하면 쿠키를 나눌 수 없으므로 호스트 이름도 다르게 정한 대조군입니다.

storage.*와 구분하기: 이번 검사는 웹 엔진의 localStorage·IndexedDB·cookie입니다. Moonpool의 storage.get/set은 호스트가 앱 ID로 나누는 별도 provider이며, 이번 실험에는 연결하지 않았습니다.

4 · 시작을 확인한 뒤에 취소해야 합니다

처음에는 load 후 100ms가 지나면 WebView를 제거했습니다. 그런데 실제 리소스 요청이 시작되기 전이라 취소 콜백을 검증하지 못했습니다. 먼저 “지연 요청이 실제 시작돼야 한다”는 검사를 추가하니 실패했습니다.

guard self.pending.removeValue(forKey: key) != nil else {
    // The stopped task no longer owns permission to receive callbacks.
    self.record?(["type": "scheme-suppressed-after-stop", "task": number])
    return

이제 실제 시작 콜백을 받은 뒤 중단합니다. 늦게 실행된 작업은 pending 목록에서 자기 항목이 사라진 것을 보고 응답·데이터·완료를 전달하지 않습니다. 최종 custom scheme 세 실행 모두 start → stop → suppressed를 기록했고 남은 작업은 0개였습니다.

이 코드는 실험 리소스의 취소 확인입니다. Moonpool의 연결 종료·앱 수명 계약 전체는 후속 task에서 정합니다.

5 · 반복과 오프라인 대조군을 남겼습니다

같은 최종 앱으로 custom scheme의 seed·restart, HTTP의 seed·restart, 서버를 끈 custom scheme까지 다섯 번 실행했습니다. 각 실행은 A/B 첫 관찰·재읽기·같은 앱 두 번째 뷰·새로고침·재생성·앱 간 이동·외부 이동·복귀의 11개 관찰을 남깁니다.

서버를 끄면 외부 HTTP 요청과 이동은 실패하지만 번들 HTML·JS·CSS·이미지·JSON은 계속 읽혔습니다. 누락 파일과 경로 탈출 요청은 로컬 404로 남았습니다. 이는 로컬 파일 공급과 테스트 서버 요청을 구분한 실험이며, 기기 전체 인터넷을 끈 실험은 아닙니다.

python3 experiments/ios-origin-probe/verify_results.py \
  experiments/ios-origin-probe/results
pnpm run check

빌드의 SDK 경고도 재현한 뒤 xcrun 단계에서 iphonesimulator를 명시해 해결했습니다. 바이너리의 대상·SDK를 검사하고 실제 설치·실행까지 확인했습니다. 새 SDK나 패키지를 설치하지 않았고, 전용 시뮬레이터만 사용한 뒤 종료했습니다.
