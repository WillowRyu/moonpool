1 · RN 앱에만 묶이지 않는 쪽을 선택했습니다

호스트가 RN이라고 정하면 RN의 앱용 JS 환경을 재사용할 수 있습니다. 다만 순수 네이티브나 Flutter 앱에는 그 환경이 없습니다. 이번에는 Moonpool 네이티브 SDK가 자체 호스트 실행 환경을 소유하는 모델을 골랐습니다. 실제 사용 앱의 저장소와 화면은 T56에서 선택합니다.

앱의 기술선택한 SDK에 연결하는 경로이번 검증 범위
Swift / Kotlin각 OS의 네이티브 API를 직접 호출호스트 런타임 호환성 실험 완료 · 제품 SDK는 후속 구현

Facade는 내부 엔진을 직접 다루지 않아도 되도록 제공하는 진입점이라는 뜻입니다. 앱 화면은 네이티브 API를 호출하고, SDK가 Portal과 커널의 생성·연결·폐기를 맡습니다. 아래 그림은 소유권 설명이며 아직 설치 가능한 공개 API의 모양은 아닙니다.

공통 기반을 선택했다는 뜻입니다. 모든 프레임워크의 설치·화면·수명 연동이 이미 검증됐다는 뜻으로 읽으면 안 됩니다. RN·Flutter 연결 모듈은 필요할 때 별도 범위로 다룹니다.

2 · 네이티브 앱에도 JS 커널을 돌릴 엔진이 필요합니다

TypeScript는 JavaScript로 묶어 실행합니다. Swift/Kotlin 앱이 그 코드를 저절로 실행하지는 않으므로 JS 엔진을 연결해야 합니다. 게스트 페이지의 엔진에 호스트 커널까지 넣으면 미니 앱의 수명과 호스트 권한이 섞입니다. 전용 환경에는 앱이 패키징한 신뢰된 호스트 코드만 넣습니다.

Trusted host

네이티브 SDK + 전용 JS 환경

네이티브 관리자가 앱 설정·권한·실제 제공자·자격 증명을 소유합니다. JS 환경의 Host는 공통 권한 검사와 요청 처리를 맡습니다. 제공자 연결에는 공개 JSON 값만 전달합니다.

Mini app / Client
게스트가 호스트 설정·권한·저장 파티션을 선택하지 못함

호스트가 가진 로그인 토큰을 JS 커널이나 미니 앱에 복사할 필요는 없습니다. 네이티브 제공자가 토큰을 사용해 작업하고, 허용한 공개 결과만 돌려줍니다. 이 결정은 SPEC §3의 플랫폼 경계와 §9의 신뢰 경계를 다룹니다. 기존 JSON-RPC 형식과 세 메서드 Transport 인터페이스는 유지했습니다.

3 · 기존 커널을 고치지 않고 두 엔진에서 실행했습니다

약 37 KB의 같은 실험 번들에 실제 protocol·client·host 코드를 포함했습니다. 실험에서는 Client와 JS 제공자 대역을 함께 두어 실제 핸드셰이크·권한·오류 처리를 호출했습니다. 제품 Client는 게스트에 놓이며, 이번 배치는 실제 네이티브 제공자나 게스트 통로의 완성 검사가 아닙니다.

OS실측 환경선택한 실행 소유권
iOSiOS 26.4.1 전용 시뮬레이터 · JavaScriptCorePortal별 VM/context와 전용 직렬 큐
AndroidAndroid 17 / API 37 전용 에뮬레이터 · JavaScriptEngine 1.1.1 지원 확인앱별 sandbox 하나 · Portal별 isolate · 직렬 native executor

VM/context와 isolate는 여기서 호스트 JS 전역과 실행 상태를 따로 보관하는 단위입니다. Android는 제공자의 엔진 지원을 먼저 확인하고 미지원이면 차단합니다. Android sandbox가 죽으면 여러 isolate가 함께 영향을 받을 수 있고, iOS JSC는 앱 프로세스 안에서 실행됩니다. 분리된 JS 전역만으로 모든 프로세스 장애가 격리되는 것은 아닙니다.

native owner A → private host runtime A → Host A
native owner B → private host runtime B → Host B

guest document replacement: keep the Portal's host owner
Portal retirement: retire that host owner terminally

전용 엔진을 소유하면 앱 프레임워크에 덜 의존하지만 엔진 생성·타이머·제공자 연결과 자원 관리 비용이 생깁니다. 메모리·Pool 기본값과 지원 최소 OS는 이번 작은 실험으로 정하지 않았습니다.

4 · 현재 문서를 찾지 않고 원래 소유자에게 돌아갑니다

네이티브에서 예약한 작업도 자신이 속한 소유자를 붙잡아야 합니다. 이전 소유자의 작업이 늦게 끝났을 때 전역의 ‘현재 Portal’을 찾아 보내면 새 소유자에게 잘못 전달할 수 있습니다. 실험은 이전 소유자를 캡처한 뒤 폐기 상태를 확인해 제어 호출을 버렸습니다.

// From the iOS probe: captured owner, not a current-runtime lookup.
self.queue.asyncAfter(deadline: .now() + 0.04) {
    guard self.active else {
        self.note(self.name, "late-control-dropped")
        return
    }
    self.note(self.name, "late-control-unexpectedly-active")
}

런타임 소유자는 Portal 단위이고 문서 세대는 게스트 문서의 연결 단위입니다. 허용된 A→B 문서 교체에서 호스트 런타임을 매번 없애는 모델은 아닙니다. 이전 문서의 응답을 막는 세대 계약은 T30/T31에서 더 정합니다. 이미 시작한 네이티브 저장이나 다른 효과를 자동 취소·복구한다는 규칙도 추가하지 않았습니다.

저장 제공자는 버려지는 Portal 바깥에서 앱별로 유지합니다. 이번 실험은 A의 공개 스냅샷을 네이티브 관리자가 보관해 새 A에 넣고 B에는 넣지 않는 흐름만 확인했습니다. 실제 디스크 저장·동시 제공자 공유는 아직 검증하지 않았습니다.

5 · 통과한 검사와 남은 구현을 구분합니다

12두 OS 첫 실행·재실행의 소유자

실제 커널의 초기화·ping·프로필 공개 필드·저장·권한 거절·알림·제공자 오류 숨김을 확인했습니다. Promise·Map·Reflect·속성 검사·JSON, 타임아웃·타이머 취소·microtask 순서도 두 엔진에서 통과했습니다. Node VM 계약 테스트 두 개도 통과합니다.

실험용 타이머: 네이티브가 주기적으로 tick을 호출하는 작은 대역입니다. 커널 실행에 필요한 동작을 확인했으며, 제품의 타이머 방식·모든 작업 순서·백그라운드·성능 정책까지 승인한 것은 아닙니다. 제품 스케줄러는 T35에서 구현·검증합니다.
python3 experiments/trusted-runtime-probe/build_bundle.py
pnpm exec vitest run --config experiments/trusted-runtime-probe/vitest.config.ts
pnpm exec tsc --noEmit -p experiments/trusted-runtime-probe/tsconfig.kernel.json
python3 experiments/trusted-runtime-probe/verify_results.py experiments/trusted-runtime-probe/results

기존 사용자 기기를 제외한 실험 소유 기기만 사용하고 종료했습니다. Android 실험에만 엔진 라이브러리를 추가했으며 루트·순수 커널 의존성과 프로토콜 0.1은 그대로입니다. 문서 세대의 별도 안전성 테스트 세 개도 아직 RED입니다.
