영문 세부 계획에 각 task의 완료 조건·선행 task·정책 관문을 적었습니다. 아래 표는 공부하며 따라갈 수 있는 요약입니다. 기간이나 새 버전 번호는 아직 정하지 않았습니다.

2 · 먼저 확인할 세 가지가 있습니다

문서 세대 방식은 ADR 0024로 채택했습니다. T30의 상세 계약과 T32 구현은 아직 완료하지 않았습니다. T27에서 범용 네이티브 SDK와 전용 호스트 실행 위치·소유권을 선택했습니다.

앱별 출처가 실제로 분리되는가

현재 명세는 moonpool://<mini-app-id>/를 요구합니다. Android 공식 자산 로더는 HTTP(S)를 설명하고, iOS의 커스텀 스킴 처리도 실제 저장소·출처 동작을 증명하지는 않습니다. T23·T24에서 실측하고 T28에서 필요한 결정을 합니다.

TypeScript 호스트 커널은 어디서 실행하는가

T27에서 Swift/Kotlin 기반과 iOS JSC·Android JavaScriptSandbox를 선택했습니다. 호스트 커널은 게스트 문맥과 분리하고 네이티브 SDK가 소유합니다. RN·Flutter는 각각의 연결 모듈이 필요하며 아직 구현하지 않았습니다.

문서 교체와 종료를 어떻게 구분하는가

오래된 응답이 새 문서에 붙는 문제, 상대 종료 시 대기 요청 처리, 문자열 전송의 값·오류 규칙을 계약으로 정해야 합니다. 필드 이름이나 오류 코드를 지금 임의로 추가하지 않고 T29–T31에서 근거와 선택 결과를 설명한 뒤 확정합니다.

정책 질문은 이전 동작 → 새 플랫폼에서 생긴 문제 → 선택할 경우의 결과 순서로 설명합니다. T28과 ADR 0026의 구체적인 제안을 읽을 수 있습니다. 초안이 작성됐다는 사실은 계약 승인을 뜻하지 않습니다. 현재 명세·출처 규칙은 그대로 유지됩니다.

3 · T22–T27 완료 · T28 계약안을 검토합니다

T22에서 두 OS의 실제 설치 도구와 가상 기기 후보, 남은 지원 범위·호스트 선택 조건을 기록했습니다. T22의 명령과 쉬운 설명으로 결과를 읽을 수 있습니다. 이미 미정이라고 답한 호스트 기술을 다시 같은 질문으로 묻지 않고, 구체적인 선택지가 준비됐을 때 결정합니다.

T23에서 Android의 실제 출처·저장소 격리 실패를 확인했습니다. T23 해설에 이어 T24 iOS 해설에서 앱별 출처·DOM·저장소 분리와 쿠키 한계를 확인할 수 있습니다. 이어 T25 Android 메시지 실험에서 실제 출처·프레임과 포트 전달을 검증했습니다. T26 iOS 메시지·reply·실행 문맥 실험도 완료했습니다. 이어서 T27에서 범용 Swift/Kotlin SDK와 전용 호스트 런타임을 선택하고 두 OS에서 같은 커널을 검증했습니다. T28은 출처·로더·초기화 권한 계약안을 작성했습니다. Android 로컬 HTTPS와 앱별 웹 데이터 보관함을 실측했습니다. 이후 공통 비동기 쿠키·HTTP 설계를 추가했습니다. 기존 쿠키 차이를 제품 동작으로 남기지 않으며 새 검증과 최종 계약 승인 전이므로 T28은 아직 완료하지 않았습니다. 단순히 문서에 API가 있다는 사실만으로 네이티브 구현 완료를 선언하지 않습니다. 초기 실험의 에뮬레이터·시뮬레이터 결과와 실기기 결과도 구분합니다.

진행 방식
task 하나 → 필요한 실패 테스트·구현·검증 → 쉬운 한국어 코드 설명 → 계획과 HANDOFF 갱신
Android·iOS 양쪽 관문을 모두 통과해야 해당 단계 완료
현재 상태
T22 환경 조사와 T23 Android 실측을 마쳤습니다. 실험 앱은 에뮬레이터에서 실행했으며, 확인한 격리 실패를 근거로 T28의 계약 관문은 유지합니다. iOS도 T24 출처와 T26 메시지·응답을 전용 시뮬레이터에서 검증했습니다. T27의 실행 위치·소유권 결정도 완료했습니다. 실제 앱은 T56에서 선택하며, 공통 문서 신원과 인증 계약은 후속 결정에 남아 있습니다. 기존 브라우저 완료 기록과 현재 1,134개 테스트 기준은 유지합니다.

Pool은 기존 ADR 0002의 네이티브 목표를 계획에 넣은 것입니다. 앱 전체 메모리 관리자나 분석 기능을 추가하는 작업이 아닙니다. 새 기능·숫자 정책은 근거와 승인된 계약을 먼저 갖춥니다.
