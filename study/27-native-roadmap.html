두 플랫폼을 함께,
설계 확인부터 실제 앱까지.

브라우저 v0.1 다음 작업을 T22–T65의 44개 task로 나눴습니다. Android와 iOS를 짝으로 검증하며, 한쪽 결과로 다른 쪽을 완료 처리하지 않습니다. 호스트 앱은 아직 미정이므로 공통 계획부터 만들었습니다.

T45는 양쪽 앱에서 돌아가는 첫 사용 지점입니다. 고객 운영 배포는 이후 안정화와 실제 앱 검증까지 통과해야 판단할 수 있습니다. npm 공개 발행은 필수가 아니며, 선택한 앱에서 소비 가능한 묶음이면 됩니다.

영문 세부 계획에 각 task의 완료 조건·선행 task·정책 관문을 적었습니다. 아래 표는 공부하며 따라갈 수 있는 요약입니다. 기간이나 새 버전 번호는 아직 정하지 않았습니다.

2 · 먼저 확인할 세 가지가 있습니다

앱별 출처가 실제로 분리되는가

현재 명세는 moonpool://<mini-app-id>/를 요구합니다. Android 공식 자산 로더는 HTTP(S)를 설명하고, iOS의 커스텀 스킴 처리도 실제 저장소·출처 동작을 증명하지는 않습니다. T23·T24에서 실측하고 T28에서 필요한 결정을 합니다.

TypeScript 호스트 커널은 어디서 실행하는가

호스트 앱이 미정이라 React Native의 JS 실행 환경을 쓴다고 가정하지 않았습니다. 신뢰된 코드의 실행 문맥·수명·스레드와 네이티브 연결을 T27에서 확정합니다. 게스트 코드와 같은 권한으로 두면 안 됩니다.

문서 교체와 종료를 어떻게 구분하는가

오래된 응답이 새 문서에 붙는 문제, 상대 종료 시 대기 요청 처리, 문자열 전송의 값·오류 규칙을 계약으로 정해야 합니다. 필드 이름이나 오류 코드를 지금 임의로 추가하지 않고 T29–T31에서 근거와 선택 결과를 설명한 뒤 확정합니다.

정책 질문은 이전 동작 → 새 플랫폼에서 생긴 문제 → 선택할 경우의 결과 순서로 설명합니다. 초안이 작성됐다는 사실은 계약 승인을 뜻하지 않습니다. 현재 명세·출처 규칙은 그대로 유지됩니다.

3 · 첫 작업은 T22입니다

T22에서는 두 OS의 후보 지원 범위, 필요한 도구·기기, 호스트 앱 선택에 필요한 조건을 문서로 정리합니다. 이미 미정이라고 답한 호스트 기술을 다시 같은 질문으로 묻지 않고, 구체적인 선택지가 준비됐을 때 결정합니다.

그다음 T23·T24로 각 플랫폼의 실제 제약을 확인합니다. 단순히 문서에 API가 있다는 사실만으로 네이티브 구현 완료를 선언하지 않습니다. 초기 실험의 에뮬레이터·시뮬레이터 결과와 실기기 결과도 구분합니다.

진행 방식
task 하나 → 필요한 실패 테스트·구현·검증 → 쉬운 한국어 코드 설명 → 계획과 HANDOFF 갱신
Android·iOS 양쪽 관문을 모두 통과해야 해당 단계 완료
현재 상태
후속 계획을 작성했습니다. native task는 아직 시작하지 않았으며, SDK 설치·프로토콜 변경·앱 배포도 실행하지 않았습니다. T01–T21의 완료 기록과 1,131개 테스트 기준은 유지합니다.

Pool은 기존 ADR 0002의 네이티브 목표를 계획에 넣은 것입니다. 앱 전체 메모리 관리자나 분석 기능을 추가하는 작업이 아닙니다. 새 기능·숫자 정책은 근거와 승인된 계약을 먼저 갖춥니다.
