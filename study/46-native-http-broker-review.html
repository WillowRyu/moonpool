2 · 미니 앱 입력 막기

가장 심각한 문제는 쿠키 값 안의 ;였습니다. 브로커는 쿠키를 이름=값으로 이어 붙여 보내기 때문에, 값에 ;가 있으면 쿠키가 하나 더 생긴 것처럼 서버에 도착합니다.

// 미니 앱이 보낸 값
cookies.set({ name: 'x', value: '1; prot=guest' })

// 고치기 전: 거절 없이 저장됐습니다. 이대로 나가면 보호된 prot 옆에 가짜 prot이 붙습니다
Cookie: prot=protected-marker; x=1; prot=guest

// 고친 뒤: RFC 6265 문법에 맞지 않으면 -32602로 거절하고 보내지 않습니다
static final Pattern COOKIE_VALUE = Pattern.compile("[\\x21\\x23-\\x2B\\x2D-\\x3A\\x3C-\\x5B\\x5D-\\x7E]*");

위 헤더는 코드로 추론한 모습입니다. 실제 실행에서는 뒤 단계가 같은 이름을 덮어써서 이 값 자체는 나가지 않았고, 이름에 ;를 넣은 a;b=x가 iOS에서 서버까지 그대로 도착한 것을 확인했습니다. Android에서는 줄바꿈이 든 값 때문에 이후 요청이 모두 -32603으로 실패했습니다.

iOS에는 다른 문제가 있었습니다. 타입이 틀린 값을 기본값으로 읽어 버려서, 쿠키를 빼려는 요청이 오히려 쿠키를 보냈습니다.

// 고치기 전: false는 문자열이 아니므로 기본값 "include"가 됩니다
let credentials = params["credentials"] as? String ?? "include"

// 고친 뒤: 값이 있는데 타입이 틀리면 거절합니다
if let given = params["credentials"] {
    guard let text = given as? String, text == "include" || text == "omit" else { return false }
}

헤더도 같습니다. 값 하나만 숫자여도 전체 변환이 실패해서 금지 헤더 검사를 건너뛰었는데, 이제 항목마다 검사합니다.

3 · 두 OS가 달랐던 곳

44가지 사례가 우연히 피해 간 입력들입니다. 모든 사례가 포트를 적었고, POST에는 전부 본문이 있었고, 응답은 금방 왔습니다.

입력고치기 전 Android고치기 전 iOS고친 뒤 (양쪽)
https://host/ (포트 생략)-32000 거절전송443으로 처리
본문 없는 POST-32603전송빈 본문으로 전송
12초 걸리는 응답시간 초과 실패정상정상 (시간 제한 40초)
Set-Cookie: ;네트워크 오류로 바뀜정상무시하고 정상
ASCII가 아닌 서버 쿠키이후 요청 전부 실패그대로 다시 전송저장하지 않음

포트 문제의 원인은 값 하나였습니다.

// Java: 포트가 없으면 -1. 승인 목록에서 "host:-1"을 찾고 있었습니다
uri.getPort()

// 고친 뒤: Swift의 url.port ?? 443과 같은 뜻입니다
uri.getPort() == -1 ? 443 : uri.getPort()

Set-Cookie: ;는 Java의 특성 때문입니다. ";".split(";")는 뒤쪽 빈 문자열을 버려서 빈 배열을 돌려주고, parts[0]에서 예외가 납니다. split(";", -1)로 바꾸면 Swift처럼 빈 문자열이 남습니다.

4 · 닫힌 Portal의 대기 요청

주석에는 소유자를 다시 확인한다고 적혀 있었는데, 실제 코드는 세대 번호만 봤습니다. 그래서 Portal을 닫은 뒤에도 아직 시작하지 않은 요청이 앱 쿠키를 달고 나갔습니다.

// 네트워크에 나가기 직전에 확인합니다
if portal.retired { finish(portal, pending, denied("retired")); return }
if session.generation != generation { finish(portal, pending, denied(-32007, "sessionReset")); return }

이미 나간 요청은 그대로 둡니다. 서버가 처리했을 수 있으므로 쿠키도 커밋합니다. 이번 수정은 아직 시작하지 않은 요청만 막습니다.

6 · 고치지 않은 것과 한계

쉼표 처리는 이미 받아들인 설계입니다. iOS는 Set-Cookie 줄을 하나로 합쳐서 보여 주기 때문에 원래 경계를 알 수 없습니다. 그래서 고치지 않고 영향을 재 봤더니, 계약서에 적힌 "쿠키가 하나 더 생긴다"보다 한 가지가 더 있었습니다.

서버가 보냄   Set-Cookie: sid=abc, x=y; Path=/; Secure; HttpOnly
보관함        sid=abc, x=y
미니 앱이 읽음 sid=abc     ← HttpOnly를 잃어서 읽힙니다 (양쪽 OS 동일)

RFC 6265의 서버 문법은 쿠키 값에 쉼표를 허용하지 않으므로, 규칙을 어기는 서버에서만 생깁니다. 더 엄격한 규칙도 정확할 수 없습니다. iOS에서는 정상적인 두 줄도 똑같은 글자로 보이기 때문입니다.

결정할 것내용권하는 것
Basic 401 뒤 쿠키iOS는 두 번째 응답, Android는 첫 응답의 쿠키가 남음 (변함없음)failureResponse를 iOS에서 한 번 측정
쉼표와 HttpOnly양쪽 동일하지만 보호가 풀림. SPEC §9 관련계약서에 이 영향을 적을지 결정

이번 시험의 한계

  • 허용 메서드 7개와 쿠키 문법은 이 실험에서 정한 값이고, 아직 계약 문구가 아닙니다.
  • 서버는 메서드, 본문 길이, Cookie, Authorization만 기록합니다. User-Agent나 기본 Content-Type처럼 클라이언트가 스스로 붙이는 헤더는 비교하지 못했습니다.
  • C04와 C09–C12, 실제 Portal, 브리지는 여전히 시험하지 않았습니다.
현재 상태: 완료 수는 6 / 44 그대로입니다. 이번 수정은 커밋하지 않았고, SPEC·프로토콜·제품 패키지는 바뀌지 않았습니다. 새 시험용 키도 휴지통에 있어 직접 비워 주셔야 합니다.
