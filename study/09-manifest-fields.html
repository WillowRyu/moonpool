T05 · Read the form, then check its fields

JSON으로 읽혔다고,
앱 설정이 올바른 것은 아닙니다.

미니 앱의 설정 서류인 moonpool.json에서 필요한 항목과 자료형을 검사합니다. 읽기 → 필수 항목 → 형식 확인의 순서로 실제 코드를 살펴봅니다.

1 · 앱을 띄우기 전에 확인할 서류

매니페스트(manifest)는 앱의 id, 이름, 버전, 시작 파일, 요청 권한을 적은 서류입니다. 현재 예제에는 같은 정보를 TypeScript 상수로 직접 적어 두었습니다. 파일로 받은 내용을 검증할 기반을 이번에 만들었습니다.

항목T05에서 확인하는 내용
manifestVersion숫자 1
idSPEC §7의 정확한 앱 id 형식
name문자열, 유니코드 코드 포인트 기준 1–40
version정식 SemVer 2.0.0 형식
entry문자열인지 확인. 경로의 안전성은 T06
protocolVersion문자열인지 확인. 연결 시 버전 협상과 구분
permissions문자열 배열. 빈 배열도 허용. 알려진 권한인지는 T06

구현 위치는 packages/host/src/manifest-fields.ts입니다. 내부 함수 이름은 parseManifestFields이며, 아직 완전한 매니페스트 파서로 외부에 내보내거나 예제에 연결하지 않습니다.

2 · JSON.parse 다음에도 검사가 필요합니다

let parsed: unknown;
try {
  parsed = JSON.parse(source);
} catch {
  throw new ManifestError('json', 'manifest must contain valid JSON');
}
if (!isRecord(parsed)) {
  throw new ManifestError('manifest', 'manifest must be a JSON object');
}

그전에 source가 실제 문자열인지도 검사합니다. JSON 문법이 깨졌으면 첫 오류가 나고, 문법이 맞아도 결과가 배열·null·숫자라면 두 번째 오류가 납니다. 예를 들어 42는 올바른 JSON이지만 앱 설정 객체는 아닙니다.

parsed를 unknown으로 두기 때문에, 내용을 확인하기 전에 속성을 함부로 사용할 수 없습니다. isRecord도 “항목이 아직 unknown인 객체”라는 사실만 확인합니다. 유효한 매니페스트라고 미리 주장하지 않습니다.

JSON의 원래 SyntaxError에는 입력 일부가 포함될 수 있습니다. 대신 고정된 오류 문구를 만들고, 검사하지 않은 원문을 그대로 오류 메시지에 복사하지 않습니다.

3 · 필요한 칸은 이 객체에 직접 있어야 합니다

function required(record: Record<string, unknown>, field: string): unknown {
  if (!Object.hasOwn(record, field)) {
    throw new ManifestError(field, `manifest.${field} is required`);
  }
  return record[field];
}

자바스크립트 객체는 부모인 프로토타입에서도 항목을 찾을 수 있습니다. 하지만 JSON 서류에 id가 빠졌는데 부모 객체에 id가 있다고 합격시키면 안 됩니다. 그래서 직접 가진 항목인지 먼저 확인합니다.

const manifestVersion = required(parsed, 'manifestVersion');
if (manifestVersion !== 1) {
  throw new ManifestError('manifestVersion', 'manifest.manifestVersion must be 1');
}

문자열 '1'을 숫자로 바꾸지 않고 거절합니다. 실제로 숫자 1이어야 합니다. 모든 필수 항목이 같은 required 확인을 거칩니다.

4 · 승인한 이름 길이 기준을 코드로 지킵니다

SPEC의 “1–40 chars”는 이모지를 어떻게 셀지 모호했습니다. 2026.10.23에 코드 포인트 기준을 승인받아 SPEC §7을 먼저 명확히 하고 ADR 0010에 기록했습니다.

이름코드 포인트 수결과
😀1허용. JavaScript length는 2여도 코드 포인트는 1
😀 40개40허용
😀 41개41거절
e + 결합 악센트2눈에 한 글자처럼 보여도 구성 단위 두 개로 계산
let nameLength = 0;
for (const _character of name) {
  nameLength += 1;
  if (nameLength > 40) {
    break;
  }
}
if (nameLength < 1 || nameLength > 40) {
  throw new ManifestError('name', 'manifest.name must contain 1–40 Unicode code points');
}

문자열의 for...of는 코드 포인트 단위로 순회합니다. 41개째를 만나면 이미 너무 길다는 사실을 알았으므로 바로 멈춥니다. 긴 문자열을 모두 문자 배열로 복사할 필요가 없습니다.

이는 사람이 눈으로 구분하는 모든 글자 묶음을 세는 방식과는 다릅니다. 여러 문자로 만든 이모지나 결합 문자의 구성 요소는 각각 셉니다. 입력 이름을 잘라 내거나 공백을 없애서 합격시키지도 않습니다.

5 · ID와 버전은 정해진 형식 전체가 맞아야 합니다

const id = required(parsed, 'id');
if (typeof id !== 'string' || !matchesEntirely(MINI_APP_ID, id)) {
  throw new ManifestError('id', 'manifest.id must match the reverse-DNS id pattern');
}

앱 id는 SPEC에 적힌 패턴을 그대로 적용합니다. 대문자, 빈 구간, 슬래시, 앞뒤 공백을 임의로 고쳐 주지 않습니다. 패턴이 허용한 하이픈 위치에 추가 DNS 규칙을 덧붙이지도 않습니다.

앱 버전은 SemVer 2.0.0의 공식 JavaScript 정규식으로 문법을 확인합니다. 1.2.3, 1.2.3-alpha.1, 1.2.3+001은 허용하고 v1.2.3과 1.2.3-01은 거절합니다. 버전 순서를 비교하는 기능은 만들지 않습니다.

function matchesEntirely(pattern: RegExp, value: string): boolean {
  // JavaScript's $ can match before a final newline. Require the whole string.
  return pattern.exec(value)?.[0] === value;
}

정규식의 $는 마지막 줄바꿈 앞에서도 맞을 수 있습니다. 따라서 실제로 맞은 내용 전체와 입력을 다시 비교해, 뒤에 줄바꿈이 붙은 ID나 버전을 승인하지 않도록 했습니다.

6 · 권한 목록은 문자열 배열인지 확인합니다

const permissions = required(parsed, 'permissions');
if (
  !Array.isArray(permissions) ||
  !permissions.every((scope: unknown) => typeof scope === 'string')
) {
  throw new ManifestError('permissions', 'manifest.permissions must be an array of strings');
}

먼저 배열인지 확인하고, every로 각 항목이 문자열인지 묻습니다. 숫자·객체·배열을 문자열로 바꾸지 않습니다. 빈 배열에는 잘못된 항목이 없으므로 every는 true이고, 권한을 요청하지 않는 앱도 허용됩니다.

여기서는 문자열 목록의 형태까지 확인합니다. profile과 storage처럼 실제로 아는 권한인지 확인하는 일은 다음 T06의 책임입니다. protocolVersion도 현재는 문자열 여부를 확인하며, 연결할 때의 버전 협상과 섞지 않습니다.

이번 함수는 내부 ManifestFields를 돌려주며, 패키지의 공개 진입점에 내보내지 않습니다. entry가 문자열이라고 해서 안전한 상대 경로라는 뜻은 아니기 때문입니다. T06의 검사를 결합해 완전한 파서를 만든 뒤 T07에서 예제에 연결합니다.

ManifestError는 로컬 설정 오류입니다. field에는 어느 칸이 문제인지 담습니다. 연결된 요청의 응답이 아니므로 JSON-RPC 오류 번호나 MoonpoolError를 새로 만들지 않습니다.

이 함수는 파일 읽기나 브리지 생성을 하지 않는 순수 함수입니다. 현재 함수 자체는 동기적으로 검사하지만, 모든 capability가 비동기여야 한다는 약속은 그대로입니다. 파일을 읽는 작업과 브리지 호출은 이 내부 검사 함수와 구분합니다.

8 · 테스트는 서류의 각 규칙을 확인합니다

구현 전에 새 테스트 89개를 작성해 실패를 확인했습니다. 정상 서류, 잘못된 JSON, 객체가 아닌 값, 필수 항목 누락, 잘못된 자료형, 앱 id, Unicode 이름 경계, SemVer 문법을 검증합니다.

부모 객체의 id가 누락된 필수 항목을 대신하지 못하는지, 잘못된 원문이 오류 메시지에 섞이지 않는지도 확인합니다. 매우 큰 버전 숫자를 자바스크립트 숫자로 바꾸지 않고 문법만 검사하는 사례도 포함합니다.
