왜 커널과 운반을 나눌까?

커널은 공통 규칙을 처리하는 핵심 부분입니다. protocol·client·host에는 브라우저의 window 같은 플랫폼 기능을 넣지 않습니다. 운반만 바꾸어도 같은 규칙을 사용할 수 있도록 하기 위해서예요.

브라우저 연결의 경계

transport-iframe만 브라우저 창과 postMessage를 다룹니다. 받은 메시지의 origin과 실제 보낸 창을 확인합니다. origin은 주소의 출처로, 개발 중에도 호스트 5173과 미니 앱 5174를 구분합니다.

현재 범위는 브라우저에서 프로토콜을 검증하는 v0.1입니다. 네이티브 iOS/Android 코어는 현재 구현하지 않습니다. 운영 환경의 origin 규칙은 SPEC §8의 moonpool://<mini-app-id>/이며, 고정 localhost 주소는 §8.1의 개발 환경 예외입니다.

02 · A request's journey

storage.set 요청 한 번의 여행

JSON-RPC(JSON Remote Procedure Call)는 함수 요청과 응답을 JSON 형식으로 주고받는 약속입니다. id는 요청 번호여서 응답이 돌아오면 어느 기다림을 끝낼지 알 수 있어요.

{ "jsonrpc": "2.0", "id": 2, "method": "storage.set",
  "params": { "key": "settings", "value": { "theme": "dark" } } }

⑤의 실제 호출 경로
host: STORAGE_METHODS.SET → isStorageSetParams(params) → isJsonValue(params.value)
마지막 함수는 true / false만 반환합니다. 실패 응답 -32602를 보내는 책임은 host에 있습니다.

성공하면

호스트 설정에서 가져온 미니 앱 id와 key를 provider에 넘깁니다. 저장이 끝날 때까지 기다린 뒤 { "id": 2, "result": {} }로 응답합니다. client가 요청 2의 기다림을 완료합니다.

입력이 잘못되면

provider를 호출하기 전에 -32602를 보냅니다. 기존 데이터와 입력 원본은 그대로 남습니다. 저장 기능이 제공되지 않더라도, 권한이 있는 요청의 입력 오류를 먼저 판단합니다.

저장 분기의 세부 순서: scope → 허용한 params 이름 → key·value 검사 → provider 제공 여부 → 실행. scope가 없으면 값 검사보다 먼저 -32000입니다. 포털 초기화는 일반 capability 요청과 다른 분기입니다.

T10 완료 · 지난 번호를 다시 실행하지 않기

이전에는 같은 번호도 다시 실행됐습니다. 중복 실행과 원래 응답의 혼동을 막기 위해, 호스트가 문서마다 사용한 가장 큰 번호를 기억하고 그 이하의 요청을 거절합니다.

let lastRequestId = 0;

// Reject id <= lastRequestId with -32600 and id:null.
// Consume a new id before checking the rest of the request.
lastRequestId = id;

1 → 3 → 5처럼 건너뛰는 것은 허용합니다. 5 다음의 5나 3은 실행하지 않습니다. 오류 응답에 null을 사용하므로 아직 기다리는 원래 요청은 자기 응답을 계속 기다립니다. 정상 요청 모양의 초기화는 새 번호 구간을 열고, 권한과 저장 데이터는 보존합니다.

profile.get은 소문자로 시작한 두 부분과 점 하나로 이루어져 있습니다. 받은 method가 문자열이라는 사실에 더해, 입력 전체가 승인한 문법을 지키는지 확인합니다.

const METHOD_NAME = /^[a-z][A-Za-z0-9]*\.[a-z][A-Za-z0-9]*$/;

typeof value.method === 'string' &&
METHOD_NAME.exec(value.method)?.[0] === value.method

첫 글자는 영문 소문자이고 이후에는 영문 대·소문자와 숫자를 허용합니다. exec로 찾은 글자가 입력 전체와 같은지 비교해 마지막 줄바꿈도 거절합니다. 이름을 잘라 내거나 소문자로 바꾸어 통과시키지 않습니다.

T08 복습 · 배열 전체를 거절하고 기다림 보존하기

Moonpool 0.x는 요청을 배열로 묶은 batch를 지원하지 않습니다. 이제 최상위 배열을 가장 먼저 확인해 오류 하나를 보내고, 초기화나 capability 처리로 넘어가지 않습니다.

const response: JsonRpcResponse = {

  id: null,
  error: {
    code: ERROR_CODES.INVALID_REQUEST,

const profileResult = await client.call(PROFILE_METHODS.GET);
if (
  typeof profileResult !== 'object' ||
  profileResult === null ||
  Array.isArray(profileResult) ||
  !('displayName' in profileResult) ||

T01 복습 · 코드의 설명을 실제 동작에 맞추기

주석은 실행되지 않는 코드 설명입니다. 기계는 코드를 따르지만 다음 개발자는 주석도 읽습니다. 창고에서 실제로는 상자 안까지 검사하는데 안내판에는 “겉만 확인합니다”라고 적혀 있으면 혼란스럽겠죠. 이번에는 그 안내판을 바로잡았습니다.

바뀌기 전 설명

저장 값의 중첩 데이터는 검사하지 않고 Transport의 타입 약속에 의존한다고 적혀 있었습니다. 클라이언트에도 구현 전 뼈대라는 설명이 남아 있었습니다.

바로잡은 설명

key는 문자열인지 확인하고, value는 누락·바깥쪽 null을 거절한 뒤 안쪽까지 JSON 값인지 검사합니다. 클라이언트는 요청 번호로 응답을 연결하고, 시간 초과와 연결 종료 때 대기 중인 요청을 정리한다고 설명합니다.

실제 검사 흐름은 이렇게 읽으면 됩니다

아래는 이미 동작하던 isStorageSetParams의 조건입니다. &&는 앞 조건이 통과해야 다음 조건으로 간다는 뜻입니다. 검사대를 하나씩 통과한다고 생각하면 됩니다.

isJsonObject(params)              // params가 객체인가?
&& typeof params.key === 'string' // key가 문자열인가?
&& params.value !== undefined     // 저장할 값이 있는가?
&& params.value !== null          // 바깥쪽 null을 거절하는가?
&& isJsonValue(params.value)      // 값의 안쪽도 JSON 규칙을 지키는가?

false, 0, ""는 값이 있으므로 허용합니다. { note: null }도 안쪽의 null이라 허용하지만, { count: NaN }은 JSON으로 표현할 수 없는 숫자가 있어서 거절합니다. 명세의 보안 규칙 §9.6 입력 검증을 설명하는 주석이며, 검사 로직 자체는 유지했습니다.

T01 검증: 기존 테스트 201개, 타입 검사, 린트, 두 브라우저 예제 빌드가 모두 통과했습니다. 이번 작업은 주석과 학습 자료 정비여서 새 동작을 위한 테스트를 추가하지 않았습니다.

전체 완료로 오해하면 안 되는 경계

브라우저 transport는 아직 event.data를 JsonValue로 단언합니다. 이번 검사는 storage.set의 value 부분을 실제로 확인한 것이며, 메시지 전체의 안전성을 모두 증명하지 않습니다.

Proxy는 객체 구조 조사에 함수를 연결할 수 있는 자바스크립트 기능입니다. 구조 조사 도중 실패하면 거절하지만, 임의 Proxy가 만드는 부수 효과를 모두 막는 함수는 아닙니다. 공유 그래프 검사가 빨라도 JSON 문자열로 펼쳤을 때의 크기는 클 수 있습니다.

T01 시점에는 매니페스트를 예제의 타입이 붙은 상수로 제공했고 파서는 없었습니다. 이후 T06에서 파서를 완성하고 T07에서 실제 파일 연결을 마쳤습니다. 모든 SPEC §4.4 오류에 대한 검증과 나머지 프로필 경계도 완료 판정 전에 남아 있습니다.
