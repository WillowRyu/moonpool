왜 커널과 운반을 나눌까?

커널은 공통 규칙을 처리하는 핵심 부분입니다. protocol·client·host에는 브라우저의 window 같은 플랫폼 기능을 넣지 않습니다. 운반만 바꾸어도 같은 규칙을 사용할 수 있도록 하기 위해서예요.

브라우저 연결의 경계

transport-iframe만 브라우저 창과 postMessage를 다룹니다. 받은 메시지의 origin과 실제 보낸 창을 확인합니다. origin은 주소의 출처로, 개발 중에도 호스트 5173과 미니 앱 5174를 구분합니다.

현재 범위는 브라우저에서 프로토콜을 검증하는 v0.1입니다. 네이티브 iOS/Android 코어는 현재 구현하지 않습니다. 운영 환경의 origin 규칙은 SPEC §8의 moonpool://<mini-app-id>/이며, 고정 localhost 주소는 §8.1의 개발 환경 예외입니다.

02 · A request's journey

storage.set 요청 한 번의 여행

JSON-RPC(JSON Remote Procedure Call)는 함수 요청과 응답을 JSON 형식으로 주고받는 약속입니다. id는 요청 번호여서 응답이 돌아오면 어느 기다림을 끝낼지 알 수 있어요.

성공하면

호스트 설정에서 가져온 미니 앱 id와 key를 provider에 넘깁니다. 저장이 끝날 때까지 기다린 뒤 { "id": 2, "result": {} }로 응답합니다. client가 요청 2의 기다림을 완료합니다.

입력이 잘못되면

provider를 호출하기 전에 -32602를 보냅니다. 기존 데이터와 입력 원본은 그대로 남습니다. 저장 기능이 제공되지 않더라도, 권한이 있는 요청의 입력 오류를 먼저 판단합니다.

저장 분기의 세부 순서: scope → params 전체 JSON → 허용한 params 이름 → key·value 검사 → provider 제공 여부 → 실행. scope가 없으면 값 검사보다 먼저 -32000입니다. 포털 초기화는 일반 capability 요청과 다른 분기입니다.

Wrapper B: frame-src http://127.0.0.1:5375

창의 출처뿐 아니라 실제 발신 창과 보호 문서의 Document 신원을 확인합니다. 바깥 문서의 객체를 직접 넘기면 현재 JSON 검사에서 거절되는 실행 문맥 문제도 발견했습니다. 수정안에서는 커널·연결을 각 보호 문서에 두고, 앱별 저장소는 바깥 호스트가 유지합니다. 실행 문맥 사이에서는 검사한 데이터만 전달하도록 제안했습니다.

이 설명의 출발점은 T01 당시의 저장 값 검사입니다. transport의 타입 단언은 실행 중 검사가 아닙니다. 이후 T11에서 호스트 메시지 전체의 단계별 JSON 검사, T12에서 client 응답 검사를 구현했습니다. 현재의 완료 근거는 위 T21 기록과 연결해 읽습니다.

T01 시점에는 매니페스트를 예제의 타입이 붙은 상수로 제공했고 파서는 없었습니다. 이후 T06에서 파서를 완성하고 T07에서 실제 파일 연결을 마쳤습니다. 이후 T19에서 모든 SPEC §4.4 코드 검증을 연결했고 T20·T21의 관찰·완료 기록까지 마쳤습니다.
