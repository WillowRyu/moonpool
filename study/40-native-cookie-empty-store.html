T28 · Empty store under the accepted rule

잠금장치는 도둑만 막으면
되는 게 아닙니다.

채택한 규칙이 쿠키가 있는 저장소는 막고, 쿠키가 없는 저장소는 열어 주는지 시험했습니다. 집주인까지 못 들어가는 잠금장치는 쓸 수 없기 때문입니다.

저장소 168개 · 전부 정확서버 기록 472행 · 검사 990개시뮬레이터 iOS 26.4.1만 측정

1 · 왜 이 시험이 필요했나

앞선 시험은 쿠키가 있는 저장소만 다뤘습니다. 그래서 규칙이 쿠키를 놓치지 않는다는 것만 봤고, 정상 저장소를 막아 버리는지는 몰랐습니다. 예를 들어 fetchDataRecords가 localStorage까지 쿠키처럼 세면, 설정만 저장한 평범한 미니 앱이 열리지 않게 됩니다.

// 채택한 규칙 그대로, 새 프로세스에서 실행
await policy(store, false)         // 1. 쿠키 차단 설정 완료까지 대기
let records = await records(store) // 2. 첫 번째 답
let names = await names(store)     //    두 번째 답

// 둘 다 없음 → 열기 / 둘 다 있음 → 막기 / 서로 다름 → 막기

판정이 맞았는지는 규칙에 묻지 않고, 그 뒤 페이지를 불러 서버가 실제로 쿠키를 받았는지로 확인했습니다.

2 · 168개 저장소 모두 정확했습니다

시험 시점의 저장소 상태수서버가 받은 쿠키규칙의 판단
쿠키 없음: 새 저장소, 쓴 적 없는 저장소, localStorage·IndexedDB만 있는 저장소, 쿠키 없는 페이지만 방문한 저장소56없음열기 ✓
쿠키가 사라짐: 차단으로 저장 실패, 서버가 삭제, 만료, 세션 쿠키32없음열기 ✓
쿠키가 저장되지 않았거나 남지 않음 (4번 항목 참고)16없음열기 ✓
일반 쿠키: 차단 전력 있음·없음, HttpOnly, 종료 직전 쓰고 차단40있음막기 ✓
파티션 쿠키만 있음: 일반 페이지 안, moonpool:// 페이지 안24있음막기 ✓
  • 로컬 데이터는 쿠키로 세지 않습니다. 시험 뒤에도 localStorage·IndexedDB 값이 그대로 남아 있었습니다.
  • 파티션 쿠키만 있어도 두 API 모두 찾아냅니다. 이전 시험에서는 일반 쿠키가 함께 있어서 확인할 수 없던 내용입니다.
  • 원래 문제도 여전히 재현됩니다. 같은 저장소에서 정책 전 목록은 비었고, 정책 후에는 쿠키가 나왔습니다(8개 모두). 그래서 이 실험이 그 문제를 볼 수 있는 실험이었다고 말할 수 있습니다.

3 · 첫 수집은 검증기가 거부했습니다

첫 수집에서도 "규칙이 다 맞았다"는 숫자가 나왔습니다. 그런데 파티션 쿠키가 있어야 할 저장소 24개에서 서버가 쿠키를 받지 못해 검증기가 거부했습니다.

확인해 보니 그 저장소들에는 쿠키가 애초에 저장되지 않았습니다. 비어 있는 저장소를 "비었다"고 맞힌 것이니, 파티션 쿠키는 전혀 시험하지 못한 셈이었습니다. 대조군이 없었다면 이 결과를 "파티션 쿠키도 통과"로 잘못 보고할 뻔했습니다. 준비 단계를 고쳐 다시 수집했고, 판정 기준은 그대로 두었습니다.

규칙의 판단에는 영향이 없고, 원인은 아직 모릅니다.

관찰비교

5 · 아직 모르는 것

  • 두 번째 확인이 실제로 무언가를 잡아낼지: 168개에서 두 API의 답이 한 번도 다르지 않았습니다. 안전장치는 돌아갔지만 쓰일 일은 없었습니다.
  • Android (이후 확인함): 앱을 새로 켠 직후에도 hasCookies가 정확했습니다. 41 · Android 재시작 쿠키 시험을 보세요.
  • 프로세스의 맨 첫 질문: 이 시험에서 프로세스의 첫 저장소는 쿠키가 없었습니다. 쿠키 있는 저장소를 맨 먼저 묻는 경우는 이후 시험에서 36개 모두 맞았습니다.
  • 실제 iPhone, 다른 iOS 버전, 기기 재부팅, 서비스 워커, 리다이렉트, 실제 Portal 종료도 남아 있습니다.
