Moonpool은 로그인 쿠키를 네이티브 코드가 직접 관리하려고 합니다. 그 코드를 만들기 전에, 두 OS의 기본 HTTP 클라이언트가 그 설계를 받쳐 주는지 시험했습니다.

관측 136개 · 서버 기록 164행계약과 충돌 3건설계 방향 채택 · 구현 전

1 · 왜 먼저 시험했나

계약 문서에는 "쿠키는 네이티브가 관리한다", "리다이렉트는 따라가지 않는다", "요청을 자동으로 다시 보내지 않는다" 같은 약속이 적혀 있습니다. 그런데 이 약속은 OS의 HTTP 클라이언트가 그렇게 동작하게 설정할 수 있다는 전제 위에 있습니다.

쿠키 저장소까지 만든 뒤에 전제가 틀렸다고 밝혀지면 고칠 게 많아집니다. 그래서 같은 시험 목록을 Android HttpURLConnection과 iOS URLSession에서 돌리고, 우리 서버가 실제로 받은 기록과 비교했습니다.

인증서는 기기에 등록하지 않고 프로브 앱 안에서만 신뢰했습니다. 그리고 프로브 인증서를 믿지 않는 연결은 실제로 거부되는지도 확인해서, TLS 검증을 끄고 얻은 결과가 아님을 보였습니다.

3 · iOS는 쿠키 줄을 하나로 합칩니다

서버가 Set-Cookie를 두 줄로 보내도 iOS는 쉼표로 이어 한 줄로 줍니다. 대개는 다시 나눌 수 있지만, 값에 쉼표와 이름=이 들어 있으면 구분할 수 없습니다.

서버가 보낸 것 (쿠키 2개)
  t28h_comma=a, t28h_fake=b; Path=/
  t28h_real=c; Path=/

iOS가 준 것 (한 줄)
  t28h_comma=a, t28h_fake=b; Path=/, t28h_real=c; Path=/

각 OS의 쿠키 해석기 결과
  Android: t28h_comma, t28h_real          → 2개
  iOS:     t28h_comma, t28h_fake, t28h_real → 3개

같은 응답인데 OS마다 쿠키 개수가 다릅니다. 두 OS에서 같은 동작을 약속했으므로, OS의 해석기를 그대로 쓸 수 없습니다.

4 · 401을 받으면 POST가 한 번 더 전송됩니다

서버가 Basic 인증을 요구하는 401을 보내면, iOS는 요청을 본문까지 그대로 한 번 더 보냅니다. 인증 정보는 실리지 않고, 앱은 401을 한 번만 받습니다. 401은 보통 서버가 처리를 거절했다는 뜻이라 실제 피해는 드뭅니다. 다만 거절 전에 작업을 하거나 실패 횟수를 세는 서버라면 영향이 있을 수 있습니다.

iOS에서 한 처리받은 결과서버에 도착한 횟수
거절 / 기본 처리 / 인증 정보 없이 진행4012번
취소 (GET만 시험)오류, 응답을 받지 못함1번
Bearer 401 또는 인증 요구 없는 4014011번

요즘 API는 대부분 Bearer를 쓰므로 영향 범위는 좁습니다. Digest나 NTLM 등 다른 방식은 아직 시험하지 않았습니다.

5 · iOS는 본문 첫 바이트가 와야 헤더를 줍니다

Android는 헤더가 오면 바로 보여 줍니다. iOS는 본문이 1바이트라도 올 때까지 아무것도 알려 주지 않았습니다. 그래서 "헤더는 왔는데 본문은 아직" 상태를 시험하려면 iOS에서는 1바이트를 먼저 보내야 합니다.

6 · 결정: 앱에 보이는 차이만 고칩니다

처음에는 재전송을 막으려고 인증 요구를 취소하고 오류를 돌려주자고 제안했습니다. 하지만 측정 결과를 다시 보니 앱이 받는 401과 본문은 두 OS가 같았습니다. 서버 도착 횟수 하나를 맞추려고 멀쩡한 응답을 버리는 셈이어서, 제안을 철회했습니다. 그래서 기준을 이렇게 정했습니다.

기준: OS 기본 동작을 따릅니다. 단, 미니 앱이 보는 결과가 OS마다 달라지면 고칩니다.
문제앱이 보는 결과가 달라지나결정
쿠키 줄이 합쳐짐달라짐 (쿠키 개수가 다름)두 OS가 같은 방식으로 합치고 나눠 공용 해석기로 읽음
Basic 401 뒤 재전송같음 (401과 본문)OS를 따르고 재전송을 문서화, SDK는 재시도하지 않음
헤더가 늦게 보임await 뒤에는 같음OS를 따르고 저장 시점을 "헤더를 넘겨받은 때"로 정의
// 동작은 OS를 따르되, 호스트의 인증 정보는 쓰지 않습니다
urlCredentialStorage = nil  // 저장된 비밀번호를 자동으로 쓰지 않음
httpCookieStorage    = nil  // 쿠키는 SDK가 직접 관리

쿠키 처리의 비용: 값에 , 이름=이 든 쿠키는 두 OS에서 똑같이 쿠키 하나가 더 생깁니다. 표준 문법에서 쿠키 값에 쉼표는 허용되지 않으므로 표준을 벗어난 서버에서만 생깁니다.

다른 프로젝트는 어떻게 하나

Ionic Portals가 쓰는 Capacitor는 같은 URLSession을 쓰고, Tauri는 Rust reqwest, Electron은 Chromium을 씁니다. 소스를 읽어 확인한 내용이고 실행해 보지는 않았습니다. Tauri처럼 공용 Rust HTTP 계층을 두면 이 문제들을 피할 수 있지만, 네이티브 코어를 v0 뒤로 미룬 방침과 충돌해서 나중에 검토할 대안으로 기록했습니다.

만들기 전에 확인할 것

  • 호스트 앱이 Android의 Authenticator, CookieHandler를 앱 전체에 설정한 경우
  • 쿠키를 함께 보내는 Basic 401, 미리 넣은 Authorization이 재전송될 때의 동작
  • 다른 인증 방식, HTTP/2, 본문 도중 실패, 요청 취소
현재 상태: 설계 방향으로 채택했고 쿠키 저장소는 아직 없습니다. 완료 수는 6 / 44 그대로입니다. SPEC, 프로토콜, 제품 패키지는 바꾸지 않았습니다. 자세한 수치는 검증 보고서와 실험 안내에 있습니다.
