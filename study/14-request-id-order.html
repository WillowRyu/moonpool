T10 · Increasing ids within each document

이미 지난 번호는 거절하고,
원래 요청의 기다림은 지킵니다.

호스트가 현재 문서에서 사용한 가장 큰 번호를 기억합니다. 중복·역순 요청을 실행하지 않고, 새 초기화에서는 번호 기준을 다시 시작합니다.

T10 완료645 / 645 테스트 통과다음 T11 · 메시지 전체 JSON 검사

1 · 이전 동작에서 무엇이 달라졌나

단계설명
이전 동작양의 정수 번호인지는 검사했지만, 같은 번호를 다시 보내도 요청이 실행됐습니다.
지금 해결할 문제저장이 중복 실행될 수 있습니다. 중복 번호를 붙인 오류가 아직 기다리는 원래 호출의 응답으로 해석될 수도 있습니다.
승인한 결과사용한 가장 큰 번호 이하의 요청은 -32600 / id:null로 거절합니다. 원래 호출은 자기 응답을 계속 기다립니다.

2026.10.23에 이 정책을 승인받아 SPEC §4.1·§4.2·§5.1에 먼저 기록했습니다. ADR 0015에는 검사 순서, 초기화 예외와 남은 한계를 정리했습니다. 이후 정책 질문도 이전 동작 → 현재 문제 → 선택 결과 순서로 설명하기로 했습니다.

이번 코드에서 만나는 표현

표현뜻비유
lastRequestId현재 문서에서 사용한 가장 큰 요청 번호접수대가 기억한 마지막 번호
단조 증가다음 번호가 이전 번호보다 커야 하는 규칙1 → 3 → 5도 괜찮지만 5 → 3은 거절
번호 소비요청을 받았으므로 다시 쓸 수 없다고 기록서류 내용에 오류가 있어도 사용한 접수번호는 남김
문서 경계일반 요청 형식이 맞는 portal.initialize로 새 번호 구간 시작새 문서의 접수 장부 열기
id:null 오류특정 대기 요청에 연결하지 않을 오류원래 번호표의 손님을 호출하지 않는 거절 안내

2 · 가장 큰 번호 하나로 판단합니다

let initialized = false;
let lastRequestId = 0;

변수는 connect 안에 있으므로 같은 호스트에 연결된 두 Portal도 각자의 번호를 기억합니다. 5까지 사용했다면 5 이하의 번호를 모두 거절할 수 있어, 과거 번호 목록 전체를 보관할 필요가 없습니다.

들어온 요청처리기억한 번호
initialize 1새 기준에서 초기화1
ping 5허용. 중간 번호를 건너뛰어도 됨5
저장 요청 5중복이므로 실행하지 않음5
저장 요청 3사용하지 않았던 번호여도 역순이므로 거절5
잘못된 이름의 요청 6번호는 소비하고 이름 오류로 거절6
이름을 고쳐 다시 보낸 요청 6중복이므로 거절. 새 번호가 필요6
ping 7허용7

새 번호는 이름·인자·권한 등의 검사보다 먼저 기록합니다. 따라서 오류로 끝난 요청도 번호를 사용한 것입니다. 양의 정수가 아닌 번호와 알림, 배열 요청은 이 번호 기준을 올리지 않습니다.

3 · 중복 번호를 오류의 id로 돌려주지 않습니다

if (Number.isInteger(id) && id > 0) {
  if (id <= lastRequestId) {
    const response: JsonRpcResponse = {
      jsonrpc: '2.0',
      id: null,
      error: {
        code: ERROR_CODES.INVALID_REQUEST,
        message: 'request ids must increase within a document',
      },
    };
    transport.send(response);
    return;
  }
  lastRequestId = id;
}

<=는 “작거나 같다”입니다. 이 조건에 걸리면 오류를 보내고 return으로 끝내므로 provider는 호출되지 않습니다. 통과한 번호만 마지막 줄에서 기록합니다. 이 코드는 packages/host/src/index.ts에 있습니다.

예를 들어 프로필 요청 2가 아직 실행 중인데 또 2가 들어왔다고 해 봅시다. 오류에도 id:2를 붙이면 클라이언트가 원래 프로필 호출을 실패로 끝낼 수 있습니다. id:null로 보내면 T08의 클라이언트 처리가 그 오류를 대기 중인 호출과 연결하지 않습니다.

원래 요청 2
provider 결과 대기
→
중복 요청 2
실행 없이 null 오류
→
원래 응답 2
정상 완료

중복 요청의 이름이나 인자까지 틀렸어도 번호 검사를 먼저 합니다. 그래야 다른 오류 분기에서 같은 번호를 돌려주어 원래 호출을 끝내는 일이 없습니다. 새 번호가 통과한 뒤에는 기존 T09 이름 검사와 다른 오류 순서를 따릅니다.

4 · 정식 초기화는 새 문서의 번호 구간을 엽니다

if (message.method === PORTAL_METHODS.INITIALIZE && isJsonRpcRequest(message)) {
  lastRequestId = 0;
}

이 코드는 번호 비교보다 앞에 있습니다. 일반 요청 모양이 맞는 정확한 portal.initialize이면 기준을 0으로 돌린 뒤 그 초기화의 번호를 소비합니다. 이전 문서에서 20까지 썼어도 새 문서가 initialize 1 → ping 2로 시작할 수 있습니다.

일반 요청 모양은 버전 협상의 성공과 다릅니다. params가 객체이거나 생략된 정상 요청 모양이라면 새 문서 경계이고, 그다음 protocolVersion 검사가 실패할 수도 있습니다. 이때 초기화 상태는 실패 상태이며 새 번호 기준은 유지합니다. 기존 클라이언트가 initialize 3으로 재시도하는 경우도 허용합니다.

이름을 잘못 적거나 params 자체가 배열인 초기화는 새 문서 경계가 아닙니다. 기존 상태를 유지하면서, 새 번호라면 그 번호를 소비한 뒤 형식 오류를 보내고, 이전 번호라면 null 오류로 거절합니다.

SPEC §9의 권한 경계와 §5.1의 보존 규칙을 지킵니다. 요청 번호는 권한 증명이 아닙니다. 초기화로 번호 기준이 바뀌어도 grantedScopes와 저장 내용은 유지하며, 실제 호출에서는 계속 호스트의 권한 검사를 거칩니다.

문서별 검사의 범위: 초기화는 의도적으로 새 번호 구간을 시작하므로 영구적인 재실행 방지 기능은 아닙니다. 문서가 바뀐 뒤 예전 provider 응답이 늦게 도착하는 문제는 SPEC §11에 남아 있습니다. 이번 번호 초기화가 예전 provider 작업을 취소하는 것은 아닙니다.

5 · 결과와 저장 내용, 대기 중인 호출을 확인했습니다

구현 전 새 테스트 25개 중 17개가 실패했고 8개는 기존 동작을 확인했습니다. 구현 후 모두 통과했습니다. 같은 호스트의 서로 다른 연결, 증가하는 번호의 건너뛰기, 중복·역순 저장, 실패 요청의 번호 소비, 초기화 경계와 버전 실패 후 재시도를 확인합니다.

실제 host와 client를 메모리 전송으로 연결한 테스트는 원래 프로필 호출을 기다리게 한 뒤 중복 요청과 잘못된 이름의 중복 요청을 보냅니다. provider는 한 번만 호출되고 원래 호출과 타이머가 유지됩니다. 원래 provider를 완료하면 호출이 성공하고 타이머가 정리됩니다.
