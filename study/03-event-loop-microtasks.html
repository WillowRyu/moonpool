1. 한 줄 모델: 스레드 하나, 큐 두 개

JavaScript는 한 번에 한 가지만 실행합니다. 스레드가 하나뿐이에요. 그래서 "나중에 할 일"은 전부 큐(queue, 대기줄)에 쌓아두고, 지금 하던 일이 끝나면 하나씩 꺼내서 처리합니다. 이 꺼내서-처리하는 무한 반복이 이벤트 루프(event loop)입니다.

핵심은 큐가 하나가 아니라 둘이라는 것. 그리고 둘은 동등하지 않습니다. 마이크로태스크 큐가 절대적으로 우선합니다.
매크로태스크 큐 (task queue) 마이크로태스크 큐 (microtask queue)
들어가는 것 setTimeout, setInterval, DOM 이벤트 콜백, 네트워크 응답, postMessage 배달 queueMicrotask, Promise.then/catch/finally, await 뒷부분, MutationObserver
한 턴에 몇 개? 딱 하나 큐가 빌 때까지 전부 — 처리 중에 새로 추가된 것까지
렌더링 전/후 렌더링 사이사이에 하나씩 렌더링 전에 반드시 다 비움
비유 손님을 한 명 받는다 그 손님 일 처리하다 생긴 뒤처리를 다음 손님 부르기 전에 전부 끝낸다

용어 주의: 명세(WHATWG HTML)에는 "매크로태스크"라는 말이 없습니다. 그냥 task예요. "매크로"는 마이크로태스크와 대비시키려고 커뮤니티가 붙인 이름입니다. 뜻은 통하니 그대로 쓰겠습니다.

2. 진짜 규칙 — "하나 꺼내고, 전부 비운다"

이벤트 루프 한 바퀴(한 턴)는 이렇게 생겼습니다:

이벤트 루프 한 턴

1단계 — 매크로태스크 하나 큐 맨 앞의 task를 딱 하나 꺼내서 끝까지 실행
↓
2단계 — 마이크로태스크 체크포인트 큐가 완전히 빌 때까지 계속 꺼내 실행. 실행 중에 새 마이크로태스크가 추가되면 그것도 이번 턴에 처리
↓
3단계 — 렌더링 (기회가 되면) 스타일 계산 · 레이아웃 · 페인트. 대략 화면 주사율에 맞춰서
↺ 처음으로
2단계의 "새로 추가된 것도 이번 턴에"가 전부입니다. 마이크로태스크 안에서 queueMicrotask를 또 부르면, 그건 다음 setTimeout보다 먼저 실행됩니다. "한 턴에 하나씩"이 아니라 "빌 때까지"거든요.

4. 누가 어느 큐에 들어가나

같은 마이크로태스크 큐를 쓰는 것들

queueMicrotask(fn) 과 Promise.resolve().then(fn) 은 똑같은 큐에 들어갑니다. 우선순위 차이가 없고, 그냥 부른 순서대로(FIFO)입니다. 

queueMicrotask(() => console.log('1'));
Promise.resolve().then(() => console.log('2'));
queueMicrotask(() => console.log('3'));
// → 1, 2, 3   (예약한 순서 그대로)

그럼 왜 둘 다 존재할까요? Promise.then 은 값을 나르는 도구입니다 — 체이닝되고, 반환값이 다음으로 흘러가고, 던지면 catch로 잡히죠. queueMicrotask 는 값도 체인도 없이 그냥 나중에 실행만 하는 최소 도구입니다.

우리 코드에 이게 왜 중요한가: 우리는 에러를 붙잡히면 안 되는 상태로 던져야 합니다. Promise.resolve().then(() => { throw error }) 로 하면 그건 unhandled rejection이 됩니다 — uncaught error가 아니라요. 둘은 다른 이벤트(unhandledrejection vs error)로 보고되고, 많은 에러 수집 도구가 전자를 다르게 취급하거나 놓칩니다. queueMicrotask 안의 throw는 진짜 uncaught error가 됩니다.

await 는 어디에?

async function f() {
  console.log('a');       // 동기 — 그 자리에서 실행
  await null;             // ← 여기서 함수가 멈추고,
  console.log('b');       //   나머지는 마이크로태스크로 예약됨
}
f();
console.log('c');
// → a, c, b

await 는 문법 설탕입니다. 뒷부분이 통째로 .then() 콜백이 되어 마이크로태스크 큐로 갑니다. 그래서 await 는 매크로태스크를 만들지 않습니다.

setTimeout(fn, 0) 은 정말 0ms인가

아닙니다. 두 가지 이유로요.

  1. 앞선 마이크로태스크를 전부 기다립니다. 큐가 안 비면 타이머 차례가 안 옵니다.
  2. 브라우저가 최소값으로 올려칩니다. HTML 명세상 setTimeout이 5단계 이상 중첩되면 최소 4ms로 클램프됩니다. 백그라운드 탭이면 1000ms 이상으로 늘어나기도 합니다.
백그라운드 탭 클램핑은 우리 결정에도 걸립니다. setTimeout으로 에러를 다시 던졌다면, 사용자가 다른 탭을 보고 있는 동안 발생한 브릿지 에러가 1초 넘게 늦게 보고될 수 있습니다. 마이크로태스크는 그런 클램핑이 없습니다.

5. 마이크로태스크가 던지면?

우리가 일부러 하고 있는 일이니 정확히 알아야 합니다. HTML 명세는 이렇게 정합니다:

마이크로태스크 콜백이 예외를 던지면 → "report the exception" 한다. 즉 window에 error 이벤트를 쏘고, window.onerror가 불리고, 콘솔에 uncaught error로 찍힌다. 그리고 루프는 다음 마이크로태스크로 계속 진행한다.

마지막 문장이 중요합니다. 우리가 핸들러 3개 중 2개가 던져서 마이크로태스크 2개를 예약해도, 둘 다 각각 보고됩니다. 하나가 다른 하나를 막지 않아요 — 우리가 for 루프에서 고친 것과 정확히 같은 성질이, 큐 레벨에서도 성립합니다.

그런데 우리 테스트는 이걸 검증하지 않습니다. 가짜 타이머(sinon)로 재봤더니 vi.runAllTicks()를 두 번 부르면 첫 번째 에러를 또 던졌습니다 — 실제 브라우저 동작이 아니라 가짜 타이머의 버릇입니다. 그래서 그 테스트는 안 썼습니다. 가짜 타이머로 확인한 사실은 "가짜 타이머의 사실"일 수 있다 — HANDOFF에 적힌, 오리진 판정을 DOM 없는 모듈로 뺀 이유와 같은 교훈입니다.

6. 우리 코드의 타임라인

이제 packages/transport-iframe/src/index.ts 에서 실제로 무슨 일이 벌어지는지 시간순으로 놓아보겠습니다. 피어가 프레임 하나를 보냈고, 핸들러 2번이 던지는 상황입니다.

매크로태스크 1개 — message 이벤트 배달

브라우저가 message 이벤트를 dispatch onWindowMessage 실행 시작 → isFromPeer 통과
핸들러 1 실행 — 정상
핸들러 2 실행 — throw! catch가 잡음 → queueMicrotask(() => { throw error }) 예약
핸들러 3 실행 — 정상 (← 이게 우리가 고친 것)
↓ 이벤트 dispatch 종료 = 매크로태스크 종료
마이크로태스크 체크포인트 예약해둔 콜백 실행 → throw error → uncaught error / window.onerror
↓
렌더링. 에러는 이미 이 프레임 안에서 보고된 뒤다

만약 setTimeout이었다면

queueMicrotasksetTimeout(…, 0)
에러가 뜨는 시점 같은 이벤트 루프 턴, 렌더링 전 빨라야 다음 턴. 대기 중인 타이머들 뒤
백그라운드 탭 영향 없음 1000ms+ 로 클램핑될 수 있음
콘솔에서 원인 찾기 원인 메시지 바로 뒤에 붙어서 나옴 무관한 로그들 사이에 섞여서 나옴
코드가 말하는 의도 "이 스택에서만 빼내라" "나중에 실행해라" — 시간 개념이 끼어듦

마지막 줄이 제일 중요합니다. client는 이미 §4.5 타임아웃에서 setTimeout을 진짜 시간 용도로 쓰고 있습니다. 여기서도 setTimeout을 쓰면 한 이름이 두 가지 다른 의도를 뜻하게 되고, 나중에 읽는 사람이 "이 지연에 의미가 있나?"를 매번 다시 판단해야 합니다.

7. 함정: 마이크로태스크 기아(starvation)

"마이크로태스크가 우선"에는 대가가 있습니다. 큐가 빌 때까지 돌기 때문에, 자기 자신을 계속 다시 예약하면 영원히 렌더링에 도달하지 못합니다. 

// 페이지가 완전히 얼어붙습니다. 스크롤도, 클릭도, 애니메이션도 안 됩니다.
function spin() { queueMicrotask(spin); }
spin();

// 이건 멀쩡합니다. 매 턴 하나씩만 처리하니 렌더링 기회가 계속 옵니다.
function tick() { setTimeout(tick, 0); }
tick();
우리 코드는 이 함정에 안 빠집니다. 예약하는 콜백이 throw 한 줄이라 새 마이크로태스크를 만들지 않기 때문입니다. 하지만 규칙으로 기억해두세요: 마이크로태스크 안에서 다시 마이크로태스크를 예약하는 루프는 위험합니다. "빠르니까 좋다"가 아니라 "양보를 안 한다"가 마이크로태스크의 본질입니다.

8. Node는 살짝 다르다

우리 테스트는 Node에서 happy-dom을 얹어 돌리니 알아둘 만합니다. Node에는 마이크로태스크 큐가 둘입니다.

큐우선순위비고
process.nextTick 큐가장 먼저Node 전용. 브라우저에 없음
Promise / queueMicrotask 큐그다음브라우저와 같은 것
타이머 등 매크로태스크마지막Node는 phase가 더 세분화됨 (timers · poll · check…)

setImmediate 도 Node 전용이고 브라우저에 없습니다. 우리 transport-iframe 은 브라우저 전용 패키지라 queueMicrotask 로 충분하고 안전합니다 — 브라우저와 Node 양쪽에 같은 의미로 존재하는 몇 안 되는 API 중 하나입니다.

한 장 요약

  1. 스레드 하나, 큐 둘. 마이크로태스크가 절대 우선.
  2. 한 턴 = 매크로태스크 딱 하나 → 마이크로태스크 전부 → 렌더링.
  3. queueMicrotask 와 Promise.then 은 같은 큐, FIFO. await 뒷부분도 여기.
  4. 마이크로태스크가 던지면 uncaught error로 보고되고, 루프는 계속 간다. 이게 우리가 쓴 성질.
  5. Promise.then 안에서 던지면 uncaught error가 아니라 unhandled rejection. 다른 이벤트다.
  6. 마이크로태스크로 무한 루프를 만들면 페이지가 언다. 양보를 안 하니까.
