T09 · Validate namespace.action before dispatch

메서드 이름도,
받은 글자 그대로 검사합니다.

profile.get처럼 정해진 이름 구조인지 확인합니다. 잘못된 이름은 -32600으로 거절하고, 형식이 맞는 요청은 기존 초기화·권한·메서드 조회 순서로 처리합니다.

T09 완료620 / 620 테스트 통과다음 T10 · 요청 번호 정책

1 · 문자열이라고 올바른 메서드 이름은 아닙니다

기존 요청 검사는 method가 문자열인지 확인했습니다. 그래서 profile..get이나 Profile.get도 이름 형식 검사 없이 초기화·권한·메서드 조회로 넘어갔습니다. 이제 요청의 바깥 형식을 확인할 때 이름 문법까지 검사합니다.

기존 SPEC에는 namespace.action과 lowerCamelCase라는 요구만 있었고 정확한 글자 규칙과 오류 순서는 없었습니다. 2026.10.23에 권장안을 승인받아 SPEC §4.2·§6.1과 ADR 0014에 먼저 기록했습니다.

이름형식 검사이유
profile.get통과소문자로 시작한 두 부분과 점 하나
profile.readName통과첫 글자 이후 대문자도 허용
profile.getURL통과첫 글자 이후 약어의 대문자 연속도 허용
storage2.get2통과첫 글자 이후 숫자도 허용
Profile.get거절namespace 첫 글자가 대문자
profile..get거절점이 두 개이고 중간 구간이 비어 있음
profile.get_name거절밑줄은 허용한 글자에 없음

형식을 통과한 이름도 실제로 구현된 기능이어야 호출할 수 있습니다. 이 표는 이름의 문법만 보여 주며 새로운 capability를 추가한 목록이 아닙니다.

2 · 짧은 패턴에 이름 규칙을 적습니다

const METHOD_NAME = /^[a-z][A-Za-z0-9]*\.[a-z][A-Za-z0-9]*$/;
부분읽는 법
^입력의 시작에서 검사
[a-z]첫 글자는 ASCII 영문 소문자 한 개
[A-Za-z0-9]*이후에는 영문 대문자·소문자·숫자를 0개 이상 허용
\.구분자로 사용하는 실제 점 한 개
뒤의 [a-z][A-Za-z0-9]*action에도 같은 글자 규칙 적용
$정규식의 끝 위치 조건. 마지막 줄바꿈 예외는 아래에서 추가 확인

허용하지 않은 글자는 공백·밑줄·하이픈·Unicode 문자 등을 포함합니다. 이름을 소문자로 바꾸거나 공백을 잘라서 합격시키지 않습니다. 승인된 규칙에는 길이 제한을 새로 넣지 않았습니다.

3 · 찾은 부분이 실제 입력 전체와 같아야 합니다

기존 isJsonRpcRequestEnvelope의 조건에 아래 마지막 비교를 더했습니다. 코드는 packages/protocol/src/index.ts에 있습니다.

typeof value.method === 'string' &&
METHOD_NAME.exec(value.method)?.[0] === value.method

먼저 문자열인지 확인하므로 숫자나 객체를 글자로 바꿔 검사하지 않습니다. exec가 찾은 결과의 첫 항목 [0]이 실제로 맞은 글자 전체입니다. 찾지 못했다면 ?.가 항목 읽기를 건너뛰어 undefined가 되므로 입력과 같지 않습니다.

JavaScript 정규식의 $는 마지막 줄바꿈 바로 앞에서도 맞을 수 있습니다. profile.get\n에서 앞부분만 맞았다고 합격시키지 않도록, 실제로 찾은 글자와 입력 전체를 한 번 더 비교합니다. T05의 ID·버전 검사에서 배운 것과 같은 이유입니다.

isJsonRpcRequest도 이 envelope 검사를 재사용하므로 두 검사 함수가 같은 이름 규칙을 지킵니다. params가 객체인지와 메서드별 필수 항목이 맞는지는 각각 다음 단계에서 확인합니다.

4 · 이름이 틀렸으면 다른 판단 전에 -32600입니다

배열·응답할 id 확인
→
envelope
메서드 이름 문법 포함
→
params의 바깥 모양
→
초기화·권한·메서드

호스트는 기존 envelope 실패 분기에서 숫자 요청 id를 그대로 돌려주고 -32600을 보냅니다. 받은 메서드 원문을 오류 메시지에 복사하지 않습니다.

요청처리
profile..get · params가 객체초기화·권한과 관계없이 -32600
profile..get · params가 배열이름 문법을 먼저 보므로 -32600
profile.get · params가 배열이름은 맞고 인자 모양이 틀려 기존 -32602
profile.get · params가 객체 · 초기화 전기존 -32005
id 없는 일반 알림 · 잘못된 이름기존 알림 규칙대로 응답 없음
잘못된 이름이 든 최상위 배열T08의 배열 거절: 응답 하나, id:null, -32600

잘못 적은 portal.initialize 는 반복 초기화가 아닙니다. 기존 초기화 상태를 바꾸지 않고 거절합니다. 거절 이후에도 정확한 이름의 초기화와 일반 호출은 계속 처리할 수 있습니다.

5 · 문법이 맞으면 기존 권한 경계를 따릅니다

SPEC §9.3·§9.6의 보안 경계와 관련된 작업입니다. 이름 문법을 통과한 일반 호출에는 기존 초기화 확인 → 권한 확인 → 메서드 조회 → 메서드별 입력 검사 → provider 확인·호출 순서를 유지합니다. params가 생략되었거나 객체인지는 이보다 앞의 바깥 모양 검사입니다.

형식이 맞는 이름호스트 상태결과
profile.readDisplayName초기화 전-32005
profile.readDisplayName초기화 후 profile 권한 없음-32000
profile.readDisplayName초기화 후 profile 권한 있음실제 구현된 메서드가 아니므로 -32601
profile.get초기화·권한·provider 준비 완료정상 프로필 결과
portalX.pingportalX 권한 없음-32000. portal과 접두사가 같아도 별개 이름

이름 검사는 공개된 글자 규칙만 사용하고 메서드 목록을 조회하지 않으므로, 권한 없는 호출에 실제 구현 여부를 알려주지 않습니다. 별도 scope 등록부를 만들지 않고 각 단계가 문법·권한·실제 기능 확인을 담당합니다. 순수 커널에 플랫폼 API나 런타임 의존성도 추가하지 않았습니다.

6 · 잘못된 이름과 기존 정상 동작을 함께 검증했습니다

먼저 기존 정상 동작을 확인하는 테스트 29개를 준비했습니다. 규칙 승인 후 경계 사례를 더한 T09 테스트는 122개이며, 구현 직전에는 83개가 실패하고 39개가 통과했습니다. 이제 전부 통과합니다.
