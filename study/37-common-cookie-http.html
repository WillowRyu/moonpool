1 · 기존 개발자는 어떤 부분을 바꿔야 하나요?

앱의 구조필요한 변경
새로 만드는 미니 앱처음부터 같은 Moonpool API를 사용
요청 코드가 API 클라이언트 한 곳에 모인 앱지원되는 경우 그 요청 함수를 교체
요청 함수 주입을 지원하는 라이브러리지원 범위가 명시된 어댑터를 연결
document.cookie나 전역 fetch를 직접 쓰는 라이브러리직접 수정하거나 대체 경로가 필요 · 자동 호환을 보장하지 않음

1번을 택하면 기존 코드 수정이 생깁니다. 이를 줄이기 위해 공통 SDK 위에 선택적으로 붙이는 요청 어댑터를 제안합니다. 전역 fetch를 몰래 바꾸거나 모든 라이브러리가 그대로 동작한다고 약속하지 않습니다.

2 · 일반 로그인에서는 쿠키를 직접 읽을 필요가 없습니다

API 이름은 아직 설계 예시입니다. 로그인 응답의 쿠키는 네이티브가 저장하고, 다음 요청에는 그 앱의 쿠키를 자동으로 붙입니다.

// 제안 API — 아직 구현된 함수가 아닙니다.
await moonpool.http.request({
  url: 'https://api.example.com/login',
  method: 'POST',
  json: { username, password },
});

const me = await moonpool.http.request({
  url: 'https://api.example.com/me',
});

서버가 쓰는 Cookie·Set-Cookie 형식은 그대로입니다. 개발자가 수동 쿠키 작업을 할 때만 await moonpool.cookies.set(...)처럼 완료를 기다립니다. 저장 완료 후 다음 요청이 새 값을 보도록 공통 순서를 정합니다.

document.cookie는 값을 즉시 반환하는 기존 API이므로 Promise로 바꾸면 같은 API가 아닙니다. 공통 비동기 API는 별도로 제공하고, 기존 코드의 호환 한계를 명시합니다.

3 · 실제 쿠키의 주인은 네이티브의 앱별 보관함입니다

A의 여러 화면은 A 보관함을 함께 쓰고 B·호스트 앱과는 분리합니다. 호스트의 로그인 쿠키나 기본 HTTP 클라이언트 세션을 가져오지 않습니다. 보관함의 주인은 메시지 안의 앱 id가 아니라 호스트가 확인한 Portal 신원으로 결정합니다.

HttpOnly 쿠키는 서버 요청에 쓸 수 있지만, 쿠키 조회 API·응답 헤더·오류 등에 직접 노출하지 않습니다. 서버가 자기 응답 본문에 쿠키 값을 반사하는 것까지 HttpOnly가 막아주지는 않습니다.

세션 초기화가 끝난 뒤 이전 요청의 늦은 Set-Cookie가 로그인을 되살리지 못하도록 네이티브의 세션 세대를 바꿉니다. 화면을 닫는 것, 앱 쿠키를 지우는 것, 서버에서 로그아웃하는 것은 각각 다른 작업입니다.

4 · 기본 document.cookie도 두 OS에서 같게 제한합니다

추천안은 WebView의 쿠키를 양쪽에서 비활성화하고 네이티브 쿠키 보관함만 사용하는 것입니다. 기본 document.cookie는 빈 값을 읽고 쓰기가 반영되지 않는 상태를 목표로 합니다. Android에서만 기본 쿠키로 우회하지 않도록 해야 합니다.

후속 실측에서 확인한 조건: 선택한 보관함의 정책을 바꿔도 실험용 호스트와 다른 보관함은 정상 동작했습니다. 하지만 iOS는 기존 HTTPS 쿠키가 남아 있으면 계속 읽고 전송했습니다. 빈 보관함을 먼저 차단한 대조군은 양쪽에서 통과했습니다. 아래 실측 결과에서 범위를 구분합니다. 이전 96개 출처 관측과 이번 쿠키 차단 관측 모두 공통 네이티브 쿠키 SDK의 구현 검증은 아닙니다.

세션을 사용하는 API 요청은 SDK로 통일합니다. 원격 fetch·XHR·form이 다른 경로로 요청하지 못하게 하고, 별도로 허용한 정적 리소스 요청에는 네이티브 쿠키를 붙이지 않습니다. 허용된 외부 스크립트가 앱 안에서 실행되면 그 앱의 SDK 권한을 쓸 수 있다는 신뢰 경계도 유지합니다.

5 · 브라우저 전체를 그대로 복제하는 설계는 아닙니다

이 SDK는 호스트가 허용한 HTTPS 서비스에 접속하는 네이티브 클라이언트입니다. 요청에는 http 권한이 필요하고, 쿠키를 직접 읽거나 수정하려면 cookies 권한도 필요합니다. 호스트가 지정하지 않은 API 주소나 게스트가 주장한 쿠키 보관함을 사용할 수 없습니다.

허용된 서비스의 자체 세션으로 쿠키를 선택하므로, 브라우저의 교차 사이트 SameSite·CORS 차단을 그대로 재현하지 않습니다. 이 차이는 명시적인 설계 선택이며 검토가 필요합니다. 초기안은 자동 리다이렉트를 하지 않고 3xx 응답을 돌려주므로, 브라우저 리다이렉트 기반 로그인도 그대로 호환되지 않습니다.

일반 요청은 쿠키 포함이 기본값이고, omit을 지정하면 보내지도 저장하지도 않는 안입니다. 세션 쿠키는 화면 재생성 동안 유지하되 네이티브 프로세스 재시작 때 끝내고, 영구 쿠키는 만료 규칙에 따라 유지합니다. 이 세부 정책들도 제안 상태입니다.

6 · 설계를 승인하기 전에 확인할 결과가 명확해야 합니다

동일한 C01–C12 기준으로 앱별 격리, 서버가 실제로 받은 쿠키, HttpOnly 보호, 만료·삭제, 늦은 응답과 세션 초기화, WebView 우회 방지, 호스트에 영향 없는 쿠키 차단, 기존 API 클라이언트의 어댑터 사용을 검사해야 합니다.

계약 검토와 검사 절차를 먼저 작성한 뒤, 새 쿠키 검사만 재개하도록 승인받았습니다. C09/C10 일부를 실제로 측정했고 의도적 충돌 재현은 하지 않았습니다. 공통 SDK 구현·SPEC·프로토콜 0.1은 그대로이며 T28도 아직 완료가 아닙니다.

7 · 첫 검사는 “호스트 로그인도 그대로인가?”입니다

쿠키를 끄는 API가 있어도, 그 설정이 호스트 앱의 다른 WebView까지 영향을 주면 사용할 수 없습니다. Android의 Profile별 CookieManager가 실제로 설정까지 분리하는지, iOS도 기존 쿠키가 있는 보관함에서 같은 결과를 내는지 확인해야 합니다.

순서실험에서 확인할 결과
① 대조군을 먼저 확인실험용 호스트 H와 별도 보관함 U에서 공개 표식 쿠키를 저장·조회·전송할 수 있어야 함
② A만 쿠키 차단A의 두 화면에서는 읽기가 비고 쓰기가 무효이며, B·H·U는 계속 정상 동작
③ B도 차단 후 재생성A·B는 제한을 유지하고 H·U의 쿠키는 계속 정상 · 게스트 실행 전에 정책 적용 완료
④ 서버 수신 기록 대조JS 화면만 보지 않고 HTTPS 서버가 실제 받은 Cookie와 요청 횟수까지 검사

사용자의 실제 로그인 정보를 쓰지 않고 실험용 표식만 사용합니다. 이 첫 실험으로 모든 네트워크 우회·네이티브 쿠키 기능이 검증된 것은 아닙니다. C01–C12 전체 검증은 남아 있습니다.

계약 승인 전에 남은 선택: 기본 쿠키 포함과 수동 리다이렉트, 네이티브 서비스 요청의 SameSite·CORS 차이, 앱 전체 세션 초기화, 기존 라이브러리의 수정 비용입니다. 공통 비동기 방향을 선호한다는 결정과 이 세부 정책의 최종 승인은 구분합니다. 보안 명세 §9에도 영향을 줍니다.

8 · “늦은 응답”은 도착 위치에 따라 달라집니다

HTTP 응답은 헤더가 먼저 오고 본문이 나중에 올 수 있습니다. Set-Cookie는 헤더에 있으므로 화면의 Promise가 아직 기다리는 중이어도 쿠키는 이미 저장됐을 수 있습니다.

// 테스트 순서 예시 — 아직 구현된 SDK가 아닙니다.
서버: 요청 수신 → 응답 헤더를 보류
앱 A: 세션 초기화 완료
서버: 이전 Set-Cookie 헤더를 전송
검사: 이전 쿠키가 다시 저장되지 않아야 함
초기화 시점기대 결과
헤더가 오기 전늦게 온 이전 세대 쿠키는 저장되지 않음
헤더 저장 후, 본문 도착 전이미 저장된 쿠키를 초기화가 지우고, 늦은 본문이 옛 세션을 되살리지 않음
응답 Promise가 이미 끝난 뒤끝난 Promise는 바꾸지 않으며, 다음 요청에 옛 쿠키가 붙지 않음

시간 초과나 화면 종료로 이미 끝난 Promise도 다시 끝내지 않습니다. 서버에서 일어난 작업은 취소됐다고 가정하지 않고, 쿠키 저장과 응답 전달을 따로 검사합니다. 같은 앱의 다른 화면에도 초기화가 적용되고, 다른 앱과 호스트에는 영향이 없어야 합니다.

C01–C12 상세 절차에 쿠키 규칙·오류 형식 등 아직 정하지 않은 항목도 표시했습니다. 이번 실측은 쿠키 차단만 다뤘으며, 이 세션 초기화 검사는 아직 계획 단계입니다.

9 · 새 저장을 막는 것과 기존 쿠키까지 막는 것은 달랐습니다

Android·iOS 각각 두 번씩 실행해 200개 관측과 HTTPS 서버 요청 400건을 남겼습니다. 쿠키를 읽는 화면만 확인하지 않고 네이티브 저장소와 서버 수신 기록을 함께 대조했습니다.

측정한 iOS 26.4.1에서의 결과입니다. 실제 제품은 이 실험처럼 HTTPS 진단 페이지 이동을 허용한다는 뜻이 아니며, 사용자의 로그인 정보가 유출됐다는 뜻도 아닙니다. 정책 API 하나로 기존 쿠키까지 모두 차단된다고 약속할 수 없다는 근거입니다.

후속 결정 · 기본 정책 채택: WebView 쿠키가 있거나 없음을 확인하지 못하면 실행을 거절하고 데이터를 보존하기로 했습니다. 같은 저장소를 쓰는 해당 앱의 기존 화면도 종료하며, 다른 앱과 호스트는 유지합니다. 자동 쿠키 삭제·이전은 하지 않습니다. 구현·복구 절차·최종 명세 변경은 별도이며, 실험에서 기존 보관함을 지우지 않았습니다.

검증기 테스트 21개는 통과했고, 실제 iOS 계약 검사는 실패 상태를 그대로 유지합니다. “측정과 검증기가 정상 동작했다”와 “제품 계약이 충족됐다”는 다릅니다. 전체 네트워크 경로·마이그레이션·실제 SDK 연결은 남아 있습니다. 전용 기기와 서버는 종료했고 의도적 충돌 재현은 하지 않았습니다.

10 · 비어 있어야 하는 것은 WebView 쿠키입니다

2026년 11월 3일, Android와 iOS 모두 같은 기준으로 실행을 판단하는 기본 정책을 채택했습니다. 해당 앱의 WebView 쿠키가 하나라도 있거나, 없다는 사실을 확인할 수 없으면 실행을 거절합니다. Android만 기존 쿠키를 허용하는 예외는 두지 않습니다.

데이터남아 있어도 되는가?실행 거절 시
WebView의 기본 쿠키아니요 · HttpOnly와 다른 서비스의 쿠키도 포함삭제하지 않고 보존
localStorage·IndexedDB네 · 별도 로딩·네트워크 검사는 필요값과 기존 저장소 연결 보존
storage.*의 앱 데이터네그대로 보존
SDK의 별도 네이티브 로그인 쿠키네 · WebView 쿠키와 다른 보관함자동 로그아웃·초기화하지 않음
// 실행 판단 예시 — 아직 구현된 API가 아닙니다.
WebView 쿠키 0개 + 저장된 화면 설정 있음 → 다른 검사가 통과하면 실행

쿠키 확인이 끝나지 않거나 실패함       → 실행 거절, 데이터 보존

document.cookie가 빈 문자열이어도 HttpOnly나 다른 주소의 쿠키는 남아 있을 수 있습니다. 그래서 네이티브가 그 앱의 전체 쿠키 저장소를 확인해야 합니다. 쿠키 값은 게스트나 호스트 JS 실행 환경으로 보내지 않습니다.

같은 앱 A의 두 화면은 같은 보관함을 사용하므로 검사를 함께 관리합니다. 뒤늦게 돌아온 옛 검사 결과는 새 화면을 열어 주지 못해야 합니다. 공통 저장소 검사에 실패하면 A의 새 실행을 막고 이미 열린 A 화면도 종료하기로 했으며, B와 호스트 화면에는 영향을 주지 않습니다. 확인 실패가 실제 정보 유출을 뜻하는 것은 아닙니다.

후속 부분 검증: 38번 자료에서 실제 저장소 조회·데이터 보존·제어된 동시 실행과 늦은 콜백을 검증했습니다. iOS partitioned 전체 탐지 범위와 실제 쓰기 작업 배제는 아직 미확정입니다. 빈 쿠키 저장소라는 사실만으로 캐시·worker·외부 리소스의 네트워크 차단이 증명되지는 않으며, 최종 계약과 제품 구현도 남아 있습니다.

11 · 실행 거절과 쿠키 삭제는 별도 결정입니다

채택한 초기 정책은 “실행은 거절하되 데이터는 보존”입니다. 실행을 다시 시도하는 행위가 쿠키 삭제를 허가하지는 않습니다. 쿠키를 SDK의 네이티브 보관함으로 자동 복사하는 기능도 초기 범위에서 제외했습니다.

선택사용자에게 생기는 결과결정 상태
거절하고 보존조건이 해결되기 전에는 해당 앱을 열 수 없음 · 데이터 유지초기 기본값으로 채택
호스트가 명시적으로 쿠키만 정리기존 브라우저 로그인·쿠키 설정은 사라지고, 다른 저장 데이터는 유지해야 함별도 승인·검증 후 추가할 복구 절차
기존 쿠키를 SDK로 자동 복사쿠키의 원래 권한과 사용 문맥을 잘못 가져올 수 있음초기 범위에서 제외
보관함 전체 교체·초기화localStorage·IndexedDB까지 잃거나 이전 주소의 데이터와 연결이 끊길 수 있음자동 복구 수단으로 사용하지 않음

나중에 쿠키만 정리하는 복구를 추가하더라도, 먼저 그 앱의 화면과 쿠키 쓰기 작업을 멈추고 대상 보관함을 확인해야 합니다. 삭제 완료 콜백만으로 성공 처리하지 않고 다시 전체 저장소를 검사합니다. 일부만 삭제되거나 중간에 앱이 종료되면 실행 거절 상태를 유지하며, 완료 후에도 새 검사부터 시작합니다.

http.resetSession은 별도 네이티브 로그인 세션을 초기화하는 제안 API입니다. WebView 쿠키 정리 권한이나 게스트가 실행 거절을 우회하는 통로로 사용하지 않습니다. 구체적인 복구 저장 방식과 중단 후 복원 보장은 T48에서 검증해야 합니다.

채택한 기본 정책과 남은 복구 검토안에서 승인 범위와 후속 검증 항목을 구분했습니다. 이번에는 결정을 문서에 기록했으며 기기 재실행이나 데이터 삭제를 하지 않았습니다.
