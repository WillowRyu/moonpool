문지기(permission gate) 심화 네 가지

결정 1 = A(-32000, scope 검사가 먼저), 결정 2 = A(HostConfig에 타입 있는 칸). 이 두 결정이 왜 맞는지를 네 개의 개념으로 풀어 본다.

차례
  1. fail-closed: 검문 순서가 왜 보안이 되는가
  2. 에러 코드가 새는 정보: -32000과 -32601에서 상대가 배우는 것
  3. 의존성 주입: 결정 2-A는 이미 우리가 쓰던 패턴
  4. params 검증을 라이브러리 없이 TypeScript로

1. fail-closed: 검문 순서가 왜 보안이 되는가

fail-closed(= fail-secure): 모르거나, 빠졌거나, 고장 났을 때 닫힘(거부) 쪽으로 기우는 설계.
fail-open: 그 반대. 판단이 안 서면 열어 준다.

비유: 정전이 났다. 은행 금고 문은 잠긴 채로 있어야 하고(fail-closed), 비상구는 열려야 한다(fail-open). 둘 다 옳다. 차이는 "어느 쪽 실수가 더 싼가"다.

우리 문지기의 실수비용되돌릴 수 있나
정당한 호출을 잘못 거부개발자가 에러를 보고 manifest나 grant를 고친다있다
부당한 호출을 잘못 허용다른 미니앱의 데이터, 사용자 정보가 새어 나간다없다

그래서 권한 검사는 언제나 금고 쪽이다. 이걸 코드 모양으로 고정하는 방법이 두 가지 있다.

모양 1: 허용 목록(allowlist) vs 금지 목록(denylist)

fail-open · 금지 목록

if scope in deniedScopes
  → deny
→ allow            // 새 scope는 자동 허용

fail-closed · 허용 목록 (우리 선택)

if scope not in grantedScopes
  → deny
→ allow            // 새 scope는 자동 거부

둘 다 "검사"처럼 보이지만 기본값이 반대다. grantedScopes.includes(scope)는 허용 목록이다. 내일 camera라는 scope가 생겨도, 명시적으로 grant되기 전까지는 자동으로 거부된다.

모양 2: 검문 순서

같은 검사들도 순서를 바꾸면 fail-open이 될 수 있다. 우리 디스패처에서 6번(출입증)과 7번(방 존재)의 순서를 바꿔 보자. 아래 표는 storage 출입증이 없는 미니앱이 세 가지 호출에 대해 받는 답이다.

호출scope 먼저 (결정 1-A)메서드 존재 먼저 (잘못된 순서)
storage.get (존재함)-32000-32000
storage.zzz (없음)-32000-32601 ← get과 답이 다르다
camera.take (호스트에 없는 층)-32000-32601

왼쪽 열은 세 답이 전부 같다. 출입증 없는 층에 대해서는 두드려 봐도 아무것도 알 수 없다. 오른쪽 열은 답이 갈리므로, 미니앱이 이름을 하나씩 던져 보면서 "어떤 방이 존재하는가"를 알아낼 수 있다. 검사 코드는 한 줄도 안 바뀌었고, 순서만 바뀌었는데 문이 살짝 열린 것이다.

출입증이 있는 미니앱은 물론 storage.get은 결과, storage.zzz는 -32601을 받는다. 그건 자기 층이니 알아도 된다.

이 코드베이스에 이미 있는 fail-closed

어디무엇열어 줬다면

SPEC §5.1반복 handshake 때 리셋할 상태 목록이 닫혀 있음새 상태를 깜빡하면 사용자 동의 기록이 날아감
디스패처 마지막 줄어느 분기에도 안 걸리면 -32601. "통과 = 허용"이 아니다모르는 메서드가 조용히 실행됨
같은 함정, 다른 옷. portal.*은 scope가 필요 없다(§6.2). 이 예외를 method.startsWith('portal')로 쓰면 portalx.hack이 통과한다. 점 앞을 잘라 정확히 'portal'과 비교해야 한다. origin의 startsWith 함정과 완전히 같은 모양이다.

메서드 이름점 앞(scope)결과

전부 거부다. 문지기가 "이건 무슨 경우지?"라고 헷갈리는 순간에도 답이 거부라면 잘 설계된 것이다.

2. 에러 코드가 새는 정보: -32000과 -32601에서 상대가 배우는 것

정보 누출(leak): 답의 내용이 아니라 답의 차이가 정보가 되는 것. "A일 때는 이 답, B일 때는 저 답"이면 답만 보고 A/B를 알 수 있다.

여기서 "상대"는 누구인가. 호스트가 실행하는 제3자 코드, 즉 악의적이거나 해킹당한 미니앱이다. 그 코드는 우리 문지기에게 마음대로 질문할 수 있고, 답을 전부 기록할 수 있다.

웹의 고전 사례 두 개

  • 로그인 폼이 "비밀번호가 틀렸습니다"와 "그런 계정이 없습니다"를 구분해 주면, 아이디만 대량으로 던져서 가입된 계정 목록을 얻는다. 그래서 요즘은 둘 다 "아이디 또는 비밀번호가 틀렸습니다"다.
  • GitHub은 권한 없는 private 저장소에 403(금지)이 아니라 404(없음)를 준다. 저장소가 존재한다는 사실 자체를 감추기 위해서다.

우리 코드 하나하나가 말해 주는 것

답미니앱이 새로 배우는 것이미 알고 있었나
-32000 PERMISSION_DENIED이 scope는 나에게 없다그렇다. handshake의 grantedScopes와 자기 manifest로 이미 안다
-32601 METHOD_NOT_FOUND이 메서드는 존재하지 않는다내 층 안에서라면 알아도 된다
-32602 INVALID_PARAMS메서드가 존재하고 scope도 있는데 서류 모양이 틀렸다내 층이므로 문제 없음
-32001 CAPABILITY_UNAVAILABLE프로토콜엔 있는데 이 호스트엔 구현이 없다. 호스트/플랫폼의 윤곽낮은 위험. 플랫폼은 handshake의 host.platform에 이미 있다
-32603 INTERNAL_ERROR핸들러가 넘어졌다message에 스택트레이스나 파일 경로를 넣으면 여기가 구멍이 된다
결정할 때 던질 질문 하나. "이 답으로 상대가 이미 아는 것 이상을 배우는가?"
-32000의 답은 "아니오"다. 미니앱은 출입증을 받을 때 못 가는 층을 이미 들었다. 새 정보가 0이므로 -32601로 숨길 이유가 없고, 그렇다면 디버깅이 쉬운 쪽이 이긴다. 이것이 결정 1-A의 논리 전부다.

순서와 합치면

1절의 표를 다시 보자. scope 검사가 먼저이면 출입증 없는 층은 무슨 이름을 던져도 -32000이다. 답이 하나뿐이니 차이가 없고, 차이가 없으니 누출이 없다. 결정 1-A는 "코드 선택"과 "순서 선택" 두 개가 합쳐진 것이고, 둘 중 순서가 더 중요하다.

코드 말고 message와 data도 채널이다

SPEC §4.4: error.data는 구조화된 맥락을 담을 수 있지만, 호스트 자격증명, 토큰, 다른 미니앱의 데이터를 담아서는 안 된다. 실무 규칙으로 옮기면:

  • -32602의 message는 "expected params.key to be a string"처럼 어느 필드가 어떤 타입이어야 하는지까지는 괜찮다. 호출자가 보낸 서류니까. 값을 되돌려 보낼 필요는 없다.
  • -32603의 message는 일반적인 한 문장으로 고정한다. 핸들러가 던진 Error.message를 그대로 실어 보내지 않는다. 그 안에는 파일 경로, SQL, 내부 URL이 들어 있을 수 있다.

더 깊은 층: 답이 같아도 걸리는 시간이 다르면 그것도 채널이다(timing side channel). scope 검사가 맨 앞에 있으면 거부 경로가 가장 짧고 균일해서 이 면에서도 유리하지만, v0.1의 범위는 아니다.

3. 의존성 주입: 결정 2-A는 이미 우리가 쓰던 패턴

의존성 주입(dependency injection, DI): 어떤 코드가 필요한 것을 직접 만들거나 찾지 않고, 밖에서 넣어 받는 것. 이름은 거창하지만 본질은 "매개변수로 받기"다.

비유: 건물 보안 시스템(커널)은 직원(handler)을 고용하지 않는다. 입주사(호스트 앱)가 직원을 데려오고, 시스템은 출입증만 확인한 뒤 그 직원을 부른다. 시스템은 직원이 누구인지 몰라도 되고, 입주사가 바뀌어도 시스템은 그대로다.

이미 코드베이스 곳곳에 있다

어디무엇을 넣어 받나덕분에
createHost(config)hostInfo, manifest, grantedScopes, environment커널이 "이 호스트가 누구인지" 하드코딩하지 않는다
host.connect(transport)Transport테스트는 메모리 전송, 브라우저는 iframe 전송, iOS는 WKScriptMessageHandler. 커널 코드는 한 줄도 안 바뀐다
createClient({ transport })Transport위와 같음, 반대편
createIframeTransport({ localWindow })자기 window테스트가 전역 window 대신 stub을 넣을 수 있다

CLAUDE.md의 "Kernel is pure, transport is swappable"은 문장이고, connect(transport)는 그 문장의 실체다. Transport를 만들지 않고 받기 때문에 커널은 순수할 수 있다.

결정 2-A가 하는 일: 포트와 어댑터

커널 (pure) — 인터페이스(port)를 정의한다        호스트 — 구현(adapter)을 공급한다

  ProfileProvider  ◄───────────────────────  mock-host: 고정된 { displayName }
                                             iOS host : 로그인 세션에서 읽음
                                             tests    : 호출을 기록하는 가짜

  StorageProvider  ◄───────────────────────  mock-host: 메모리 Map
                                             iOS host : UserDefaults / 파일
                                             tests    : 가짜

커널이 정하는 것은 모양뿐이다. 4단계에서 시원 님이 타이핑할 것의 스케치(최종본 아님):

interface StorageProvider {
  get(key: string): Promise<JsonValue | null>;
  set(key: string, value: JsonValue): Promise<void>;
  delete(key: string): Promise<void>;
}

전부 Promise인 이유: SPEC §9.5 "Async only". 메모리 Map은 동기로도 되지만, 인터페이스가 동기이면 iOS 구현이 같은 모양으로 들어올 수 없다. 인터페이스는 가장 느린 구현에 맞춰야 한다.

왜 이게 보안 설계이기도 한가

핸들러에 닿는 유일한 길이 커널의 dispatch다. 미니앱은 핸들러 객체를 볼 수도, 부를 수도 없고, 오직 JSON 메시지를 보낼 수 있을 뿐이다. 그 메시지는 반드시 문지기를 지난다. SPEC §9.3 "check the granted scope immediately before invoking a handler"가 구조적으로 보장되는 이유다. 핸들러를 커널 안에 하드코딩했다면 문지기와 핸들러 사이에 "지름길"을 만들 유혹이 늘 있다.

이름 두 개

  • ports and adapters(= hexagonal architecture): 위 그림의 이름. 안쪽(커널)이 포트를 정의하고 바깥(플랫폼)이 어댑터를 꽂는다.
  • DI 컨테이너(Spring, NestJS 등): 이 "넣어 주기"를 자동화한 프레임워크. 우리는 함수 인자로 충분하다. 컨테이너가 없어도 DI다.

3단계에서 정할 것 미리보기: 미니앱끼리의 벽(§6.3 "namespaced per mini app id")을 커널이 키 앞에 id를 붙여서 칠지, 호스트가 미니앱마다 다른 Provider를 넣어서 칠지. 커널이 치면 순수 테스트로 "다른 미니앱 키를 못 읽는다"를 증명할 수 있다.

4. params 검증을 라이브러리 없이 TypeScript로

핵심 사실. TypeScript 타입은 컴파일하면 사라진다. params: { key: string }이라고 적는 것은 컴파일러에게 하는 약속이지 검사가 아니다. 다리를 건너온 params는 다른 origin에서 온 JsonValue, 즉 신뢰할 수 없는 입력이다. SPEC §9.6은 그래서 "validate params against a schema before dispatch"를 MUST로 둔다.

이미 있는 도구: 타입 가드(type predicate)

반환 타입이 value is T인 함수. 본문이 런타임 검사를 하고, 결과가 true이면 컴파일러가 그 뒤부터 value를 T로 취급한다. isJsonObject, isJsonRpcRequest, hasRequestId가 전부 이것이다. 메서드마다 하나씩 같은 패턴을 쓰면 된다.

실제 메서드는 4단계에서 시원 님이 쓸 것이므로, 여기서는 가상의 메서드로 모양만 본다. greeting.say의 params가 { name: string; times?: number }라고 하자.

type GreetingSayParams = { name: string; times?: number };

function isGreetingSayParams(v: JsonValue | undefined): v is GreetingSayParams {
  return (
    isJsonObject(v) &&                                   // ① 객체인가 (null, 배열 제외)
    typeof v.name === 'string' &&                        // ② 필수 필드
    (v.times === undefined || typeof v.times === 'number') // ③ 선택 필드: 없거나, 맞는 타입
  );
}
줄왜 이 순서인가
①isJsonObject가 먼저 true여야 v.name이라는 인덱싱이 타입상 허용된다. &&는 왼쪽이 false이면 오른쪽을 평가하지 않으므로 순서가 곧 안전이다.
②noUncheckedIndexedAccess가 켜져 있어 v.name의 타입은 JsonValue | undefined다. typeof가 그것을 string으로 좁힌다. 없는 필드는 undefined라 자연히 실패한다.
③선택 필드는 "없다"와 "있는데 틀리다"를 구분해야 한다. { name: 'a', times: 'many' }는 거부되어야 한다.

HANDOFF에 적힌 교훈을 다시

타입 가드는 검증되지 않은 단언이다. 본문을 return true로 바꿔도 컴파일된다. D단계에서 실제로 isJsonRpcRequest의 본문이 붙여넣기 사고로 바뀌었는데 typecheck는 통과했고 테스트 8개가 잡았다. 그러니 가드마다 테스트, 그것도 false여야 하는 입력을 반드시 포함한 테스트가 필요하다.

가드에서 -32602까지

if (!isStorageGetParams(message.params)) {
  reply error { code: -32602, message: 'expected params.key to be a string' }
  return
}
// 여기부터 message.params는 { key: string } — 컴파일러도 안다

message에는 어느 필드가 어떤 타입이어야 하는지만 적는다. 받은 값을 되돌려 보내지 않는다(2절).

왜 zod 같은 스키마 라이브러리를 안 쓰나

이유설명
CLAUDE.mdprotocol, client, host는 zero runtime dependencies. 다리의 신뢰 경계에 남의 코드를 넣지 않는다
크기v0.1 메서드는 4개. 가드 4개는 스키마 라이브러리 배우는 시간보다 짧다
이식성손으로 쓴 가드는 Swift/Kotlin으로 그대로 옮길 수 있다. zod 스키마는 못 옮긴다. 네이티브 코어는 v0 다음이지만, 지금 모양이 그때의 비용을 정한다
나중에메서드가 수십 개가 되면 스키마 + 코드 생성이 답일 수 있다. 그때는 ADR 한 장이 필요한 결정이다

4단계에서 정할 것 미리보기

  • 모르는 추가 필드: 거부할까, 무시할까. JSON-RPC 관례와 앞으로의 호환성은 "무시"를 가리키고, 핸들러가 아는 필드만 읽는다면 무시해도 안전하다.
  • 크기 제한: storage.set에 50MB 값이 오면? 이건 모양 검사가 아니라 자원 문제다. SPEC에 없으므로 open decision으로 올린다.
  • 가드가 사는 곳: wire 모양은 양쪽이 공유하므로 protocol 패키지가 자연스럽다. 클라이언트도 UX용 사전 검사에 쓸 수 있다(§9.3: "Client-side checks are a UX affordance only").

코드에서 찾아보기: packages/protocol/src/index.ts의 isJsonObject, isJsonRpcRequest, hasRequestId. 세 가드의 모양이 그대로 params 가드의 모양이다.

한 장 정리

  • fail-closed: 헷갈리면 거부. 허용 목록으로 쓰고, scope 검사를 메서드 조회보다 앞에 둔다. 순서가 곧 보안이다.
  • 누출: 답의 차이가 정보다. -32000은 상대가 이미 아는 것만 말하므로 안전하고, 그래서 디버깅이 쉬운 쪽을 고른다. -32603 message에 내부 정보를 싣지 않는다.
  • DI: 커널은 인터페이스만 정하고 호스트가 구현을 넣는다. Transport에서 이미 하던 일을 capability에도 한다. 핸들러로 가는 유일한 길이 문지기를 지나게 된다.
  • params 검증: 타입은 사라지므로 타입 가드로 런타임에 검사한다. 가드마다 false 케이스 테스트. 라이브러리는 안 쓴다.
