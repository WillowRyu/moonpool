Android가 직접 알려 주는 WebView·출처·프레임 정보를 실측했습니다. 첫 포트 전달의 인증과 그 이후 메시지의 발신자 확인을 구분하고, 문서 교체와 포트 재전달에서 생기는 한계도 확인했습니다.

1 · 페이지의 주장과 네이티브 관찰을 구분합니다

// Deliberately forged by the fixture page:
{ claimedOrigin: "https://forged.invalid", claimedMainFrame: true }

// Separately supplied by WebView's native callback:
onPostMessage(view, message, sourceOrigin, isMainFrame, replyProxy)

메시지 본문의 출처나 앱 ID는 페이지가 마음대로 쓸 수 있습니다. 이번 실험은 그 값을 거짓으로 보내면서, 실제 Android 콜백의 WebView 인스턴스·sourceOrigin·isMainFrame을 검사했습니다. 페이지의 주장이 권한을 고르지 못하게 한 것입니다.

페이지를 로드하기 전에 리스너를 등록하자 HTML head의 첫 인라인 스크립트에서도 메시지가 왔습니다. 그 시점은 page-finished보다 빨랐습니다. 페이지 로드 완료를 권한의 시작 신호로 삼지 않고 실제 메시지의 정보를 확인해야 합니다.

2 · 출처가 같아도 프레임과 인스턴스를 확인합니다

if (!active) return "retired";
if (owner != sender) return "wrong-view";
if (!expectedOrigin.equals(origin)) return "wrong-origin";
if (!mainFrame) return "subframe";
return "accepted";

정확한 출처에만 객체를 주입해도 같은 출처의 iframe은 그 객체를 받았습니다. 따라서 메인 프레임 여부를 검사해야 합니다. A와 같은 주소를 띄운 다른 WebView도 A의 인스턴스가 아니므로 별도로 거절해야 합니다.

다른 WebView의 실제 콜백 메타데이터를 A의 검사에 넣는 실험은 호스트가 의도적으로 잘못 연결한 대조군입니다. Android가 콜백을 잘못 전달했다고 해석하지 않습니다. 이 발신자 검사는 실험 전용이며 기존 JSON-RPC 권한·기능 처리를 복제하지 않았습니다.

SPEC §9와 연결됩니다. 이번에는 공개 진단 메시지만 주고받습니다. 호스트 자격 증명이나 실제 기능은 연결하지 않았고, 제품의 출처·프레임·이동 정책을 확정하지 않았습니다.

3 · 정확한 출처만으로는 같은 주소의 새 문서를 구분하지 못합니다

A의 첫 문서에서 준비
→
같은 출처의 새 문서
→
늦게 targetOrigin=A로 전달
→
새 문서가 포트를 받음

targetOrigin은 출처를 제한합니다. 같은 출처에 있는 서로 다른 문서까지 구분하지는 않습니다. 실제 실험에서도 이전 문서용으로 준비한 전달이 새 문서에 도착했습니다.

같은 앱의 새 문서가 받으면 얼마나 중요한 문제인가요?

같은 origin·앱·권한을 유지하는 문서 교체 자체가 다른 앱으로의 권한 유출은 아닙니다. 새 문서의 새 연결로 초기화한다면 포트를 새 문서가 받는 동작은 정상적인 재연결일 수도 있습니다. 문제는 이전 문서의 연결이나 진행 중인 요청까지 새 문서의 것으로 잘못 연결할 때입니다.

현재 공통 커널은 새 문서의 portal.initialize를 받아 초기화 상태와 요청 번호 기준을 다시 시작합니다. 하지만 모든 요청·응답에 검증된 문서 식별자를 붙이는 장치는 아직 없습니다. 새 클라이언트는 초기화 요청을 1번으로 보내고 다음 요청을 2번으로 보내므로, 이전 문서와 번호가 겹칠 수 있습니다.

// Hypothetical editor using the existing storage.get capability:
Document A: initialize #1; get draft:post-1 #2
// Reload / navigate within the same mini app; old host work is still pending.
Document B: initialize #1; get draft:post-2 #2
// If the transport delivers A's late reply into B's current connection:
{ "jsonrpc": "2.0", "id": 2, "result": { "value": "Post 1 draft" } }

B가 id 2만 보고 자기 요청의 응답으로 받으면 글 2 편집기에 글 1 초안이 들어갑니다. 그 미니앱이 자동 저장한다면 잘못 표시한 내용을 draft:post-2에 저장할 수도 있습니다. 권한을 넘어 다른 앱을 읽은 상황은 아니지만 자기 앱 데이터가 잘못 바뀔 수 있는 정확성 문제입니다. 이전 응답을 새 문서에 전달하지 않는 통로라면 이 경로는 차단됩니다.

SPEC §11의 Responses that outlive their document도 이 한계를 명시합니다. T25에서 직접 재현한 것은 늦은 포트 전달과 포트 재전달입니다. 위의 요청 번호 혼선·자동 저장은 그 중요성을 설명하는 조건부 예시이며, T25에서 데이터 덮어쓰기를 실측했다는 뜻은 아닙니다.

문서별 reply proxy로 보낸 임시 확인값을 포트에서 증명하게 한 실험에서는 이전 확인값이 거절되고 새 문서의 확인값은 통과했습니다. 교체·같은 URL 새로고침 뒤 이전 reply proxy로 보낸 답도 새 문서에는 도착하지 않았습니다. 확인값은 보고서에 저장하지 않았습니다.

const channel = new MessageChannel();
T25Pinned.postMessage(publicDiagnostic, [channel.port2]);
// Native callback receives the transferred port together with
// sourceOrigin / isMainFrame / actual WebView.

페이지에서 만든 포트를 네이티브 콜백으로 넘기는 방법도 시험했습니다. 실제 프레임 정보와 함께 하나의 포트가 도착했고 왕복 통신이 됐습니다. 초기 전달을 실제 발신자 정보에 묶는 근거지만, 이후 모든 메시지의 발신자를 증명하는 것과는 별도입니다.

이때 확인되는 것은 포트를 넘긴 프레임입니다. 연결된 반대쪽 포트를 어느 프레임에서 만들었는지나, 이후 어디로 옮겼는지까지 직접 증명하지는 않습니다.

이 확인값이나 문서 라벨은 실험용 데이터입니다. Moonpool 메시지에 새 필드를 추가한 것이 아니며, 최종 문서 신원 계약은 T30에서 정합니다.

4 · 승인된 페이지가 포트와 확인값을 직접 넘기면

// Deliberately done by the authorized A fixture:
foreignFrame.contentWindow.postMessage(
  { kind: "delegated", proof }, foreignOrigin, [port]
);

A가 포트와 확인값을 B의 iframe에 직접 넘기게 했습니다. B의 리스너는 네이티브에서 B 출처·하위 프레임으로 식별됐습니다. 하지만 이어지는 포트 메시지에는 그 출처·프레임 인자가 없었고, 유효한 확인값은 여전히 통과했습니다.

통로네이티브가 받는 정보이번에 확인한 한계
origin-aware listener실제 WebView·출처·메인 프레임·reply proxy같은 출처 문서의 신원·수명 계약은 추가로 필요
MessagePort callback포트와 메시지이후 포트 재전달의 실제 출처·프레임을 직접 알려 주지 않음

따라서 “처음 포트를 안전하게 건넸으니 이후에도 모든 메시지가 처음 문서에서 온다”라고 결론 내리지 않았습니다. SPEC §9.1을 어떻게 만족시킬지는 T26의 iOS 근거까지 모아 후속 계약에서 결정합니다.

5 · 같은 네이티브 포트라도 Java 래퍼는 달랐습니다

처음에는 등록한 포트 객체와 콜백의 포트 객체를 ==로 비교했습니다. 실제 AndroidX가 다른 래퍼 객체를 돌려줘 정상 메시지도 막혔고, 여섯 왕복 관찰이 실패했습니다.

// The callback registration already captures the native-owned binding.
hostPort.setWebMessageCallback(new WebMessageCallbackCompat() {
  public void onMessage(WebMessagePortCompat wrapper, WebMessageCompat message) {
    receivePort(binding, wrapper, message, "platform");
  }
});

수정 후에는 네이티브가 그 포트에 등록한 콜백의 소유 관계로 연결을 찾고, 보관한 endpoint로 답합니다. 래퍼의 == 결과는 관찰값으로만 남겼습니다. WebView 인스턴스 검사와 포트 래퍼 비교는 서로 다른 API 계약이므로 겉모양이 비슷해도 같은 판단을 적용하지 않았습니다.

연결을 명시적으로 폐기한 뒤 실제로 들어온 메시지는 거절됐습니다. 보관된 콜백을 직접 재실행한 대조군도 거절됐고, 포트를 두 번 닫은 뒤 보내기는 IllegalStateException으로 실패했습니다. 갑작스러운 렌더러 종료까지 검증한 결과는 아닙니다.

6 · 어디까지 끝났고 다음은 무엇인가

HTTPS 두 번·custom scheme 두 번, 총 44개 관찰과 175개 대조군 검사가 통과했습니다. 독립 JVM 발신자 계약 11개와 기존 TypeScript 1,134개·Python 9개 검사도 통과했습니다. Android 빌드·린트는 성공했고 남은 실험용 경고 29개와 Gradle 경고도 기록했습니다.
