T13 · Close once, clean up failed sends

문을 닫으면 새 주문을 막고,
전송에 실패하면 그 대기표를 치웁니다.

연결 전체를 닫는 일과 요청 하나를 보내다가 실패하는 일은 처리 범위가 다릅니다. 닫힌 연결은 다시 쓰지 않고, 전송 실패는 해당 요청의 기다림과 타이머만 정리합니다.

T13 완료848 / 848 테스트 통과다음 T14 · portal.close

1 · 이전 동작 → 문제 → 승인한 결과

상황이전 동작과 문제이번 결과
close 뒤에 새 요청닫혔다는 상태를 기억하지 않아 전송과 타이머 생성을 계속했습니다.call·initialize 모두 -32008로 실패하는 Promise를 반환합니다. 전송·번호 발급·타이머 생성은 없습니다.
전송 함수가 즉시 throwPromise는 원래 오류로 실패하지만 대기표와 타이머가 남았습니다.그 요청만 정리하고 -32603 / {phase: "send"}로 알립니다. 다른 요청과 연결은 유지합니다.
close를 여러 번 호출전송 장치의 정리를 반복 실행했습니다.첫 호출만 정리하고 이후 호출은 바로 끝냅니다.

사용자가 권장안을 승인한 뒤 SPEC §4.6·§4.7에 먼저 반영했습니다. ADR 0018에 오류 형태·정리 순서·재전송하지 않는 이유를 기록했습니다.

전송 실패에는 고정된 MoonpoolError를 사용합니다. 사용하는 쪽에서 브라우저마다 다른 오류 모양을 해석하지 않고 code와 data.phase로 처리할 수 있습니다. 전송 장치의 원래 오류 내용은 이 오류에 담지 않습니다.

2 · 새 요청의 입구에서 닫힘 상태를 확인합니다

let closed = false;

// At the start of request():
if (closed) {
  return Promise.reject(
    new MoonpoolError(ERROR_CODES.CONNECTION_CLOSED, 'the bridge connection is closed'),
  );
}
const id = nextId++;

closed는 “이 클라이언트를 닫았는가?”를 기억하는 값입니다. 검사 위치가 번호 발급보다 앞에 있습니다. 닫혔다면 타이머를 만들거나 전송 함수를 부르는 단계에 도달하지 않습니다.

Promise.reject()는 실패한 Promise를 반환합니다. call()이 갑자기 동기 throw 방식으로 바뀌는 것은 아닙니다. 사용하는 쪽에서는 계속 await와 try/catch로 처리할 수 있습니다. initialize도 같은 request 함수를 사용하므로 같은 규칙을 따릅니다.

이런 상태를 terminal이라고 부릅니다. 해당 클라이언트 객체는 닫힌 상태에서 다시 열리지 않는다는 뜻입니다. 호스트 전체가 고장 났다는 뜻은 아닙니다.

3 · 닫는 순서도 중요합니다

if (closed) {
  return;
}
closed = true;

const abandoned = [...pending.values()];
pending.clear();

close의 앞부분입니다. 먼저 닫힘을 기록하고 대기표 보관함을 비웁니다. 꺼내 둔 대기표의 타이머를 각각 지우고, 기다리는 호출에 -32008을 전달합니다. 그다음 수신 구독을 해제하고 전송 장치를 닫습니다.

closed = true
→
대기표 비우기
→
타이머 제거
호출 실패 처리
→
구독 해제
→
전송 장치 닫기

재진입(reentrancy)은 어떤 작업 중 호출한 다른 함수가 다시 원래 작업을 부르는 상황입니다. 예를 들어 전송 장치의 정리 함수가 client.close()를 다시 호출할 수 있습니다. 이미 closed가 true이므로 두 번째 close는 즉시 끝나고 정리가 반복되지 않습니다.

정리 함수 하나가 오류를 던져도 다른 정리 함수는 한 번 시도합니다. 대기 요청은 이미 정리됐고 연결은 닫힌 상태로 남습니다. 정리 중 오류는 두 시도 후 첫 번째 오류를 close 호출자에게 다시 던집니다. 로컬 관리 함수 close의 실패와 기능 호출 Promise의 실패를 구분한 것입니다.

let cleanupFailed = false;
let cleanupError: unknown;

JavaScript는 throw undefined도 허용합니다. 오류 값이 undefined인지로 실패 여부를 판단하면 이런 경우를 놓칩니다. 그래서 실패했는지와 무엇이 던져졌는지를 따로 기억합니다.

닫기 전에 전송 장치가 보관한 수신 callback이 뒤늦게 실행될 수도 있습니다. 수신 함수에도 closed 검사를 가장 앞에 두어, 닫힌 뒤에는 데이터 검사나 응답 처리를 시작하지 않습니다.

4 · 전송 실패는 해당 요청만 정리합니다

try {
  transport.send(frame);
} catch {
  const failed = pending.get(id);
  if (failed === undefined) {
    return;
  }
  pending.delete(id);
  clearTimeout(failed.timer);
  failed.reject(
    new MoonpoolError(ERROR_CODES.INTERNAL_ERROR, 'failed to send the bridge request', {
      phase: 'send',
    }),
  );
}

catch는 send가 즉시 던진 오류를 처리합니다. 실패한 번호의 대기표를 찾아 지우고, 그 타이머도 지운 뒤 오류를 전달합니다. 다른 번호의 대기표는 건드리지 않습니다. error라는 변수를 받지 않는 이유는 원래 오류를 읽거나 변환할 필요가 없기 때문입니다.

표시뜻
-32008 / CONNECTION_CLOSED이 클라이언트는 닫혔습니다. 같은 연결에서 새 호출을 하지 않습니다.
-32603 + data.phase = "send"클라이언트 쪽 전송 함수가 실패했습니다. 연결 전체의 종료나 원격 호스트의 건강 상태를 뜻하지 않습니다.

자동 재전송은 하지 않습니다. 전송 함수가 메시지를 전달한 뒤 오류를 던졌을 수도 있기 때문입니다. 다시 보내면 저장 같은 동작이 두 번 실행될 수 있습니다. 실패한 번호도 재사용하지 않고 다음 번호로 넘어갑니다. 이전 요청의 늦은 응답은 이미 대기표가 없어 무시됩니다.

5 · 먼저 완료된 결과가 유지됩니다

일부 전송 장치는 send 실행 중 바로 응답 callback을 부를 수 있습니다. 그래서 대기표는 send 전에 등록합니다. 응답이 먼저 도착했다면 이미 대기표를 제거하고 Promise를 완료한 상태입니다.

const failed = pending.get(id);
if (failed === undefined) {
  return;
}

이 확인이 “이미 끝난 요청을 나중 오류로 다시 처리하지 않기”를 맡습니다.

발생 순서최종 결과
send 안에서 정상 응답 → send가 throw먼저 받은 정상 결과를 유지합니다.
send 안에서 오류 응답 → send가 throw먼저 받은 호스트 오류를 유지합니다.
send 안에서 close → send가 throw연결 종료 오류 -32008을 유지합니다.
send가 throw → 나중에 응답 도착전송 실패 -32603을 유지하고 늦은 응답을 무시합니다.

전송 장치의 내부 callback이 즉시 실행돼도 공개 기능 API는 계속 Promise를 반환합니다. 브라우저 API를 커널에 추가하지 않았으므로 같은 규칙을 다른 전송 장치에도 적용할 수 있습니다.

6 · 테스트와 실제 연결로 확인했습니다

28개 테스트를 먼저 작성했습니다. 테스트 보조 코드의 타입과 mock 영향을 수정한 뒤 기존 T12 코드에서도 다시 확인했고, 24개 실패·4개 통과였습니다. 수정한 클라이언트에서는 28개 모두 통과했습니다.

닫힌 뒤의 call·initialize, 반복·재진입 close, 정리 함수의 실패, 늦은 callback, 전송 실패 뒤 다른 요청의 정상 처리, 기존 마감 시간 유지, 오류 원문 미검사, 먼저 완료된 결과 보존을 확인합니다. 실제 브라우저에서는 초기 연결·프로필·저장·조회가 정상 동작합니다.
