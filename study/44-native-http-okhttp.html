T28 · OkHttp as the Android broker's client

전용 우편실을 시험해 보니,
건물 규칙이 들어오지 않았습니다.

43번 시험에서 호스트의 전역 설정이 HttpURLConnection에 그대로 끼어드는 것을 확인했습니다. 이번에는 같은 전역 설정을 걸어 두고 OkHttp로 요청을 보냈습니다. 쿠키와 인증 처리기는 끼어들지 않았고, 재전송 문제 하나가 새로 나왔습니다.

관측 128개 · 서버 기록 140행재전송 1건 대응 필요OkHttp 5.5.1 확정 · 구현 전

1 · 무엇을 시험했나

"끼어들지 않았다"는 결과가 의미 있으려면 그 전역 설정이 실제로 켜져 있었다는 증거가 필요합니다. 그래서 같은 실행에서 같은 설정을 HttpURLConnection에도 적용해 봤습니다. 그쪽에 적용되지 않으면 검증 자체가 실패합니다.

OkHttpClient.Builder()
    .followRedirects(false)
    .followSslRedirects(false)
    .retryOnConnectionFailure(false)
    .cache(null)
    // 쿠키와 인증은 일부러 설정하지 않음. 기본값을 시험하기 위해서입니다
    .build()

2 · 전역 설정이 끼어드나

호스트가 건 전역 설정HttpURLConnectionOkHttp
CookieHandler호스트 쿠키가 서버에 도착호출 안 됨
Authenticator호스트 인증 정보가 서버에 도착호출 안 됨, 401 그대로
ResponseCache호출됨호출 안 됨
모든 인증서를 믿는 기본 TLS 설정인증서가 맞지 않는 서버에도 접속거부
ProxySelector호출됨호출됨 (Proxy.NO_PROXY면 안 됨)

쿠키와 인증은 43번에서 나온 경우를 모두 다시 시험했고, 클라이언트를 만든 뒤에 전역 설정을 걸어도 결과가 같았습니다.

TLS 줄은 뜻밖의 수확입니다. 호스트가 앱 전체의 인증서 검증을 약하게 해 두면, HttpURLConnection으로 보내는 요청도 함께 약해집니다.

전송 조건도 42번 시험의 Android 결과와 같았습니다. Set-Cookie는 한 줄씩 순서대로 보이고, 리다이렉트는 따라가지 않으며, 404와 500도 정상 결과이고, 공유 캐시가 없고, 본문이 오기 전에 헤더가 보입니다.

3 · 재전송 한 가지가 남았습니다

"SDK는 자동으로 다시 보내지 않는다"는 약속이 있습니다. 그런데 서버가 503에 Retry-After: 0을 붙이면, retryOnConnectionFailure(false)를 넣어도 OkHttp가 한 번 더 보냅니다. 소스를 보고 예상한 대로 측정에서도 POST 본문이 두 번 전송됐습니다.

상황GETPOST
대응 없음2번2번
본문을 한 번만 쓸 수 있게 표시 (isOneShot)해당 없음1번
네트워크 인터셉터로 헤더 이름 변경1번1번

GET과 POST를 모두 막는 방법은 인터셉터입니다. OkHttp가 판단하기 전에 헤더 이름을 바꾸고, 앱에 돌려줄 때 원래 이름으로 되돌리면 됩니다.

builder.addNetworkInterceptor(chain -> {
    Response response = chain.proceed(chain.request());
    String value = response.header("Retry-After");
    if (value == null) return response;
    // OkHttp가 보지 못하게 숨기되, 값은 잃지 않습니다
    return response.newBuilder()
        .removeHeader("Retry-After")
        .header("X-Moonpool-Retry-After", value)
        .build();
});

4 · 치르는 비용

항목내용
추가되는 라이브러리OkHttp, Okio, Kotlin 표준 라이브러리, AndroidX 일부
호스트 앱의 compileSdk 요구5.5.x는 37, 5.4.0은 36, 5.3.2 이하(확인한 버전)는 요구 없음
디버그 APK 크기약 2.5MB → 약 4.1MB (코드가 달라 대략적인 비교, 난독화 전)
버전 충돌앱 안에는 OkHttp가 한 버전만 들어감. 호스트가 쓰는 버전과 맞물림 (측정 전)

compileSdk 요구는 실제로 빌드를 멈췄습니다. SDK를 쓰는 호스트 개발자에게 그대로 넘어가므로 버전을 고를 때 중요합니다. 다만 낮은 버전이 같은 결과를 내는지는 아직 측정하지 않았습니다.

이름이 비슷한 세 값은 뜻이 다릅니다. OkHttp 5.5.1 패키지가 요구하는 것은 compileSdk 37과 minSdk 21이고, targetSdk 요구는 없습니다. compileSdk는 빌드할 때 쓰는 SDK 버전이라, 앱이 돌아가는 기기의 Android 버전과는 다릅니다.

5 · 결정한 것과 남은 것

항목상태이유
Android 클라이언트OkHttp로 확정 (2026.11.04)측정 범위에서 조건을 충족. HttpEngine은 API 34 이상, 또는 SDK 확장 7이 있는 Android 12 이상이고 측정하지 않음
OkHttp 버전5.5.1로 고정, T56에서 재검토측정한 버전이고 아직 실제 호스트가 없음. 올릴 때는 프로브를 다시 돌리고, 낮춰도 호스트가 깨지지 않음
ProxySelector따르기로 확정 (2026.11.04)OS 동작을 따른다는 원칙과 맞음. 호스트에는 주소의 스킴·호스트·포트만 보이고 인증 정보는 아님. 실제 프록시와 프록시 인증은 아직 측정 전

호스트가 더 높은 OkHttp를 쓰면 앱에는 그 버전이 들어갑니다. Gradle이 가장 높은 버전 하나를 고르기 때문입니다. 그래서 고정은 "최소 이 버전"에 가깝고, 이 점은 T56에서 함께 확인합니다.

이번 시험의 한계

  • 에뮬레이터 한 구성, OkHttp 한 버전, loopback의 HTTP/1.1에서만 시험했습니다.
  • HTTP/2와 421 경로, 실제 프록시, 프록시 인증, 본문 도중 실패, 요청 취소는 아직 시험하지 않았습니다.
  • 닫힌 연결 시험은 새 연결 기준입니다. 재사용 연결에서의 재전송은 확인하지 못했습니다.
  • OkHttp로 브로커를 만들 수 있다는 근거일 뿐, 브로커를 만든 것은 아닙니다.
현재 상태: 설계 방향만 확정했고 완료 수는 6 / 44 그대로입니다. OkHttp는 프로브에만 넣었고 SPEC, 프로토콜, 제품 패키지는 바꾸지 않았습니다. 시험용 키는 휴지통에 있어 직접 비워 주셔야 합니다.
