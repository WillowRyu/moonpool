프로필 담당자 다음은 저장소 담당자

T02에서는 호스트가 이름을 돌려주는 담당 함수(provider)를 연결했습니다. 이번에는 get으로 읽고, set으로 저장하고, delete로 지우는 담당자를 만들었습니다.

파일은 examples/mock-host/src/memory-storage.ts입니다. 이미 만들어 둔 StorageProvider 계약을 구현하고 mock-host에 연결했습니다. 기본 연결은 여전히 profile 권한만 부여합니다. 화면에서 저장 기능의 성공과 거절을 확인하는 단계는 다음 T04입니다.

왜 앱마다 서랍을 나눌까요? 두 앱이 모두 settings라는 키를 쓰는 것은 자연스럽습니다. 이때 다른 앱의 설정을 읽거나 덮어쓰지 못하게 앱 id를 먼저 고르고, 그 안에서 키를 찾습니다. SPEC §6.3과 ADR 0003이 정한 규칙입니다.

이번 코드에서 만나는 표현

표현뜻비유
Map키와 값을 짝지어 보관하는 자바스크립트 자료구조이름표가 달린 칸들
중첩 MapMap의 값으로 또 다른 Map을 보관하는 구조앱별 서랍 안에 키별 칸이 있음
factory새로운 저장소 객체와 그 객체가 쓸 상태를 만드는 함수새 서랍장을 만드는 작업
?.앞의 값이 null이나 undefined이면 뒤의 접근을 건너뜀서랍이 없으면 칸을 찾으러 들어가지 않음
??왼쪽 값이 null이나 undefined일 때만 오른쪽 대체값을 사용값이 없을 때만 “없음” 표를 붙임
async결과나 작업 완료를 Promise로 전달하는 함수 표시완료되면 알려 주는 접수증

1 · 바깥은 앱, 안쪽은 키

const apps = new Map<string, Map<string, StorageSetValue>>();

바깥 Map의 문자열 키는 앱 id입니다. 그 값이 안쪽 Map이고, 안쪽의 문자열 키는 앱이 지정한 저장 이름입니다. StorageSetValue는 맨 바깥 null을 제외한 JSON 저장 값을 뜻하는 기존 타입입니다.

apps
├─ com.example.alpha → Map
│  ├─ settings → "dark"
│  └─ language → "ko"
└─ com.example.beta  → Map
   └─ settings → "light"

두 settings는 다른 서랍 안에 있습니다. 앱과 키를 한 문자열로 합칠 필요가 없고, __proto__나 constructor도 Map에서는 보통의 키로 처리합니다.

createMemoryStorageProvider()가 실행될 때마다 새 apps가 만들어집니다. 반환한 get/set/delete 함수들은 자신이 만들어진 호출의 apps를 계속 사용합니다. 이를 클로저, 즉 함수가 만들어질 때의 바깥 변수를 기억하는 동작이라고 부릅니다.

2 · 처음 쓰는 앱이면 서랍부터 만듭니다

async set(miniAppId, key, value) {
  let entries = apps.get(miniAppId);
  if (entries === undefined) {
    entries = new Map<string, StorageSetValue>();
    apps.set(miniAppId, entries);
  }
  entries.set(key, value);
},

첫 줄은 앱의 서랍을 찾습니다. undefined는 아직 서랍이 없다는 뜻이므로 새 Map을 만들고 바깥 apps에 등록합니다. 마지막 줄은 그 서랍 안의 key 칸에 value를 넣습니다. 같은 앱의 같은 키에 다시 쓰면 그 값만 교체됩니다.

entries는 처음에는 Map 또는 undefined일 수 있습니다. 조건문에서 없는 경우를 처리하고 나면 TypeScript도 Map이라는 사실을 알기 때문에 as 없이 마지막 줄을 호출할 수 있습니다.

3 · 앱의 서랍에서 키를 찾고, 없으면 null

async get(miniAppId, key) {
  // ADR 0004: only absence becomes null; preserve false, 0, and "".
  return apps.get(miniAppId)?.get(key) ?? null;
},
  1. apps.get(miniAppId): 해당 앱의 서랍을 찾습니다.
  2. ?.get(key): 서랍이 있으면 그 안의 키를 찾습니다. 없으면 접근을 건너뜁니다.
  3. ?? null: 찾은 값이 없으면 명세가 정한 null을 돌려줍니다.
저장한 값?? null의 결과이유
falsefalse꺼짐이라는 실제 값
00숫자 0이라는 실제 값
""""빈 문자열이라는 실제 값
{ note: null }{ note: null }안쪽의 null은 허용된 데이터
저장한 적 없거나 삭제한 키null그 키의 값이 없음

|| null을 쓰면 false, 0, 빈 문자열까지 null로 바뀝니다. 그래서 “참처럼 보이는 값인가?” 대신 “정말 값이 없는가?”를 판단하는 ??를 사용합니다. 맨 바깥 null과 undefined 저장은 앞단의 커널 검사가 거절하므로 저장소에서 null은 부재를 뜻합니다.

4 · 선택한 앱의 선택한 칸만 지웁니다

async delete(miniAppId, key) {
  // Missing apps and keys need no mutation; other app maps stay untouched.
  apps.get(miniAppId)?.delete(key);
},

앱 A의 settings를 삭제해도 A의 language와 앱 B의 settings는 남습니다. 서랍이 없으면 ?.가 호출을 건너뛰고, 키가 없으면 Map의 delete가 아무 값도 지우지 않습니다.

get/set/delete는 모두 async입니다. 메모리 작업 자체는 빨라도 SPEC §9.5의 공통 비동기 계약을 지킵니다. set/delete는 결과 데이터 대신 작업 완료를 알려 주고, 커널이 빈 성공 결과 {}를 응답합니다.

5 · 권한과 저장소의 수명은 구분합니다

mock-host의 capabilities에 아래 줄을 연결했습니다.

// SPEC §5.1 — keep one provider for this host, across repeat handshakes.
storage: createMemoryStorageProvider(),

호스트가 시작할 때 한 번 만든 담당자를 반복 초기화에서도 그대로 사용합니다. 미니 앱의 재초기화는 같은 서랍을 유지하지만, 호스트 페이지를 새로 열거나 새 provider를 만들면 새 빈 서랍장이 생깁니다. 파일이나 영구 저장소에 기록하지 않기 때문입니다.

보안 경계: 앱 id는 미니 앱 요청에서 고르지 않고 호스트가 가진 manifest에서 가져옵니다(ADR 0003). SPEC §9.3의 권한 검사와 §9.6의 입력 검증은 커널이 담당합니다. 이 provider는 검증을 마친 입력으로 앱별 데이터를 보관합니다.

기본 연결의 grantedScopes는 ['profile']입니다. 저장소 담당자가 있어도 storage 권한이 생기는 것은 아닙니다. 허용된 저장 호출은 이번 테스트의 호스트 설정에서 검증했고, 이후 T04에서 실제 브라우저의 허용·거절 화면도 연결했습니다.

6 · 서랍이 섞이지 않는지 검증했습니다

새 테스트 18개를 먼저 작성해 실패를 확인한 뒤 구현했습니다. 직접 provider를 사용하는 테스트 15개, 실제 호스트·클라이언트를 메모리 전송으로 연결한 테스트 2개, mock-host 진입점의 설치와 기본 권한을 확인하는 테스트 1개입니다.

  • 비동기 저장·읽기·삭제와 없는 키의 null
  • false·0·빈 문자열·중첩 null 보존
  • 같은 앱의 덮어쓰기, 앱 사이 같은 키의 분리
  • 한 앱에서 삭제한 뒤 다른 앱과 다른 키의 값 보존
  • 빈 키와 특수해 보이는 키의 정상 처리
  • 새 provider는 빈 상태, 반복 초기화는 기존 데이터 유지
  • 저장소가 있어도 권한 없는 호출은 -32000이며 기존 데이터 보존
