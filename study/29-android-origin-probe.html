T23 · Android origin and local content

화면은 열렸지만,
앱 사이의 벽은 생기지 않았습니다.

실험 앱을 빌드해 Android 에뮬레이터에서 실행했습니다. 현재 요구하는 moonpool:// 주소를 직접 시험했고, 이 구성에서는 서로 다른 앱의 DOM·저장소가 분리되지 않는 문제를 확인했습니다.

T23 조사 완료 · 2 / 44실제 APK·에뮬레이터 실행운영 출처 결정은 T28

1 · 세 가지 구성을 같은 콘텐츠로 비교했습니다

구성파일 로딩앱별 출처·데이터
공식 자산 로더 + moonpool://주소를 처리하지 못해 페이지 로딩 실패페이지를 열 수 없어 관찰 불가
공개 요청 가로채기 API + moonpool://HTML·JS·CSS·이미지 표시 성공A와 B의 출처가 같고 DOM·저장소가 공유됨
공식 자산 로더 + HTTPS 대조군파일 로딩·JSON fetch 성공A/B 출처와 저장 값이 분리되고 다른 앱 DOM 접근 차단

실제 환경은 Android 17·API 37·ARM64·16KB 페이지, WebView 145.0.7632.218입니다. 이 한 구성의 측정 결과를 모든 Android 버전의 결과로 일반화하지 않습니다.

보안 명세 §8·§9와 직접 관련됩니다.
현재 요구하는 출처 규칙을 이 구성으로 구현하면 앱별 격리가 깨집니다. T23은 이 문제를 발견하고 기록하는 조사 task로 완료했습니다. 네이티브 SDK가 준비됐다는 뜻은 아닙니다.

2 · URL의 앱 이름이 다르다고 출처도 다른 것은 아닙니다

// Page A URL
moonpool://com.example.probe.a/assets/index.html
// Page B URL
moonpool://com.example.probe.b/assets/index.html

// Measured location.origin in both pages
"moonpool://"

주소에는 서로 다른 앱 이름이 있지만, 측정한 WebView는 둘을 같은 출처로 취급했습니다. 브라우저가 출처를 기준으로 만드는 DOM·저장소의 벽이 A/B 사이에 생기지 않았습니다.

// A stores its public marker first
localStorage.setItem(key, 'a');

// B reads the same key before writing its own marker
localStorage.getItem(key); // measured: "a"

B가 A의 값을 읽고 자기 값 b를 쓰면, A도 다시 읽을 때 b를 받았습니다. IndexedDB에서도 같은 충돌을 관찰했습니다. 다른 앱 프레임의 DOM도 읽을 수 있었습니다.

별도 출처의 로컬 대조 서버가 받은 요청의 Origin 헤더도 둘 다 moonpool://였습니다. 화면에서 보여주는 URL이나 게스트가 주장하는 앱 id만으로 발신 권한을 확인해서는 안 되는 이유입니다. 실제 네이티브 메시지 인증은 T25에서 별도로 검증합니다.

3 · 이번 코드는 실험용 WebView 껍데기입니다

new WebViewAssetLoader.Builder()
    .setDomain(host(app))
    .addPathHandler("/assets/", path -> asset(app, path))
    .build();

setDomain은 실험 앱의 고정 호스트를 선택하고, /assets/ 요청은 해당 앱의 번들 파일로 연결합니다. 공식 로더는 HTTP(S)를 위한 도구이므로, 같은 로더에 moonpool 주소를 넘겼을 때 실제로 처리하는지도 따로 확인했습니다.

web.evaluateJavascript(
    "JSON.stringify(window.t23Report || null)",
    raw -> { /* collect public diagnostic observations */ }
);

네이티브 실험 코드가 페이지의 공개 관찰 값을 비동기로 읽어 JSON 파일로 저장합니다. 게스트가 호출하는 네이티브 객체나 Moonpool capability를 설치하지 않았습니다. 이 수집 함수는 발신자 인증을 대신하지 않습니다.

WebView 설정과 관찰을 담당하는 작은 Android 실험 앱은 Java로 작성했습니다. 공통 TypeScript 커널의 실행 위치와 최종 호스트 기술은 T27에서 두 플랫폼의 근거를 보고 결정합니다.

4 · 차단됐다는 주장에는 정상 대조군이 필요합니다

HTTPS 대조군에서는 다른 앱의 프레임이 실제로 로드됐다는 공개 신호를 받은 다음 DOM 읽기를 시도했습니다. 이때 SecurityError가 발생했고, 같은 앱 프레임의 DOM 읽기는 성공했습니다. 단순히 프레임 로딩이 실패한 것을 격리 성공으로 세지 않았습니다.

저장·다시 읽기, 같은 앱의 두 번째 화면, 새로고침, 화면 재생성, 앱 프로세스 재시작도 비교했습니다. HTTPS에서는 앱별 값이 유지됐고, moonpool 구성에서는 공유된 값이 유지됐습니다. “값이 남는다”와 “내 앱의 값만 보인다”는 다른 검증입니다.

없는 파일·상위 경로·알 수 없는 앱은 별도로 확인하고, 명시적인 로컬 네트워크 대조군도 사용했습니다. HTTP(S) 경로의 차단 결과를 custom scheme의 fetch 성공으로 바꿔 해석하지 않습니다. custom scheme에서는 번들 JSON fetch 자체가 실패했습니다.

초기 실험 코드에는 이미지가 다 로드되기 전에 상태를 읽는 문제가 있었습니다. load/error를 기다리도록 고친 후 최종 APK로 전체 비교를 다시 수행했습니다. Android 린트의 루프백 주소 설정 오류도 수정했습니다.
