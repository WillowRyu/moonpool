T28 · Reading the first 401 through failureResponse

사라진 줄 알았던 첫 쿠키를
인증 콜백에서 찾았습니다.

45번에서 iOS는 Basic 401을 받으면 요청을 한 번 더 보내고, 브로커는 두 번째 응답의 쿠키만 읽는다는 것을 확인했습니다. 첫 응답은 응답 콜백이 아니라 인증 콜백으로 가기 때문입니다. 그 인증 콜백에서 첫 응답의 쿠키를 읽을 수 있는지 시험했더니, 읽을 수 있었습니다.

관측 22개 · 서버 기록 38행 · 검증 128건8개 Basic 사례 모두 일치브로커 적용 전
이후 변경: 이 측정 결과를 브로커에 적용했습니다. 적용 내용과 63사례 재수집은 48번에 있습니다.

1 · 왜 시험했나

서버가 시도마다 다른 쿠키를 주면, 보관함에 남는 값이 두 OS에서 달라집니다.

AndroidiOS
서버가 받은 시도1번2번
브로커가 읽는 응답첫 번째두 번째
보관함에 남는 쿠키attempt=1attempt=2

첫 시도에만 쿠키를 주는 서버라면 iOS에서는 그 쿠키가 아예 사라집니다. 인증 콜백에 첫 응답이 들어 있다면 Android와 같은 값을 쓸 수 있습니다.

2 · 판정 기준을 먼저 적었습니다

결과를 보고 기준을 맞추지 않도록, 수집 전에 "쓸 수 있다"의 뜻을 README에 적어 두었습니다. 모든 Basic 사례, 모든 수집에서 첫 인증 콜백의 failureResponse가 있고, 상태가 401이고, Set-Cookie가 서버가 첫 시도에 준 값과 같아야 합니다. 첫 시도에 쿠키가 없었다면 비어 있어야 합니다.

앱이 읽은 값은 앱의 말일 뿐이므로, 서버가 시도마다 실제로 준 값을 따로 기록해 맞춰 봤습니다.

// 앱: 두 번째 시도가 나가기 전에 실행되는 인증 콜백에서 읽습니다
func urlSession(_ session: URLSession, task: URLSessionTask, didReceive challenge: URLAuthenticationChallenge,
                completionHandler: @escaping (URLSession.AuthChallengeDisposition, URLCredential?) -> Void) {
    let first = challenge.failureResponse as? HTTPURLResponse
    record(first?.statusCode, first?.value(forHTTPHeaderField: "Set-Cookie"))
    completionHandler(.rejectProtectionSpace, nil)   // 브로커와 같은 처리
}

// 서버: 도착마다 무엇을 줬는지 남깁니다
row = {'case': case['id'], 'arrival': arrival, 'served': fields, ...}

이 실험은 브로커 프로브와 폴더를 나눴습니다. 브로커 코드를 고치면 소스 해시가 바뀌어 58사례 증거를 다시 모아야 하기 때문입니다.

4 · 고쳐지는 것과 아닌 것

브로커에 적용한다면 대략 이런 모습입니다. 아직 적용하지 않은 제안입니다.

// 인증 콜백에서 첫 응답의 쿠키를 커밋하고, 재전송 응답의 쿠키는 무시합니다
if let first = challenge.failureResponse as? HTTPURLResponse {
    commit(session, generation, include, label, url, first)   // 초기화 세대 검사도 여기서 함께 해야 합니다
    committedAtChallenge = true
}

왜 바로 적용하지 않았느냐면, 이미 받아들인 규칙인 "헤더가 전달될 때 커밋한다"를 다듬어야 하기 때문입니다. iOS의 Basic 401만 커밋 시점이 인증 콜백으로 바뀌므로 먼저 확인이 필요합니다. 적용하면 58개 사례도 양쪽에서 다시 모아야 합니다.

5 · 정한 것과 남은 것

항목상태
쉼표로 HttpOnly를 잃는 문제정함. 동작은 그대로 두고 계약서·ADR 0027·C04 절차에 적었습니다. 규칙을 어기는 서버에서만 생기고, 더 엄격한 규칙은 정상 쿠키까지 숨기기 때문입니다
failureResponse 적용결정 남음. 쓸 수 있다는 것만 확인했습니다

이번 시험의 한계

  • iOS 26.4.1 시뮬레이터 한 구성, loopback의 HTTP/1.1, Basic만 시험했습니다. Digest, NTLM, HTTP/2, 프록시는 측정하지 않았습니다.
  • SDK 헤더는 이 값이 인증 실패 응답이라고만 설명하고, 헤더 내용까지 약속하지는 않습니다. 그래서 지원하는 OS 버전마다 다시 측정해야 합니다.
  • 브로커와 쿠키 보관함 없이 세션 설정만 같게 맞춘 실험입니다. 적용 후의 동작을 시험한 것은 아닙니다.
현재 상태: 완료 수는 6 / 44 그대로입니다. 브로커, SPEC, 프로토콜은 바뀌지 않았고 이번 결과는 아직 커밋하지 않았습니다. 시험용 키는 휴지통에 있어 직접 비워 주셔야 합니다.
