T19 · Error-code mapping and producer coverage

오류 번호를 받는 일과,
그 오류를 만드는 일은 다릅니다.

명세에 있는 오류 코드 14개가 실제로 호출자까지 전달되는지 검사했습니다. 지금 구현된 발생 경로는 실제 host와 client를 연결해 확인하고, 아직 발생 기능이 없는 코드는 제어된 테스트 응답으로 받는 동작을 확인합니다.

14개 코드 검증새 테스트 54개전체 1,131개 통과

1 · 기존 동작을 한 장의 검증표로 연결했습니다

지금까지 권한, 초기화, 시간 초과 등을 task마다 검사했습니다. 이번에는 코드마다 어떤 검증이 있는지 모아 빠진 항목을 보완했습니다. 새 테스트는 기존 구현에서 통과했으므로 SDK의 실행 코드나 명세를 바꾸지 않았습니다.

확인한 것결과
14개 코드의 정상 오류 응답실제 MoonpoolError로 전달. code·message·data 보존
오류에 data가 없는 경우임의의 추가 정보를 만들지 않고 undefined 유지
종료 코드가 아닌 오류로 요청 하나가 실패해당 요청의 타이머만 정리. 다른 대기 요청은 유지
id:null 오류어느 요청인지 알 수 없으므로 기존 요청과 마감 시간을 유지
실제 host가 만드는 오류실제 client까지 연결해 검증. 내부 예외 정보는 공개하지 않음

data를 생략했을 때의 undefined는 JavaScript 오류 객체에서 읽는 값입니다. 응답 메시지에 data:undefined를 직접 넣는 것은 기존 JSON 검사에서 거절됩니다.

현재 client의 실제 코드입니다. 오류 응답이 검사를 통과하고 요청 번호가 일치한 뒤 실행합니다. 그 전에 대기 목록에서 해당 요청을 빼고 타이머를 해제합니다.

예를 들어 호스트가 -32000과 권한 정보를 보냈다면, 호출자는 catch에서 error.code와 error.data를 읽을 수 있습니다. client가 다른 번호로 바꾸거나 내부 정보를 임의로 보태지 않습니다. 이미 끝난 요청에 늦은 성공 응답이 와도 처음 결과를 바꾸지 않습니다.

4 · 테스트에서 상대역의 응답을 직접 정합니다

h.bridge.b.send({ jsonrpc: '2.0', id: 2, error: wireError });
const error = await rejected(failed.outcome);
expect(error.code).toBe(code);

이번에 추가한 실제 테스트의 일부입니다. h는 실제 client와 테스트용 상대 transport를 묶은 도구입니다. wireError에는 코드·공개 메시지·선택적인 추가 정보를 넣습니다. 상대 응답을 정해도 오류를 받아 처리하는 client는 실제 구현을 사용합니다.

코드 번호만 비교하지 않습니다. 실제 MoonpoolError인지, 메시지와 중첩된 data가 유지되는지, 다른 요청을 끝내지 않는지, 타이머가 남지 않는지, 늦은 응답이 결과를 덮어쓰지 않는지도 확인합니다. 객체를 as로 우기는 대신 instanceof로 실제 오류 종류를 검사합니다.

실제 host와 연결한 검증에서는 잘못된 이름·없는 기능·잘못된 인자·제공자 실패·권한 거절·제공자 없음과 버전 거절·초기화 전 호출을 확인했습니다. 버전을 명시적으로 바로잡거나 초기화를 마치면 이어서 정상 호출할 수 있는지도 검사합니다.

5 · 번호 없는 오류는 어느 호출을 끝내야 할까요?

id:null이면 연결할 요청 번호가 없습니다. client가 아무 요청이나 골라 거절하면 정상 요청을 잘못 끝낼 수 있습니다. 그래서 기존 요청은 계속 기다리고 원래 마감 시간을 유지합니다.

시각일어나는 일
0ms요청 시작. 이 테스트의 마감 시간은 1000ms
600msid:null 오류 도착. 요청·타이머 유지
999ms아직 대기 중
1000ms응답이 없으므로 client가 -32003 시간 초과 발생

가짜 시계를 움직여 확인하므로 실제로 1초씩 기다리지 않습니다. 오류 메시지가 왔다고 마감 시간을 다시 늘리지 않는다는 것도 이 순서로 확인합니다. 이것을 14개 코드 모두에 적용했습니다.

6 · 제공자가 던진 예외와 공개 오류 응답은 구분합니다

provider가 MoonpoolError(-32002)를 던졌다고 해서 취소 기능이 생기는 것은 아닙니다. 현재 호스트는 제공자 예외를 고정된 -32603으로 정리합니다. 원래 예외의 메시지·추가 정보는 호스트 진단에 남고 미니 앱 응답에 포함되지 않습니다.

provider 예외
내부 메시지·data
→
host
공개 가능한 실패 응답 작성
→
client
실제로 받은 -32603 보존

반대로, 상대가 실제 오류 응답으로 보낸 코드·공개 메시지·data는 client가 그대로 보존합니다. “호스트에서 공개 응답을 만드는 단계”와 “client가 받은 응답을 전달하는 단계”의 책임이 다릅니다. 기존 SPEC §4.4·§9.4의 내부 정보 보호도 이번 검증에 포함했습니다.

7 · 오류 번호가 정의돼도 기능이 자동으로 생기지 않습니다

RATE_LIMITED가 있다는 것은 나중에 호출량 제한을 알려 줄 번호가 있다는 뜻입니다. 몇 번부터 제한할지, 언제 다시 시도할지까지 정했다는 뜻은 아닙니다. 이번에는 제한기·동의창·호스트 상태 정책·문자열 transport를 추가하지 않았습니다.

현재 Transport는 이미 JSON 값인 객체 등을 받습니다. 문자열 디코더가 없는 상태에서 PARSE_ERROR 발생기를 새로 만들지 않았습니다. manifest JSON 파일 검사에서 생기는 ManifestError도 브리지 파싱 오류와는 다릅니다.

portal.close는 “닫기 요청 접수”의 성공 응답을 보냅니다. 이를 USER_CANCELLED 오류로 바꾸지 않습니다. 상대가 연결을 끊었다는 사실을 client가 감지하는 규칙도 기존 SPEC §11의 미결 사항으로 남습니다.
