T08 · Reject the array and preserve pending requests

묶음 요청은 실행 전에 거절하고,
다른 요청의 기다림은 지킵니다.

Moonpool 0.x는 여러 요청을 배열로 묶어 보내는 batch를 지원하지 않습니다. 배열 전체에 오류 하나를 보내고, 안쪽 요청을 하나도 실행하지 않도록 연결했습니다.

1 · 배열에 담긴 요청을 조용히 무시하고 있었습니다

[
  { "jsonrpc": "2.0", "id": 2, "method": "profile.get" },
  { "jsonrpc": "2.0", "id": 3, "method": "storage.get", "params": { "key": "settings" } }
]

이처럼 요청 여러 개를 한 배열에 담은 것을 batch라고 합니다. 일반 JSON-RPC에는 batch 처리가 있지만, Moonpool은 SPEC §4.1에서 0.x의 배열 요청을 -32600 Invalid Request로 거절하도록 정했습니다. T08은 이미 있던 약속을 구현합니다.

기존 호스트는 숫자 id가 있는지 먼저 확인했습니다. 배열 전체에는 id가 없으므로 응답 없이 돌아갔습니다. 이제 배열인지 먼저 확인해 거절 응답을 한 번 보냅니다.

2 · 가장 바깥 값이 배열이면 바로 거절합니다

if (Array.isArray(message)) {
  const response: JsonRpcResponse = {
    jsonrpc: '2.0',
    id: null,
    error: {
      code: ERROR_CODES.INVALID_REQUEST,
      message: 'batch requests are not supported',
    },
  };
  transport.send(response);
  return;
}

Array.isArray는 받은 값 자체가 배열인지 확인합니다. 전송하는 것은 응답 객체 하나이며, 배열 안의 요청 수만큼 응답하지 않습니다. return에서 처리가 끝나므로 요청 안의 초기화·조회·저장·삭제는 호출되지 않습니다.

이 코드는 id 확인과 초기 연결 처리보다 앞에 있습니다. 빈 배열, 요청 하나가 든 배열, 알림만 든 배열, 중첩 배열 모두 같은 규칙으로 거절합니다. 연결 전인지 연결 후인지에 따라 결과를 달리하지 않습니다.

배열 안에 portal.initialize가 있어도 초기화되지 않습니다. 이미 연결된 상태에서 잘못된 초기화가 배열에 들어와도 기존 연결 상태를 초기화하지 않습니다. 멤버를 읽어 실행하지 않는 것이 상태 보존에도 필요합니다.

3 · 배열 안의 번호를 골라 쓰지 않습니다

{
  "jsonrpc": "2.0",
  "id": null,
  "error": { "code": -32600, "message": "batch requests are not supported" }
}

배열 전체에는 하나의 요청 번호가 없습니다. 안쪽의 id 2나 3을 골라 오류를 보내면, 클라이언트가 그 번호로 기다리던 다른 호출을 잘못 끝낼 수 있습니다. 그래서 특정 요청을 식별할 수 없다는 뜻으로 id에 null을 씁니다. JSON-RPC 2.0 §5의 응답 규칙에 있는 표현입니다.

export type JsonRpcResponse = {
  jsonrpc: '2.0';
  id: number | null;
  result?: JsonValue;
  error?: { code: number; message: string; data?: JsonValue };
};

공유 응답 타입도 null을 표현하도록 바꿨습니다. 실제 응답 검사에서는 null id를 오류에만 허용하며, null id를 가진 성공 응답은 거절합니다. 정상 Moonpool 요청의 id는 계속 양의 정수입니다. 응답의 null 때문에 요청의 null id까지 유효해지지는 않습니다.

여기서 null은 응답 번호에 관한 표기입니다. storage.get의 값이 없음을 나타내는 value: null과는 서로 다른 항목입니다.

4 · 번호 없는 오류가 다른 요청을 끝내지 않게 합니다

if (!isJsonRpcResponse(message)) {
  return;
}

if (message.id === null) {
  return;
}

const entry = pending.get(message.id);

응답 형태가 맞아도 id가 null이면 기다리는 요청을 찾지 않습니다. pending은 숫자 id를 키로 쓰는 Map입니다. 위에서 돌아가므로 요청을 지우거나 타이머를 끄는 아래쪽 코드도 실행되지 않습니다.

번호가 맞는 응답이 나중에 오면 정상적으로 완료합니다. 끝내 오지 않으면 원래 켜 둔 타이머가 -32003 TIMEOUT으로 끝냅니다. null 오류에 답장을 보내지도 않으므로 오류 응답끼리 오가는 루프도 만들지 않습니다.

5 · 배열이 놓인 위치에 따라 규칙이 다릅니다

입력 형태처리
메시지 전체가 [] 또는 [요청, 요청]T08: -32600 응답 객체 하나
메시지 전체가 [알림]T08: 최상위 배열이므로 동일하게 거절
일반 객체의 알림, id 없음기존 규칙: 응답 없음
storage.set의 params.value가 [null, false, 0, ""]기존 스키마에 따라 정상 저장 가능
params 자체가 배열기존 규칙: -32602 Invalid Params

SPEC §9의 보안 경계를 유지합니다. 거절한 묶음은 provider까지 도달하지 않습니다. 일반 요청에는 기존 §9.3 권한 검사와 §9.6 입력 검사를 계속 적용합니다. 커널에는 플랫폼 API나 새 런타임 의존성을 추가하지 않았습니다.

이 단계가 모든 응답 검증을 끝낸 것은 아닙니다. 일반 응답 검증의 보강은 T12, 요청 번호 재사용과 순서 정책은 T10에 남아 있습니다. 이번 선택은 ADR 0013에 기록했습니다.

6 · 호스트와 클라이언트 양쪽에서 확인합니다
