① 계층화 — 프로토콜은 왜 화면 크기를 모르는가

계층화(layering) — 시스템을 여러 층으로 쌓되, 각 층은 자기 일만 알고 다른 층의 사정을 모르게 만드는 설계 방법. 층과 층 사이에는 약속된 접점(인터페이스)만 존재한다.

우편 시스템으로 비유하면

우편Moonpool이 층이 아는 것
편지 내용미니앱 코드"프로필 보여줘" 같은 의도
봉투 규격과 주소 쓰는 법JSON-RPC 프로토콜 (SPEC §4~§5)메시지의 모양, 인사 절차, 에러 코드
트럭 · 비행기 · 배Transport (iframe, WKWebView, …)바이트를 실제로 옮기는 방법

트럭 기사는 편지 내용을 읽지 않고, 편지 쓰는 사람은 트럭 노선을 모릅니다. 그런데도 전체 시스템은 완벽하게 동작하죠. 인터넷도 똑같이 만들어져 있어요 — HTTP는 당신이 WiFi인지 LTE인지 모르고, 그래서 HTTP가 설계될 때 존재하지도 않았던 스마트폰에서도 웹이 그대로 동작합니다.

이 설계가 주는 것

1. 이식성. 커널이 플랫폼을 모르므로, iOS/Android 지원은 "Transport 한 층만 새로 쓰기"가 됩니다. CLAUDE.md의 불변 규칙 "Kernel is pure, transport is swappable"이 바로 이것.

2. 테스트 가능성. 진짜 iframe 없이 가짜 Transport(우리의 "가짜 전화선")만 꽂으면 커널 전체를 테스트할 수 있어요. STEP 2에서 만들 바로 그것.

3. 비전 변경에도 코드가 살아남음. "풀스크린 앱 → 임베디드 컴포넌트도 포함"은 맨 아래 층(호스트 앱 UI)의 이야기라서, 위 네 층(핸드셰이크 테스트 포함)은 한 글자도 안 바뀝니다. 만약 프로토콜에 화면 크기 개념이 박혀 있었다면, 새로운 임베딩 방식이 나올 때마다 프로토콜이 깨지고 — §10에 따라 배포된 모든 미니앱이 깨졌을 거예요.

기억할 한 줄 — "아래층은 위층의 사정을 모른다." packages/protocol·client·host에 플랫폼 API import 금지 규칙은 이 원칙을 강제로 지키게 하는 장치다.

② Ionic Portals는 임베디드 컴포넌트를 어떻게 다루나

Ionic Portals — 네이티브 앱 안에 웹 미니앱을 심는 상용 런타임. Moonpool은 이 제품의 격리 모델을 오픈소스(MIT)로 다시 만드는 프로젝트다 (CLAUDE.md 첫 문단).

핵심 아이디어: Portal은 "화면 부품"이다

Portals에서 Portal은 특별한 전체 화면이 아니라 네이티브 UI 부품(뷰)이에요. 버튼이나 이미지 놓듯 레이아웃에 배치합니다 — iOS에선 PortalView(SwiftUI), Android에선 PortalView/Fragment, React Native에선 <PortalView> 컴포넌트. 화면 전체를 채우면 "미니앱"처럼 보이고, 한 구석에 놓으면 "웹 컴포넌트"처럼 보일 뿐, 런타임 입장에선 둘이 같은 물건입니다.

화면 전체 = 미니앱처럼

님이 말한 "네이티브 앱이랑 연결되는 컴포넌트"가 정확히 오른쪽 그림이고, 업계에서 이미 검증된 사용 방식이라는 뜻이에요. Moonpool의 Portal 정의(SPEC §2)도 같은 모델을 따릅니다.

통신은 어떻게?

Portals는 웹↔네이티브 사이에 pub/sub 메시지(주제를 정해 발행하고 구독하는 방식)와 플러그인 호출을 씁니다. Moonpool은 여기를 공개 문서화된 JSON-RPC + scope 권한 모델로 바꾸는 게 차별점이에요:

Ionic PortalsMoonpool
라이선스상용 제품MIT 오픈소스
메시지 규칙제품 내부 구현SPEC.md에 공개된 JSON-RPC 2.0
권한플러그인 구성에 따름메서드 이름 = 권한 scope, 디스패치 시점 강제 (§9.3)
라이브 업데이트 등제품 기능v0 범위 밖 (의도적으로 제외)

주의: Portals 제품 세부(API 이름, 가격 정책)는 제 학습 데이터(2026년 1월) 기준이라 바뀌었을 수 있어요. 다만 "Portal = 배치 가능한 뷰"라는 구조 모델 자체는 안정적인 사실입니다.

③ Origin 격리 — 작은 컴포넌트에도 똑같이 적용되는 이유

origin(오리진) — 웹에서 "이 코드가 어느 사이트 소속인가"를 가리는 신원 단위. 주소의 앞부분, 즉 방식 + 도메인(+포트)이다. 예: https://example.com과 https://shop.example.com은 서로 다른 origin.
동일 출처 정책(Same-Origin Policy) — 브라우저에 내장된 기본 보안 규칙. "같은 origin의 코드끼리만 서로의 데이터(저장소·쿠키·화면 내용)를 만질 수 있다." 아파트로 치면 호실마다 다른 열쇠 — 옆집 문은 브라우저가 원천적으로 안 열어준다.

Moonpool이 하는 일: 미니앱마다 '호실'을 배정

SPEC §8은 모든 Portal을 moonpool://<미니앱-id>/라는 자기만의 origin에서 로드하라고 요구합니다. 그 순간부터 벽을 쌓는 건 우리 코드가 아니라 브라우저 엔진이에요 — 20년 넘게 두들겨 맞으며 단단해진 보안 장치를 공짜로 물려받는 겁니다. 스펙이 이걸 "load-bearing"(구조를 떠받치는 벽)이라고 부르는 이유죠.

차트 위젯

moonpool://com.example.chart/
📦 자기만의 localStorage
📦 자기만의 IndexedDB
브라우저가 강제하는 벽

결제 위젯

moonpool://com.example.pay/
📦 자기만의 localStorage
📦 자기만의 IndexedDB

작은 컴포넌트라서 달라지는 건 없습니다. 위 그림의 두 위젯이 같은 네이티브 화면에 나란히 떠 있어도, 브라우저 눈에는 서로 다른 "사이트"라서 상대 데이터를 읽을 수 없어요. 격리는 화면 배치가 아니라 origin이 결정합니다. 덤으로 origin은 미니앱 버전이 바뀌어도 동일하므로 저장 데이터가 업데이트에서 살아남고 — 그래서 스킴 변경이 "배포된 모든 미니앱을 깨는" 파괴적 변경(§8)인 거예요.

왜 file://은 금지인가 — file://로 열면 제대로 된 origin이 없어서(신원 없음) 저장소·쿠키·CORS가 이상하게 동작하고, 격리의 근거 자체가 사라진다. §8이 커스텀 스킴 핸들러를 MUST로 못 박은 이유.

오늘 질문과의 연결 — 임의 URL은 왜 안 되나

https://아무사이트.com을 웹뷰에 띄우는 것 자체는 자유지만, 거기에 Moonpool 브릿지를 꽂으면 안 되는 이유가 정확히 이 신원 문제다:

① 그 origin은 우리가 발급한 게 아니라서 manifest도, id도, grantedScopes의 근거도 없다.
② 그 페이지가 로드하는 광고·제3자 스크립트도 같은 페이지 = 같은 권한으로 브릿지를 부를 수 있다.
③ 페이지는 링크 한 번으로 딴 곳으로 이동한다 — 그래서 §9.2가 "자기 origin을 벗어나면 브릿지를 철거하라(MUST)"고 요구한다.

표시만 할 외부 콘텐츠는 일반 웹뷰나 시스템 브라우저로. 메시지가 꼭 필요한 특정 파트너가 생기면, 그건 만능 브릿지가 아니라 좁게 계약된 별도 통로로 푸는 주제다(v0 범위 밖).
