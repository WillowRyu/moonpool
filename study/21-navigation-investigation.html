T17 · Observe actual navigation before designing containment

메시지의 출처는 확인할 수 있지만,
iframe의 현재 주소는 바로 알 수 없습니다.

이번에는 보호 코드를 먼저 붙이지 않고 실제 브라우저에서 조사했습니다. 외부 페이지의 호출 차단과, 외부로 나갔을 때 이전 연결을 영구히 끝내는 일은 별개의 요구입니다.

T17 조사 완료995 / 995 기존 테스트 통과다음 T18 · 결정안 승인 후 구현

1 · 무엇을 확인했나요?

실험관찰 결과
같은 출처 내부 이동·새로고침반복 초기화와 프로필 조회가 정상 동작합니다.
외부 출처에서 기능 호출현재 origin 검사가 차단합니다.
외부를 거쳐 원래 출처로 복귀초기화하지 않아도 이전 연결로 기능을 호출했습니다.
매번 load에서 연결 종료정상 내부 이동도 끊고, load 전에 실행한 호출은 막지 못했습니다.
부모 CSP로 허용 출처 제한직접 이동·조용한 왕복·폼 제출·리다이렉트의 외부 로딩을 차단했습니다.

측정 브라우저는 사용자 에이전트에 Chrome 155.0.0.0을 보고한 앱 내 브라우저입니다. 다른 브라우저·모든 URL 형식을 검증했다는 뜻은 아닙니다. 영문 조사 보고서에 실제 기록과 관찰 범위를 연결했습니다.

이번 task는 SPEC §9.2의 보안 요구와 직접 관련됩니다. 조사용 페이지와 결정안을 추가했으며, 제품의 이동 방어 코드나 규범 명세는 아직 바꾸지 않았습니다.

2 · 현재 검사는 외부 페이지의 호출을 막습니다

if (event.origin !== peer.origin) {
  return false;
}
return event.source !== null && event.source === peer.window;

실제 isFromPeer의 핵심입니다. origin은 프로토콜·호스트 이름·포트로 정해지는 출처이고, source는 메시지를 보낸 창을 가리킵니다. 출처와 창을 둘 다 확인합니다.

실험에서는 호스트 5273, 허용된 미니 앱 5274, 외부 페이지 5275 포트를 사용했습니다. 외부 페이지가 보내는 메시지는 source가 같은 창이어도 origin이 달라 기능에 도달하지 않았습니다. 호스트가 허용 origin을 지정해 보내는 메시지도 외부 페이지에는 전달되지 않았습니다.

문제는 원래 출처로 돌아온 다음입니다. 그때는 출처가 다시 맞고 창의 바깥 참조도 같았습니다. 기존 연결이 닫히지 않아 초기화 없이 id 100으로 보낸 profile.get이 실행됐습니다. 이것이 “출처 검사 통과 여부”와 “연결 수명 종료”를 구분해야 하는 이유입니다.

3 · src와 contentWindow는 현재 주소 증명이 아닙니다

iframe.getAttribute('src');
iframe.contentWindow === originalWindow;
iframe.contentWindow.location.href;
읽는 것실제 관찰의미
src 속성자식이 이동해도 처음 지정한 주소 그대로현재 문서 주소를 뜻하지 않습니다.
contentWindow 참조 비교외부 이동·복귀 뒤에도 true문서가 바뀌어도 같은 WindowProxy를 사용합니다.
location.href 읽기허용 페이지·외부 페이지 모두 SecurityError둘 다 부모와 다른 origin이므로 구분할 수 없습니다.
contentDocument / 자식 Navigation APInull / SecurityError부모가 자식의 문서나 이동 API를 자유롭게 관찰할 수 없습니다.

WindowProxy는 안쪽 문서가 바뀌어도 유지되는 창의 바깥 참조라고 이해하면 됩니다. 실제로 참조하는 Window·Document는 바뀔 수 있습니다. HTML의 iframe 규칙과 WindowProxy 설명도 이 점을 명시합니다.

따라서 location을 읽다가 오류가 나면 외부 이동이라고 판단하는 코드를 만들면, 정상 미니 앱도 외부로 판단하게 됩니다. 호스트와 미니 앱은 원래 다른 origin이어야 한다는 SPEC §8.1 때문입니다.

4 · load는 이동 시작 알림이 아닙니다

let loads = 0;
iframe.addEventListener('load', () => {
  loads += 1;
  if (loads > 1) {
    transport.close();
  }
});

첫 load는 허용하고 그다음 load부터 닫는 후보를 실험했습니다. 정상적인 같은 출처 이동에서도 연결이 끊겨 새 초기화가 시간 초과됐습니다. 더구나 외부 문서가 느린 이미지를 요청한 뒤 load 전에 원래 출처로 돌아오면 외부 문서의 load 자체를 관찰하지 못했습니다.

이 시간은 한 번의 실험에서 기록한 값입니다. 실제 안전한 시간 간격을 뜻하지 않습니다. 실험의 5초 이미지 지연은 순서를 드러내기 위한 장치입니다. 기능이 이미 실행된 후 연결을 닫았다는 사실이 핵심입니다.

일반 페이지에서는 load가 초기화 메시지 전달보다 먼저 나타나기도 했습니다. “load는 항상 먼저”나 “항상 나중”이라고 일반화하면 안 됩니다. hash 이동에서는 load 횟수가 늘지 않는 것도 확인했습니다.

5 · 외부 로딩을 브라우저가 막게 할 수는 있었습니다

Content-Security-Policy: frame-src http://127.0.0.1:5274

CSP는 페이지를 제공하는 쪽이 브라우저에 주는 허용 규칙입니다. 이 실험에서는 부모 문서의 frame-src에 미니 앱 출처 하나만 허용했습니다. CSP frame-src 규칙은 중첩 문서 로딩을 제한합니다.

직접 외부 이동, 폼 제출, 허용 URL의 외부 리다이렉트, 조용한 외부 왕복이 모두 차단됐고 frame-src 위반 이벤트가 나타났습니다. 허용된 출처의 내부 이동과 새로고침은 계속 동작했습니다.

현재 실험과 앞으로의 구현을 구분합니다.
실험용 CSP 페이지는 위반을 기록하기만 합니다. 위반을 받으면 실제 연결과 iframe을 폐기하는 코드는 T18에서 구현해야 합니다. CSP로 현재 주소를 읽을 수 있게 된 것은 아닙니다.

ADR 0022의 권장안은 개발용 호스트를 한 문서당 Portal 하나·허용 미니 앱 출처 하나로 제한하고, CSP 차단 뒤 연결을 영구 폐기하는 계약입니다. 사용자가 호스트에서 새 Portal을 만드는 것은 허용하되, 원래 출처로 돌아왔다는 이유만으로 이전 연결을 살리지 않습니다.

여러 앱 출처를 하나의 frame-src 목록에 넣으면 한 iframe도 그 목록의 다른 출처를 로드할 수 있어, 같은 보장을 주장할 수 없습니다. 이 단순한 개발용 계약에는 그 구성이 포함되지 않습니다. 운영 환경의 요구와 일반적인 URL 감지 기능을 해결했다고 주장하지 않습니다.

대안은 지금의 일반 명세를 유지하고 브라우저의 완전한 이동 방어 완료 판단을 보류하는 것입니다. 이번 결과를 구현에 맞춰 명세를 조용히 낮추지 않고, 지원 범위와 제약을 확인받을 결정안으로 남겼습니다.

6 · 다시 실행할 수 있도록 실험과 기록을 남겼습니다

pnpm --filter moonpool-example-mock-host exec node navigation-lab/serve.mjs

저장소 루트에서 실행하고 http://127.0.0.1:5273/host.html을 엽니다. CSP 비교는 host-csp.html입니다. 재현 안내와 시나리오별 기록을 참고하세요. 일반 예제의 5173·5174 포트와 분리했습니다.

초기 실행에 추가 로딩이 관찰돼 그 기록을 제외했습니다. 개발 서버의 영향을 줄이도록 HMR·파일 감시·의존성 자동 탐색을 끈 뒤 다시 기록했습니다. 서버 재시작도 페이지를 다시 로드할 수 있으므로 측정 중에는 재시작하지 않습니다.
