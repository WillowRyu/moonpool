T14 · Accept a dismissal request, then invoke the embedder

미니 앱은 닫기를 요청하고,
호스트가 그 화면을 닫습니다.

미니 앱은 자신을 담은 바깥 화면을 직접 지우지 않습니다. portal.close를 보내면 호스트가 입력을 확인하고, 해당 Portal에 연결해 둔 담당 함수를 실행합니다.

호출역할담당
client.close()로컬 통신을 끝내고 기다리는 요청을 정리합니다.클라이언트 라이브러리 · T13

이전에는 portal.close라는 이름이 명세에만 있고 구현이 없어, 초기화 후 호출해도 -32601로 끝났습니다. 이번에는 실제 닫기 요청을 전달합니다.

화면을 먼저 없애면 답장을 받을 미니 앱도 사라질 수 있습니다. 사용자가 승인한 규칙은 접수 응답을 먼저 전송하고 닫기 함수를 실행하는 것입니다. 성공 {}는 닫기 완료가 아니라 요청 접수를 뜻합니다. SPEC §6.2를 먼저 갱신했고 ADR 0019에 결정과 한계를 기록했습니다.

2 · reason은 생략하거나 문자열로 전달합니다

if (rejectUnknownParams(id, params, ['reason'])) {
  return;
}
const reason = params?.reason;
if (reason !== undefined && typeof reason !== 'string') {
  // Reply with INVALID_PARAMS (-32602).
  return;
}

호스트 분기의 핵심을 발췌했습니다. reason 이외의 인자는 먼저 거절하고, reason이 있다면 실제로 문자열인지 확인합니다. 이 단계 전에 T11의 JSON 검사를 통과했으므로 직접 넣은 undefined도 허용되지 않습니다. 생략한 reason과 구분합니다.

인자결과
생략 / {} / {reason: "finished"} / {reason: ""}유효합니다. 공백이나 문자열 내용을 바꾸지 않습니다.
{reason: 42} / {reason: null} / {portalId: "other"}-32602 · 화면 담당 함수를 호출하지 않습니다.
유효한 인자지만 담당 함수가 없음-32001 · 이 호스트에서 사용할 수 없습니다.

초기화 전에는 기존처럼 -32005입니다. portal은 별도 scope가 필요 없는 예약 이름이므로 profile·storage 권한 없이도 닫기를 요청할 수 있습니다. 다른 Portal을 고르는 id는 인자로 받지 않습니다.

export interface HostConnectionOptions {
  onCloseRequested?: (reason?: string) => Promise<void>;
}

hook은 라이브러리가 특정 순간에 호출할 수 있도록 호스트가 연결해 둔 함수입니다. 이름은 “닫기 요청이 들어오면”이라는 뜻입니다. 각 connect에 따로 전달하므로 하나의 호스트를 여러 연결에 사용해도 닫을 화면을 구분할 수 있습니다.

3 · 두 줄의 순서가 계약입니다

transport.send({ jsonrpc: '2.0', id, result: {} });
void invokeCloseRequested(handler, reason);
portal.close 수신
→
기존 요청·초기화 검사
→
reason·담당 함수 확인
→
접수 응답 전송
→
닫기 함수 실행

첫 줄의 전송이 실패해 예외를 던지면 두 번째 줄로 진행하지 않습니다. 두 번째 답장을 보내지도 않습니다. void는 비동기 보조 함수의 반환 Promise를 이 위치에서 사용하지 않는다는 표시입니다. 함수 안에서는 await로 담당 함수의 실패를 처리합니다.

try {
  await handler(reason);
} catch (error) {
  queueMicrotask(() => {
    throw error;
  });
}

이미 접수 응답을 보냈으므로 이후 화면 담당 함수가 실패해도 새 오류 응답으로 덮어쓰지 않습니다. 기존 호스트 오류 보고 방식으로 호스트 쪽에만 드러냅니다. 미니 앱에 호스트의 오류 원문·내부 정보가 넘어가지 않습니다.

전송과 수신은 다릅니다.
현재 Transport.send는 상대가 읽었다는 확인을 돌려주지 않습니다. 이 코드는 응답을 전송한 뒤 닫기를 시작한다는 순서만 보장합니다. 미니 앱의 await가 끝나기 전에 화면이 없어질 수도 있습니다. 성공 응답을 실제 닫기 완료나 수신 확인으로 해석하면 안 됩니다.

4 · iframe을 지우는 코드는 예제 호스트에 있습니다

async onCloseRequested(reason) {
  if (activeTransport !== transport || iframe.parentElement !== portal) {
    return;
  }
  activeTransport = undefined;
  transport.close();
  iframe.remove();
  // Update the host's status text and configuration buttons.
}

예제의 실제 닫기 함수 앞부분입니다. 지금 사용 중인 연결과 이 함수가 기억하는 연결이 같은지 확인합니다. iframe도 원래 자리에 있어야 합니다. 이전 화면의 함수가 뒤늦게 실행되면 바로 끝내므로 새 화면을 닫지 않습니다.

activeTransport를 먼저 비워 두어 같은 함수가 다시 호출돼도 정리를 반복하지 않습니다. 그다음 연결을 닫고, 이 함수가 기억한 iframe만 제거합니다. 저장 데이터는 호스트 페이지의 저장소에 남아 새 Portal에서도 읽을 수 있습니다.

이 DOM 코드는 examples/mock-host에만 있습니다. 순수 커널은 iframe이나 window를 모르고, 연결해 둔 비동기 함수만 호출합니다. SPEC §9.4·§9.5·§9.6에 따라 호스트 오류 정보는 로컬에 두고, 함수는 비동기로 제공하며, 입력 검사를 먼저 합니다. reason을 화면에 표시할 때도 textContent를 사용합니다.

5 · 미니 앱 버튼은 요청 한 줄을 보냅니다

await client.call(PORTAL_METHODS.CLOSE, { reason: 'finished' });

새 close-demo.ts의 핵심입니다. 초기화 전에는 버튼을 비활성화하고, 기다리는 동안에도 중복 클릭을 막습니다. 응답을 받으면 “Close request accepted”라고 표시합니다. 이미 화면이 제거됐다면 이 표시를 볼 수 없는 것이 승인한 계약의 한계입니다.

담당 함수 없음 같은 오류 응답을 받으면 오류 코드를 보여 주고 사용자가 직접 다시 시도할 수 있도록 합니다. 자동 재전송은 하지 않습니다. 호스트 페이지에서는 Portal이 사라진 뒤 구성 버튼으로 새 화면을 열 수 있습니다.

6 · 테스트와 실제 닫기 동작을 확인했습니다

새 테스트는 47개입니다. 호스트 테스트는 기존 검사 8개부터 시작했고, 확장한 34개 중 구현 전 20개 실패·14개 통과를 확인했습니다. UI는 새 모듈이 없어 불러오지 못한 테스트와 버튼·호스트 연결이 없어 실패한 동작 검사를 먼저 작성했습니다. 기존 초기화 테스트 두 곳도 닫기 버튼 상태를 확인하도록 강화했습니다.

검증 대상은 인자와 담당 함수의 검사 순서, 권한 없이 요청하기, 접수 후 함수 실행, 호스트 오류 정보 보호, 연결별 함수 분리, 이전 함수의 새 화면 보호, 반복 닫기, 새 Portal의 저장 데이터 유지입니다.

실제 브라우저에서는 profile-only 구성에서 닫기 → storage 구성으로 다시 열기 → "dark" 저장 → 닫기 → 다시 열고 "dark" 조회 → 닫기까지 확인했습니다. 이는 화면 동작 검증이며 응답의 실제 수신 보장을 뜻하지 않습니다.
