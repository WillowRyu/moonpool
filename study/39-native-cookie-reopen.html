T28 · iOS partition and writer evidence

앱을 다시 켜면,
빈 목록이 거짓일 수 있습니다.

iOS 쿠키의 남은 질문 두 가지를 측정하다가 더 중요한 문제를 찾았습니다. 새로 시작한 앱에서 처음 묻는 쿠키 목록은, 쿠키가 있어도 비어 있다고 답했습니다.

서버 기록 497행 · 검사 524개시뮬레이터 iOS 26.4.1실기기·다른 버전은 미확인

1 · 목록은 비었는데, 서버에는 쿠키가 도착했습니다

지금까지 세운 기준은 "쿠키가 없을 때만 미니 앱을 연다"입니다. iOS에서는 쿠키 차단을 켜도 이미 있던 쿠키가 계속 전송되기 때문입니다. 그래서 getAllCookies가 돌려주는 목록을 믿고 판단합니다.

창고에 비유하면 이렇습니다. 문을 막 연 창고에 "물건 있어요?"라고 물었더니, 직원이 아직 장부를 꺼내 오지 않은 채 "없어요"라고 답합니다. 실제 선반에는 물건이 있습니다.

같은 저장소를 본 방법결과
쿠키를 쓴 앱이 켜져 있을 때 목록 조회쿠키 있음
앱을 다시 켜고 처음 목록 조회빈 목록
바로 이어서 페이지 요청, 서버가 받은 헤더쿠키 있음
그 뒤 다시 목록 조회쿠키 있음

이렇게 쿠키가 있는데 없다고 답하는 것을 이 문서에서는 거짓 빈 결과(false empty)라고 부릅니다. 목록만 믿는 검사는 쿠키가 있는 저장소에 미니 앱을 열어 줍니다. 이 기준이 막으려던 바로 그 상황입니다.

앞선 검증은 왜 놓쳤을까요? 저장소를 "다시 열기"는 했지만 같은 프로세스 안에서였고, 그 전에 정책도 이미 설정한 상태였습니다. 앱을 새로 시작한 경우는 시험한 적이 없었습니다.

2 · 목록 조회 전에 무엇을 했는지가 결과를 바꿨습니다

// 위험한 순서: 새 프로세스에서 매번 거짓 빈 결과
let store = WKWebsiteDataStore(forIdentifier: id)
let cookies = await inventory(store)   // []

// 측정한 순서: 16개 저장소 모두 실제 쿠키 2개를 돌려줌
let store = WKWebsiteDataStore(forIdentifier: id)
await policy(store, false)             // 쿠키 차단 설정 완료까지 대기
let cookies = await inventory(store)   // 쿠키 2개
첫 조회 전에 한 일저장소 수거짓 빈 결과
아무것도 안 함2020
아무것도 안 하고 곧바로 두 번 조회1616 (두 번 다 비어 있음)
기다리기 (0.5초 뒤 조회부터 정상)22 (첫 조회 기준)
쿠키 정책 설정160

다행히 이미 채택한 검사 순서가 "정책 적용 완료 → 전체 조회"이고, 이 순서는 모두 맞게 답했습니다. 하지만 이것을 해결책으로 부르면 안 됩니다. Apple이 문서로 보장한 동작이 아니고, 원인도 아직 모릅니다. 조회를 두 번 해도 계속 비어 있었으니, 단순히 "호출을 한 번 더 왕복하면 된다"는 설명으로도 부족합니다.

채택한 규칙 (2026.11.03 · 설계 방향): 정책 완료 뒤의 조회만 증거로 인정합니다. fetchDataRecords와 getAllCookies가 모두 "쿠키 없음"이라고 답해야 비어 있다고 판단하고, 어긋나면 "확인 불가"로 보고 열지 않습니다. iOS 버전마다 이 시험을 다시 돌려 지원 범위를 정합니다. 명세 변경이나 구현은 아니며, 위험을 좁히는 조건일 뿐 원인을 고친 것도 아닙니다.

3 · 파티션 쿠키는 실제로 분리되고, 목록에도 나옵니다

파티션 쿠키(Partitioned cookie)는 같은 서비스의 쿠키라도 "어느 사이트 안에 끼워졌는지"에 따라 칸을 나눠 보관하는 쿠키입니다. 같은 회사의 지점이어도 건물마다 사물함이 따로 있는 것과 비슷합니다.

이전에는 iOS가 Partitioned 표시를 그냥 무시하는지조차 구분하지 못했습니다. 이번에는 다른 사이트 안에 iframe으로 끼워 넣어 직접 비교했습니다.

쿠키를 쓴 위치같은 위치에서 전송다른 사이트 안에서단독 방문 시목록에 나옴
다른 사이트 안 iframe · 헤더 · Partitioned예아니요아니요예
moonpool:// 페이지 안 iframe · 헤더 · Partitioned예아니요아니요예
다른 사이트 안 iframe · 헤더 · 표시 없음저장되지 않음아니요
다른 사이트 안 iframe · 스크립트로 쓰기오류 없이 저장되지 않음아니요

즉 앱이 실행 중일 때는 파티션 쿠키도 목록이 찾아냅니다. 다만 목록 항목에는 "어느 사이트 칸인지"가 나오지 않습니다. 있는지 없는지만 보는 지금 기준에는 충분하지만, 나중에 쿠키 복구 기능을 만든다면 문제가 될 수 있습니다.

4 · 검사 직후에 쿠키가 생기면 소용없습니다

"비어 있다"를 확인한 바로 다음 순간 쿠키가 생기면 검사가 무의미합니다. 이런 순서 싸움을 경쟁 상태(race)라고 합니다. 실험 서버가 Set-Cookie 응답을 일부러 붙잡아 두고, 목록이 빈 것을 확인한 뒤에 풀어 주었습니다.

쿠키를 쓰는 쪽먼저 한 조치결과
붙잡아 둔 페이지·fetch 응답없음 (대조군)쿠키가 생김 · 경쟁 상태는 실제로 있음
붙잡아 둔 페이지·fetch 응답차단 정책 완료 대기응답은 도착, 쿠키는 안 생김
붙잡아 둔 페이지 응답화면 폐기연결이 닫힘, 쿠키는 안 생김
쉬지 않고 쓰는 스크립트차단 정책 완료 대기이후 84–89회 더 시도, 쿠키는 안 늘어남
네이티브 setCookie차단 정책 켠 상태저장되고 전송됨
같은 ID로 저장소 객체를 하나 더 생성정책 변경같은 객체 · 정책과 쿠키를 공유

웹 콘텐츠 쪽은 시험한 경우에 한해 차단 정책으로 막혔습니다. 하지만 정책은 네이티브 코드를 막지 못하고, 저장소 ID를 아는 앱 내부 코드는 누구나 정책을 바꿀 수 있습니다. 그래서 이 부분은 플랫폼이 아니라 SDK가 책임져야 합니다. 네이티브 쿠키 쓰기를 검사와 겹치지 않게 줄 세우고, 저장소 ID는 밖으로 내주지 않아야 합니다.

5 · 왜 이 결과를 믿을 수 있나요

목록이 맞는지를 목록 자신에게 물을 수는 없습니다. 그래서 별도의 증인을 두었습니다. 우리가 띄운 HTTPS 서버가 실제로 받은 Cookie 헤더입니다.

# verify_results.py의 판정 핵심
witnessed = server_witness or script_witness   # 서버나 스크립트가 쿠키를 봤는가
inventoried = name in inventory                # 목록에 나왔는가
false_empty = witnessed and not inventoried    # 봤는데 목록에 없다 = 거짓 빈 결과
  • 대조군: 빈 저장소는 계속 비어야 하고, 네트워크 로드 뒤에는 목록이 완전해야 합니다. 이 조건이 깨지면 검증기가 결과를 거부합니다.
  • 순서 효과 제거: 처음에는 전략마다 저장소가 하나뿐이고 순서도 고정이라 우연일 수 있었습니다. 그래서 8개씩 번갈아 배치해 두 번 반복했습니다.
  • "안 생겼다"의 조건: 응답이 실제로 페이지까지 도착했다는 확인이 있어야 인정합니다. 첫 수집에는 이 확인이 없어서 다시 수집했습니다.

결과를 본 뒤 고친 판단도 두 가지 있습니다. 전략 실험을 추가했고, "재시작 직후 목록에 나와야 한다"고 잘못 적은 대조군을 고쳤습니다. 둘 다 실험 README와 보고서에 그대로 남겼습니다.
