어떤 문제를 막고 있나?

JSON은 문자열·유한한 숫자·불리언·null·배열·문자열 키 객체로 데이터를 표현합니다. TypeScript에 JsonValue라고 써도, 실행 중 실제 값이 그 모양이라는 증거가 되지는 않습니다.

기존 검사는 바깥쪽만 봤습니다

{ nickname: undefined }
{ scores: [NaN] }

바깥 value는 객체여서 존재하고 null도 아닙니다. 하지만 안쪽은 JSON 데이터가 아니에요. 바로 provider로 보내면 잘못된 내용이 저장될 수 있습니다.

문자열로 바꿔 보면 달라집니다

JSON.stringify({ nickname: undefined })
// "{}"
JSON.stringify({ scores: [NaN] })
// '{"scores":[null]}'

검사하려던 원본이 사라지거나 바뀝니다. 우리 규칙은 원본을 고쳐 통과시키는 대신, 잘못된 입력을 -32602로 거절하는 것입니다.

함수의 일은 하나입니다. 받은 값 전체가 허용한 JSON 데이터인지 확인하고 true 또는 false를 반환합니다. 저장하거나 오류 응답을 보내는 일은 하지 않습니다. host가 false를 보고 오류 응답을 보냅니다. SPEC §6.3 / §9.6 · ADR 0008.

BLOCK 01 / 15 · protocol:104–104

할 일의 종류를 두 개로 나누기

visit은 “값을 살펴볼 차례”, complete는 “자식까지 검사했으니 완료 표시할 차례”입니다. kind는 둘을 구분하는 이름표예요.

type JsonValueTask = { kind: 'visit'; value: unknown } | { kind: 'complete'; value: object };

|는 둘 중 하나의 모양이라는 뜻입니다. visit의 value는 아직 검사하지 않아 unknown이고, complete에는 이미 객체라고 확인한 값만 넣으므로 object입니다.

왜 넣었나 · 빠지면?
값을 만난 순간과 모든 자식을 확인한 순간을 구분하지 않으면, 순환과 안전한 공유를 구별하기 어렵습니다.
BLOCK 02 / 15 · protocol:113–115

검사할 목록과 객체별 메모 만들기

isJsonValue는 unknown을 실제로 검사합니다. value is JsonValue는 true일 때 TypeScript에게 통과한 타입을 알려 주는 표현이에요. 함수 본문이 그 약속을 지켜야 합니다.

export function isJsonValue(value: unknown): value is JsonValue {  const tasks: JsonValueTask[] = [{ kind: 'visit', value }];  const states = new Map<object, 'visiting' | 'valid'>();

tasks에는 처음에 원본 값 하나를 visit으로 넣습니다. states는 Map이라는 메모장으로, 객체 자체를 열쇠 삼아 visiting 또는 valid를 기억합니다. 둘 다 함수 호출 때 새로 만들어 서로 다른 요청의 상태가 섞이지 않습니다.

왜 넣었나 · 빠지면?
메모가 없으면 순환을 찾지 못하거나 공유된 부분을 반복해서 검사합니다. 함수가 자신을 다시 호출하는 재귀 대신 이 목록을 사용하면 깊은 데이터도 호출 한계에 덜 의존합니다.
BLOCK 03 / 15 · protocol:117–123

마지막에 넣은 작업부터 꺼내기

while은 할 일이 남아 있는 동안 반복하고, pop()은 배열의 마지막 작업 하나를 꺼냅니다. 이렇게 “마지막에 넣은 것을 먼저 꺼내는 목록”을 스택이라고 합니다.

  try {    while (tasks.length > 0) {      const task = tasks.pop();      // pop() can return undefined in its TypeScript signature.      if (task === undefined) {        return false;      }

const task는 이번에 처리할 작업입니다. TypeScript의 pop 결과에는 undefined 가능성이 있으므로, 꺼낸 결과가 없으면 false로 끝내 타입을 좁힙니다. 정상적인 이 흐름에서는 length 검사 직후라 이 분기가 발생하지 않습니다.

왜 넣었나 · 빠지면?
마지막 작업부터 꺼내는 성질이 complete의 순서를 보장합니다. 그냥 앞에서부터 꺼내면 현재 등록 순서로는 부모 완료가 자식 검사보다 빨라집니다.
BLOCK 04 / 15 · protocol:125–130

complete는 객체의 완료 도장 찍기

kind === complete이면 객체의 모든 자식이 통과한 뒤 돌아온 작업입니다. 상태를 valid로 바꾸고 다음 반복으로 넘어갑니다.

      if (task.kind === 'complete') {        states.set(task.value, 'valid');        continue;      }      const current = task.value;

states.set은 메모를 갱신합니다. continue는 함수 전체 종료가 아니라 이번 반복의 나머지를 건너뛰는 말입니다. visit인 경우에만 아래 current로 검사할 값을 꺼냅니다.

왜 넣었나 · 빠지면?
complete까지 일반 객체처럼 다시 검사하면, 아직 visiting인 자기 객체를 보고 순환이라고 잘못 거절합니다.
BLOCK 05 / 15 · protocol:132–135

그 자체로 끝나는 값 통과시키기

null·문자열·불리언은 안쪽에 더 검사할 자식이 없는 값입니다. true 또는 false도 모두 유효한 JSON 데이터예요.

      // null is valid JSON; storage's top-level null rule is separate.      if (current === null || typeof current === 'string' || typeof current === 'boolean') {        continue;      }

조건에 해당하면 continue로 다음 작업을 처리합니다. 여기서는 null을 허용합니다. storage.set의 맨 바깥 null 거절은 뒤의 별도 함수에서 처리하므로 { nickname: null }은 허용할 수 있습니다.

왜 넣었나 · 빠지면?
이 분기가 없으면 typeof null이 object라는 자바스크립트 특성 때문에 null을 객체 검사에 넣게 됩니다. 정상 문자열과 불리언도 아래 거절 분기에 걸립니다.
BLOCK 06 / 15 · protocol:137–142

숫자는 유한한지 확인하기

JSON 숫자로 허용할 수 없는 NaN·Infinity·-Infinity를 Number.isFinite로 거절합니다. 유한한 숫자는 값이 정해진 수라는 뜻이며, 0·음수·소수도 허용합니다.

      if (typeof current === 'number') {        if (!Number.isFinite(current)) {          return false;        }        continue;      }

먼저 typeof로 숫자인지 확인하고, 유한하지 않으면 return false로 함수 전체를 끝냅니다. 유한하면 continue입니다. 이 함수 안의 false는 최종 검사 실패입니다.

왜 넣었나 · 빠지면?
숫자라는 타입만 보면 NaN도 통과합니다. JSON.stringify가 이를 null로 바꿀 수 있으므로 저장 내용이 달라집니다.
BLOCK 07 / 15 · protocol:144–147

남은 기본값 중 객체가 아닌 것은 거절

위에서 허용한 기본값은 이미 continue로 빠졌습니다. 여기까지 온 값은 객체·배열이거나, undefined·함수·symbol·bigint 같은 JSON 밖의 값입니다.

      // Reject undefined, functions, symbols, and bigint.      if (typeof current !== 'object') {        return false;      }

object가 아니면 false입니다. symbol은 고유한 식별 값이고 bigint는 별도의 큰 정수 타입입니다. 함수도 JSON 데이터가 아닙니다. 이 분기 뒤에는 current가 null 아닌 객체라고 TypeScript가 알 수 있습니다.

왜 넣었나 · 빠지면?
{ toJSON() { ... } } 안의 함수도 이 단계에서 거절됩니다. 문자열로 바꿔 보려고 함수를 실행하지 않습니다.
BLOCK 08 / 15 · protocol:149–156

순환과 이미 끝난 공유 구분하기

states.get(current)는 같은 객체를 만난 적 있는지 봅니다. visiting이면 현재 검사 경로의 조상으로 다시 돌아왔으므로 순환입니다. valid이면 전에 끝낸 객체를 다른 위치에서 공유한 것입니다.

      const state = states.get(current);      if (state === 'visiting') {        return false;      }      if (state === 'valid') {        continue;      }

visiting은 false, valid는 continue입니다. 아직 메모가 없으면 처음 본 객체이므로 아래 구조 검사를 계속합니다. 값이 똑같은 두 객체와 같은 객체 하나를 구분하는 기준은 객체 자체의 동일성입니다.

왜 넣었나 · 빠지면?
“한 번이라도 본 객체면 거절”만 하면 { left: shared, right: shared }도 잘못 거절합니다. 완료 여부까지 기억해야 합니다.
BLOCK 09 / 15 · protocol:158–174

객체의 모양과 배열의 빈 자리 확인

Array.isArray로 배열 여부를 확인하고, Reflect.ownKeys로 자기 속성의 모든 이름을 가져옵니다. 일반 객체는 Object.prototype 또는 null 원형만 허용합니다. Date·Map처럼 별도 의미가 있는 객체는 거절합니다.

      const array = Array.isArray(current);      const keys = Reflect.ownKeys(current);      let arrayLength = 0;      if (array) {        const length: unknown = Object.getOwnPropertyDescriptor(current, 'length')?.value;        // Dense arrays own every index plus their bookkeeping length.        if (typeof length !== 'number' || keys.length !== length + 1) {          return false;        }        arrayLength = length;      } else {        const prototype = Object.getPrototypeOf(current);        if (prototype !== Object.prototype && prototype !== null) {          return false;        }      }

배열의 length는 원본의 속성 설명자로 읽습니다. ?.는 설명자가 없으면 undefined로 멈추는 표현입니다. 길이 n인 빈틈 없는 배열은 n개 인덱스와 length를 소유하므로 키 수가 n+1이어야 합니다. arrayLength는 뒤에서 범위 확인에 씁니다.

왜 넣었나 · 빠지면?
new Array(1)은 길이 1이지만 실제 인덱스 0이 없습니다. length만 보고 허용하면 JSON 변환이 빈 자리를 null로 메워 데이터가 바뀝니다. 키 수 검사는 다음 인덱스 검사와 함께 사용해야 완전합니다.
BLOCK 10 / 15 · protocol:176–178

검사 중으로 표시하고 완료 작업 예약

이제 구조를 받아들였지만 자식은 아직 확인하지 않았습니다. 객체를 visiting으로 표시한 뒤 complete 작업을 먼저 넣습니다.

      states.set(current, 'visiting');      // The stack processes children before this completion task.      tasks.push({ kind: 'complete', value: current });

상태 메모는 지금 변경하지만 valid는 아직 쓰지 않습니다. 이후 for문에서 자식 visit들을 추가합니다. 마지막에 넣은 것을 먼저 꺼내므로 자식들이 complete보다 위에 놓입니다.

왜 넣었나 · 빠지면?
지금 valid라고 표시하면 자기 자신을 자식으로 만나도 “전에 끝났다”고 건너뛰어서 순환을 허용하게 됩니다. 상세 스택 재생에서 이 순서를 확인할 수 있습니다.
BLOCK 11 / 15 · protocol:180–186

키는 문자열만, length는 별도로 처리

각 키를 검사합니다. 문자열 아닌 symbol 키는 JSON에서 표현할 수 없으므로 거절합니다. 배열의 length는 데이터 원소가 아니라 길이 관리용 속성이어서 건너뜁니다.

      for (const key of keys) {        if (typeof key !== 'string') {          return false;        }        if (array && key === 'length') {          continue;        }

for문은 앞에서 모은 모든 자기 키를 순서대로 봅니다. 일반 객체의 length라는 데이터 키는 건너뛰지 않습니다. array 조건이 붙어 있기 때문이에요.

왜 넣었나 · 빠지면?
Object.keys만 쓰면 symbol이나 숨겨진 속성이 보이지 않아 내용 일부를 조용히 버린 것처럼 승인할 수 있습니다. 배열 length는 enumerable이 아니므로 아래 일반 속성 검사에 넣으면 정상 배열도 거절됩니다.
BLOCK 12 / 15 · protocol:188–199

배열 키가 실제 인덱스인지 확인

숫자 모양의 키를 잠시 숫자로 계산해 0 이상의 정수이고 length 미만인지 확인합니다. String(index) === key는 원래 키가 정확한 인덱스 표기인지 확인합니다.

        if (array) {          const index = Number(key);          // Reject named members and non-canonical index spellings.          if (            !Number.isInteger(index) ||            index < 0 ||            index >= arrayLength ||            String(index) !== key          ) {            return false;          }        }

extra는 정수가 아니고, 01·-0·1e0는 다시 문자열로 만들면 원래 표기와 달라집니다. Number(key)는 검사를 위한 계산일 뿐, 원본 키나 저장 값을 바꾸지 않습니다.

왜 넣었나 · 빠지면?
키 수만 맞추면 빈 자리를 extra라는 속성으로 채운 배열을 놓칠 수 있습니다. JSON 변환이 버리는 배열의 추가 이름 속성도 막아야 합니다.
BLOCK 13 / 15 · protocol:201–209

값을 읽기 전에 속성 설명서 확인

Object.getOwnPropertyDescriptor는 속성에 저장된 값과 설정을 돌려줍니다. getter를 호출해서 결과를 얻는 방식이 아닙니다.

        const descriptor = Object.getOwnPropertyDescriptor(current, key);        // Inspect stored data without executing an accessor.        if (          descriptor === undefined ||          !descriptor.enumerable ||          !Object.hasOwn(descriptor, 'value')        ) {          return false;        }

설명자가 없으면 검사 근거가 없어서 거절합니다. enumerable이 false인 숨겨진 속성도 거절합니다. 설명자 자체가 value 항목을 직접 가지고 있어야 합니다. getter 속성의 설명자에는 get/set이 있고 value가 없습니다.

왜 넣었나 · 빠지면?
current[key]나 Object.values로 먼저 읽으면 호출자가 넣은 getter를 실행할 수 있습니다. 아래 실험에서 “설명서 보기”와 “값 직접 읽기”의 실행 횟수를 비교할 수 있어요.
BLOCK 14 / 15 · protocol:211–220

자식 작업 추가, 전체 성공 또는 조사 실패

확인한 속성의 저장 값만 새 visit 작업으로 추가합니다. 값이 또 객체면 다음 반복들이 동일한 규칙으로 검사합니다. 원본을 수정하는 할당은 없습니다.

        tasks.push({ kind: 'visit', value: descriptor.value });      }    }    return true;  } catch {    // Failed structural inspection cannot establish valid JSON data.    return false;  }}

tasks가 모두 비면 모든 값이 통과했으므로 true입니다. 구조를 조사하는 중 예외가 나면 catch가 false를 반환합니다. try/catch는 검사 불가능한 값을 성공으로 처리하지 않기 위한 장치입니다.

왜 넣었나 · 빠지면?
스택 없이 자식을 처리하면 중첩 값을 놓칩니다. 예외를 밖으로 던지기만 하면 host의 기존 입력 오류 분기로 돌아오지 못합니다. 임의 Proxy의 부수 효과를 모두 막는 것은 이 검사 범위 밖입니다.
BLOCK 15 / 15 · protocol:359–369

저장 규칙에 연결하기

isJsonValue는 모든 JSON 값의 검사이며, 저장 API의 추가 조건은 isStorageSetParams가 맡습니다. isJsonObject로 params 외형, string key, 바깥 value 존재·null 정책을 확인한 뒤 전체 검사를 호출합니다.

export function isStorageSetParams(params: JsonValue | undefined): params is StorageSetParams {  // Test absence explicitly: a truthiness check would also reject false, 0,  // and "". Inspect only the outer value so nested null remains valid data.  return (    isJsonObject(params) &&    typeof params.key === 'string' &&    params.value !== undefined &&    params.value !== null &&    isJsonValue(params.value)  );}

&&는 앞 조건이 실패하면 뒤를 실행하지 않습니다. undefined와 null을 정확히 비교하므로 false·0·빈 문자열을 거절하지 않습니다. host는 이 결과가 false면 -32602를 보내고 provider를 호출하지 않습니다.

왜 넣었나 · 빠지면?
함수만 만들어 연결하지 않으면 기존 저장 동작은 바뀌지 않습니다. null 규칙을 일반 JSON 검사 안으로 넣으면 저장 값 내부의 null까지 잘못 거절하게 됩니다.
Deep dive 01

① 순환과 공유 참조는 왜 다른가?

참조는 객체 내용의 복사본이 아니라, 그 객체를 가리키는 연결입니다. 집 주소를 두 종이에 적어도 집은 하나인 것처럼, 변수나 속성 두 개가 같은 객체를 가리킬 수 있습니다.

순환 · 거절
const a = {};
a.self = a;

a → self → a → self… 끝없이 돌아갑니다. 자식 검사가 끝나지 않아 a는 visiting인 동안 다시 등장합니다. 원본을 바꾸지 않는 JSON 데이터로 표현할 수 없어 거절합니다.

공유 · 허용
const shared = { enabled: true };
const value = {
  left: shared,
  right: shared,
};

어느 쪽을 따라가도 S에서 끝납니다. S를 한 번 끝까지 검사한 뒤 valid로 기억하면 다른 위치에서 다시 만나도 허용할 수 있습니다.

“전에 본 적 있나?”보다 “지금 검사 중인가, 이미 끝났나?”가 중요합니다.
visiting 재등장 → 검사 중인 조상으로 돌아옴 → 순환 거절
valid 재등장 → 끝낸 내용을 공유함 → 허용·재검사 생략

공유 내용은 JSON 문자열로 표현할 때 각 위치에 같은 내용이 반복됩니다. 객체 동일성 자체를 JSON이 보존한다는 뜻은 아닙니다. 여기서는 원본을 바꾸지 않고 검사·전달합니다.

공유를 기억하면 빠른 이유

let value = { leaf: true };
for (let i = 0; i < 30; i += 1) {
  value = { left: value, right: value };
}

실제 객체는 31개지만 모든 경로를 다시 따라가면 마지막 leaf를 2의 30제곱, 즉 10억 번 이상 방문합니다. valid 메모를 재사용하면 같은 객체의 자식을 다시 펼치지 않습니다. 다만 이렇게 빠르게 검사해도, 문자열로 모두 펼친 크기는 클 수 있습니다. 검사 효율과 전송 크기 제한은 별개의 문제입니다.

Deep dive 02

② complete는 왜 먼저 넣고 나중에 처리할까?

스택은 마지막에 넣은 작업을 먼저 꺼냅니다. complete는 부모의 완료 예약표예요. 자식들의 visit을 그 위에 올려 놓으면 자식이 끝나야 예약표를 꺼낼 수 있습니다.

tasks.push({ kind: 'complete', value: current });
// Then add each child's visit task.

예를 들어 키가 a, b 순서면 등록은 complete 부모 → visit a → visit b이고, 실제 꺼내는 순서는 b → a → complete 부모입니다. a가 또 객체라면 a의 자식들도 a의 complete보다 먼저 처리합니다. a와 b 중 어느 것을 먼저 보든 모두 검사하므로 최종 판정에는 영향이 없습니다.



할 일 목록 · tasks
위쪽이 맨 마지막 요소입니다. 다음 pop은 맨 위를 꺼냅니다.
    객체 상태 메모 · states
    visiting = 검사 중 / valid = 자식까지 완료
    이 재생은 실제 코드의 작업 순서를 설명하는 고정 예제입니다. 속성 키를 등록한 뒤의 상태를 보여 주며, 각각의 기본 형식 검사까지 한 줄씩 실행하는 디버거는 아닙니다.
    

    valid를 너무 일찍 쓰면?
    자식 확인 전 valid로 표시한 객체가 자신을 다시 가리키면 “이미 검증됐다”고 건너뛰어서 순환을 놓칩니다. 먼저 visiting, 모든 자식 후 valid라는 순서가 필요합니다.
    complete를 자식보다 나중에 넣으면?
    스택 맨 위에 부모 complete가 놓여 먼저 실행됩니다. 위의 문제처럼 자식보다 먼저 valid가 됩니다. 그래서 등록은 complete 먼저, 처리는 complete 나중입니다.
    

    일반 함수 호출의 자동 호출 스택을 사용하면 깊이 20,000인 데이터에서 한계가 생길 수 있습니다. 지금은 자바스크립트 배열로 할 일을 관리합니다. 이 테스트의 20,000은 스트레스 예제이고, 허용 깊이의 공식 최대치는 아닙니다.
    

    

    Deep dive 03
    ③ getter를 실행하지 않고 속성을 검사하기
    getter는 속성을 읽을 때 호출되는 함수입니다. value.nickname처럼 읽어도 저장된 문자열을 가져오는 대신 코드가 실행될 수 있어요. JSON 입력은 데이터여야 하므로, 검사하려고 입력의 함수를 실행하지 않습니다.
    값을 직접 읽으면 실행
    const value = {
  get nickname() {
    calls += 1;
    return 'Moon';
  },
};
value.nickname; // Executes the getter.
    Object.values도 값을 읽으므로 getter를 실행할 수 있습니다. 실행 후 정상 문자열이 나와도, 원본이 데이터 속성이었다는 증명은 아닙니다.
    설명서는 실행 없이 구분
    Object.getOwnPropertyDescriptor(
  value, 'nickname'
);
// Accessor: { get: function, set: undefined, ... }
// Data:     { value: 'Moon', writable: true, ... }
    설명자에 직접 value 항목이 있는지 확인합니다. getter 속성은 get/set으로 표현되므로 거절합니다. descriptor.value는 원본 속성이 아니라 설명서에 담긴 데이터입니다.

    세 가지 조건을 함께 확인하는 이유
    조건왜 필요한가
    descriptor가 존재앞에서 키를 봤어도 설명서를 얻지 못하면 검사할 근거가 없습니다. 구조 조사 실패를 성공으로 취급하지 않습니다.
    enumerable이 true일반 JSON 변환에서 빠지는 숨겨진 속성을 몰래 버리고 승인하지 않으려고 거절합니다.
    Object.hasOwn(descriptor, 'value')설명자가 자체 value를 가진 데이터 속성인지 확인합니다. get/set이 있는 접근자 속성은 실행하지 않고 거절합니다.
    

    toJSON은 JSON.stringify가 호출할 수 있는 사용자 함수입니다. 우리 검사는 문자열로 변환하지 않고 구조를 살펴보므로 이를 호출하지 않습니다. 일반 객체의 toJSON 함수도 검사 목록에 들어오면 함수 타입이라 거절합니다.
    “getter를 실행하지 않는다”는 임의 Proxy까지 아무 부수 효과 없이 조사한다는 약속은 아닙니다. Proxy는 구조 조사 자체에 함수를 연결할 수 있습니다. ADR 0008은 이 경계를 별도로 기록합니다.

completed objects may be shared. * This check does not impose size limits or prevent Proxy trap side effects. */export function isJsonValue(value: unknown): value is JsonValue {  const tasks: JsonValueTask[] = [{ kind: 'visit', value }];  const states = new Map<object, 'visiting' | 'valid'>();  try {    while (tasks.length > 0) {      const task = tasks.pop();      // pop() can return undefined in its TypeScript signature.      if (task === undefined) {        return false;      }      if (task.kind === 'complete') {        states.set(task.value, 'valid');        continue;      }      const current = task.value;      // null is valid JSON; storage's top-level null rule is separate.      if (current === null || typeof current === 'string' || typeof current === 'boolean') {        continue;      }      if (typeof current === 'number') {        if (!Number.isFinite(current)) {          return false;        }        continue;      }      // Reject undefined, functions, symbols, and bigint.      if (typeof current !== 'object') {        return false;      }      const state = states.get(current);      if (state === 'visiting') {        return false;      }      if (state === 'valid') {        continue;      }      const array = Array.isArray(current);      const keys = Reflect.ownKeys(current);      let arrayLength = 0;      if (array) {        const length: unknown = Object.getOwnPropertyDescriptor(current, 'length')?.value;        // Dense arrays own every index plus their bookkeeping length.        if (typeof length !== 'number' || keys.length !== length + 1) {          return false;        }        arrayLength = length;      } else {        const prototype = Object.getPrototypeOf(current);        if (prototype !== Object.prototype && prototype !== null) {          return false;        }      }      states.set(current, 'visiting');      // The stack processes children before this completion task.      tasks.push({ kind: 'complete', value: current });      for (const key of keys) {        if (typeof key !== 'string') {          return false;        }        if (array && key === 'length') {          continue;        }        if (array) {          const index = Number(key);          // Reject named members and non-canonical index spellings.          if (            !Number.isInteger(index) ||            index < 0 ||            index >= arrayLength ||            String(index) !== key          ) {            return false;          }        }        const descriptor = Object.getOwnPropertyDescriptor(current, key);        // Inspect stored data without executing an accessor.        if (          descriptor === undefined ||          !descriptor.enumerable ||          !Object.hasOwn(descriptor, 'value')        ) {          return false;        }        tasks.push({ kind: 'visit', value: descriptor.value });      }    }    return true;  } catch {    // Failed structural inspection cannot establish valid JSON data.    return false;  }}

    1 · isStorageSetParams 설명 — 정리 완료
    이전 주석의 “중첩 데이터를 검사하지 않는다”는 설명을 실제 검사 동작에 맞췄습니다. 주석은 개발자가 읽는 안내문이라서 실행 동작은 그대로지만, 다음에 코드를 읽을 때 잘못 이해하는 일을 줄입니다.
    /**
 * SPEC §6.3 / §9.6 / ADR 0004 / ADR 0008 — validate before storage access.
 * Require a string key and a non-null JSON value without changing input.
 * isJsonValue checks nested data and rejects non-JSON values and cycles.
 * Nested null remains valid; only a top-level null is reserved for absence.
 * This validates storage params, not the complete inbound message.
 */
// Check absence explicitly so false, 0, and "" remain valid values.
// Reject only top-level null here; isJsonValue validates nested contents.
    문서 주석은 함수 위에, 마지막 두 줄은 함수 안에 반영했습니다. 영어 주석은 저장소의 언어 규칙을 따릅니다. 입력 검증을 다루는 SPEC §9.6의 설명 정비이며, 전체 메시지 검증은 별도 후속 task입니다.

    기억 점검 · 답을 먼저 생각해 보기
    1. 같은 객체를 두 번 만났다고 언제나 순환인가요?
    2. complete는 먼저 넣었는데 왜 나중에 처리하나요?
    3. descriptor에서 value가 있는지 확인하기 전에 current[key]를 읽으면 왜 문제가 되나요?
    답 확인
    1. 아닙니다. 검사 중인 조상(visiting)으로 돌아오면 순환이고, 끝낸 객체(valid)를 재사용하면 공유입니다.
    2. 스택이 마지막에 넣은 자식 visit부터 꺼내기 때문입니다.
    3. getter가 실행될 수 있고, 실행 후 얻은 값은 원래 속성이 순수 데이터였다는 증명이 아니기 때문입니다.
