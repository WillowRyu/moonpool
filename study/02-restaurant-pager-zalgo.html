① 패키지 4개 = 레스토랑 부품 4개

손님(미니앱)과 주방(네이티브 앱)이 주문서로 소통하는 레스토랑입니다.

손님 테이블 — 미니앱 (웹뷰 안)

미니앱 코드"프로필 보여줘" 같은 의도
client — 주문 접수기주문서 작성 · 번호표 붙이기 · 진동벨 울리기 · 타임아웃

주방 — 네이티브 앱

요리사들 (기능 핸들러)profile.get, storage.set …
host — 지배인 + 주방양식 검사 · 자격(권한) 확인 · 요리사 호출 · 응답 반송
transport-iframe — 서빙 카트주문서/음식을 물리적으로 나름 · 매장(플랫폼)마다 교체되는 유일한 부품
protocol — 메뉴판 + 주문서 양식공용 단어 사전 (메시지 모양 · 에러 코드 · 카트 규격) · 스스로 하는 일 없음

왜 4개로 나눴나

분리이유
protocol 따로손님과 주방이 같은 양식을 봐야 함. 사전이 두 곳이면 언젠가 어긋난다.
client / host 따로실행 장소가 다르고(웹뷰 안 vs 네이티브), 보안: 권한 검사가 손님 손에 있으면 조작 가능 → SPEC §9.3 "검사는 dispatch 시점에 host에서".
transport 따로플랫폼이 바뀌면 서빙 방법만 바뀐다. iOS 지원 = 카트 하나 새로 만들기.

현재 상태: protocol ✅ 완성(타입·상수) · client/host 빈 껍데기(메인테이너가 구현 예정) · transport-iframe 나중에.

② TransportPair = 종이컵 전화기 한 쌍

테스트는 진짜 iframe 없이 미니앱을 연기해야 합니다. 계층화 덕분에 호스트는 §3.1 Transport 규격(send / onMessage / close)만 지키면 진짜 카트인지 장난감인지 구별할 수 없어요. 그래서 메모리 안에서만 도는 전화기를 꽂습니다.

컵 a테스트가 잡음
(미니앱 역)
마이크로태스크로 배달 (항상 비동기)
컵 b호스트에게 쥐여줌
host.connect(b)

테스트 한 판의 왕복

  1. 테스트: a.send(주문서) — portal.initialize 등
  2. 전화선: 메시지를 마이크로태스크 목록에 올림 (즉시 배달 금지!)
  3. 호스트: b의 핸들러(초인종에 연결한 스피커)로 수신
  4. 호스트: 양식 검사 → 규칙 적용 → 응답 작성
  5. 호스트: b.send(응답)
  6. 전화선: a쪽으로 배달
  7. 테스트: a의 핸들러로 받아 배열에 저장 → await flush() 후 내용 검사
createLinkedTransports()의 비밀 — 컵마다 "내 명단(own)"과 "상대 명단(peer)"을 엇갈려 물려준다: a의 상대 명단 = b의 명단. 그래서 a.send가 b의 핸들러들을 울린다.

③ 진동벨 시스템 — promise correlation

Promise(프로미스) — "결과가 나중에 오면 알려줄게"라는 티켓. 카페 진동벨과 같다: 받는 순간엔 커피가 없지만, 울리면(resolve) 받으러 가면 된다. 실패로 울릴 수도 있다(reject — "재료 소진").

문제 상황: 미니앱이 주문을 여러 개 걸어놓는데, 응답은 시간차를 두고 도착합니다. 어떤 응답이 어떤 주문의 답일까요? 해법이 번호표(id)와 대기 명부예요. 이것이 client 패키지의 심장, promise correlation(응답 짝 맞추기)입니다.

client가 하게 될 일 (곧 메인테이너가 구현)

  1. call('profile.get') 호출 → 새 번호표 발급 (1, 2, 3… 증가만 함, §4.1)
  2. 대기 명부(Map: 번호 → 진동벨)에 등록하고, 호출자에겐 Promise(진동벨)를 돌려줌
  3. 주문서를 transport로 전송
  4. 응답 도착 → id를 읽고 명부에서 벨을 찾아 울림 — result면 resolve, error면 reject → 명부에서 삭제
  5. 30초(§4.5) 안에 안 오면: 벨을 실패(-32003 TIMEOUT)로 울리고 명부에서 삭제. 그 뒤 늦게 도착한 응답은 명부에 없으므로 조용히 무시 — 스펙이 이걸 MUST로 요구
대기 명부 (pending Map) — 응답 { "id": 2, "result": … } 도착!
번호표(id)무슨 주문진동벨
1portal.initialize🔔 대기 중
2profile.get🔔 → ✅ 지금 울림! (resolve) 후 명부에서 삭제
3storage.get🔔 대기 중

번호표를 재사용하지 않는 이유(§4.1): 지워진 번호가 재활용되면 "늦게 온 옛 응답"이 새 주문의 답으로 오인될 수 있다. 증가만 하는 번호는 그 사고를 원천 차단한다.

④ Zalgo — 왜 "항상 비동기"로 통일하는가

동기(sync) — 그 자리에서 끝날 때까지 기다렸다가 다음 줄로. 비동기(async) — 일을 걸어두고 다음 줄로 넘어가고, 결과는 나중에 받는 것.

"Zalgo(잘고)"는 인터넷 밈 괴물 이름인데, Node.js 커뮤니티에서 "어떤 때는 동기로, 어떤 때는 비동기로 콜백을 부르는 API"가 낳는 지옥을 부르는 별명이 됐어요. 왜 지옥이냐면:

✗ 배달이 "즉시(동기)"라면

let ready = false;
transport.send(msg);
// ← 이 순간 상대 핸들러가
//    이미 실행돼 버림!
ready = true;
// 핸들러는 ready=false를 봤다.
// 코드 순서와 실행 순서가 어긋남.

✓ 배달이 "항상 나중(비동기)"이면

let ready = false;
transport.send(msg);
ready = true;
// 핸들러는 반드시 이 뒤에 실행.
// 위에서 아래로 읽은 그대로
// 동작한다. 예측 가능.

진짜 무서운 건 "가끔"이에요. 열에 아홉은 비동기인데 캐시에 있으면 동기 — 이런 API는 테스트에선 통과하고 현장에서 가끔만 터지는, 재현 불가능한 버그를 만듭니다. 그래서 JavaScript의 Promise 표준(Promises/A+)은 .then 콜백을 무조건 비동기로 실행하도록 아예 명세에 박아버렸어요.

Moonpool에 적용하면 — ① 가짜 전화선의 send가 Promise.resolve().then(…)으로 배달을 미루는 이유: 진짜 postMessage는 절대 즉시 배달되지 않으니, 가짜가 즉시 배달하면 "테스트에서만 통과하는 코드"가 생긴다. ② SPEC §9.5 "동기 브릿지 호출은 어떤 층에도, 영원히 금지"의 이유: 동기 API가 하나라도 있으면 iOS/Android transport는 물리적으로 구현 불가능해진다.
