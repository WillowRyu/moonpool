Date: 2026-10-26
Status: Browser v0.1 milestone complete — T01–T21.
Normative source: [SPEC.md](../SPEC.md); this record does not amend it.

## Completion scope

The completed deliverable is the source workspace, pure protocol/client/host
kernel, iframe transport and reference browser-development embedder. It implements
the seven v0.1 completion requirements in CLAUDE.md and the T01–T21 plan.
The declared browser configuration is the served-wrapper profile in SPEC §8.1.1,
measured with Chrome 156 on macOS. This is a scoped implementation/evidence
record, not an all-platform or all-browser security certification.

Protocol 0.1 remains a draft with unstable compatibility. Workspace packages
are private, versioned 0.1.0, and export TypeScript source. Package distribution,
release tags and publication are separate maintainer actions. The production
moonpool:// origin requirement remains; native cores and production HTTPS
hosting are not part of the completed browser milestone.

## Architecture and security evidence

Source review of protocol, client and host found imports only from internal
modules and @moonpool/protocol. Protocol has no runtime dependency; client/host
depend only on that workspace package. Their typecheck omits the DOM library;
the browser adapter/examples have a separate DOM-enabled configuration.
Timers and queueMicrotask retain their existing narrow runtime declarations.
Platform integration remains outside the pure kernel.

| SPEC §9 requirement | Current enforcement | Evidence |
| --- | --- | --- |
| 9.1 Origin binding | Exact origin and native source-window checks; pinned outbound targetOrigin | Peer/adapter unit tests; T20 records 35–42 isolate each native gate with positive controls |
| 9.2 Navigation containment | Served trusted wrapper per Portal, narrow enforcing CSP, instance/Document binding and terminal cleanup | Accepted [ADR 0022](adr/0022-constrain-browser-navigation-with-host-csp.md), [T18](browser-containment-verification.md), T20 records 18–19, 28–34, 50–52 and response headers |
| 9.3 Scope at dispatch | Host-held manifest/grant intersection before provider invocation; method namespace is the scope | Permission tests; T20 denied CRUD yields zero provider calls, followed by allowed-call controls |
| 9.4 No host credentials | Public profile projection; sanitized provider failures; private details stay in host diagnostics | Profile/provider tests, T19 exception cases, T20 dummy-private-field observation |
| 9.5 Async capabilities | Client calls and injected capabilities return Promises; transport submission remains the §3.1 primitive | Public interfaces, host/client tests, actual browser calls/dismissal/notifications |
| 9.6 Input validation | Staged envelope/params JSON checks, field schemas and manifest admission before provider access | JSON/params/manifest suites; T20 native Date rejection without a write and inert markup rendering |
| 9.7 No ambient authority | Grants/id/origin come from host registry/config, not guest claims or screen context | Permission/provider-binding tests, T20 forged grants/SOP checks and denied-provider counters |

Trusted wrappers share host authority; they do not isolate hostile host code
from the outer host. Each guest remains at its distinct app origin. The retained
storage provider partitions by host-selected app id; browser-native storage
separately follows engine origin rules. Same-app instances share their app data
and retain separate connection state. The memory provider ends with its owner.

Manifest parsing checks path grammar without I/O. The reference entry is the
host-bundled hello app file under its fixed development root. Native/package
loaders remain responsible for actual file/symlink confinement under SPEC §7.
Injected providers are trusted implementations and must honor their result and
partition contracts. Generic client.call returns unknown; view-specific result
checks and trusted host handshake metadata retain their existing model.

## Retained limits and open work

- **Same-origin document epochs:** §11 knowingly accepts that an older response
  may match a new document's reused id after inner reload. Terminal Portal
  disposal suppresses retired-instance sends; it does not solve that epoch issue.
- **Peer disconnect:** local client.close drains requests, while remote teardown
  has no generic close signal. Surviving clients retain timeout behavior.
- **Consent and throttling:** grants are fixed per connection; no runtime consent
  UI, cancellation producer or rate-limit/backoff policy is implemented.
- **Host availability/string decoding:** -32007 and -32700 are receivable codes
  without current generic emitters. All 14 receiver mappings are tested.
- **Composition versus communication:** different-origin Portals coexist; guest
  addressing/broadcast between Portals remains the §11 question.
- **Other §11 questions:** streaming/progress, capability discovery and an
  imminent-destruction lifecycle state remain unspecified.
- **Resource bounds:** §4.2 defines no payload/depth quota or protection against
  arbitrary Proxy trap effects. Existing validation does not establish those limits.
- **Deployment/platform breadth:** HTTP origins and the CSP server are browser
  development. Native custom-scheme hosts/cores and production web hosting need
  their own implementation/verification; other engines/schemes/history/BFCache
  and GC/performance are not certified by the current observations.
- **Diagnostics:** the retained MutationObserver error also reproduces in
  script-free nested HTML; its precise browser/tooling source remains unknown.
  The Vite future-loader advisory is non-blocking in the tested build.

These are existing scope boundaries and accepted open questions, not silently
closed issues. SPEC, protocol version and APIs remain authoritative and unchanged.
No required T01–T21 browser-milestone gate remains pending. Further implementation
belongs to a separately scoped maintainer request.
